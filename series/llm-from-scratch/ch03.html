The problem attention was invented to solve

The problem. Suppose you're translating German to English. You cannot translate word by word — grammar reorders things, and a word's meaning depends on words far away from it. So pre-transformer translation systems used an encoder–decoder RNN: the encoder read the source sentence one word at a time, updating a hidden state as it went; the decoder then took the encoder's final hidden state and generated the translation from it, word by word.

Look at what that architecture asserts: the meaning of an entire sentence — however long — fits inside one fixed-size vector, and the decoder may never look back at anything earlier. For a six-word sentence, fine. For a forty-word sentence with a pronoun referring to a noun fifteen words back, the information that pronoun needs was crushed long before the decoder got there.

You don't need to know how RNNs work internally to build an LLM. The only thing to carry forward is why they were replaced: one vector is too small a doorway for a whole sentence to fit through.

Attention arrives — in two steps, three years apart

Step one (2014). The Bahdanau attention mechanism (Bahdanau, Cho & Bengio, Neural Machine Translation by Jointly Learning to Align and Translate, 2014) modified the encoder–decoder RNN so the decoder could selectively reach back to any encoder position at every decoding step — deciding, per output word, which input words matter right now. The bottleneck was gone: nothing had to squeeze through a single vector anymore.

Step two (2017). Researchers then discovered something more surprising: once you have attention, the RNN itself is unnecessary. The resulting architecture — the transformer, from Vaswani et al., Attention Is All You Need, 2017 — replaced recurrence entirely with a form of attention called self-attention. That is the mechanism inside GPTs, and it is what we now build.

The “self” in self-attention

Bahdanau attention relates two sequences — an input sentence and an output translation. Self-attention relates a sequence to itself: every position in one sentence weighs the relevance of every other position in that same sentence. That one word, “self,” is the whole distinction.

Simple self-attention — no trainable weights yet

We start with a deliberately stripped-down version — version 1 on the route strip, with nothing to learn — because it isolates the mechanism. Once you can compute this version by hand, the real one is a small edit.

What we're computing, in plain words

The word “journey” means something slightly different in “your journey starts” than in “a journey of a thousand miles”. Its embedding from Unit 2, though, is fixed — the same vector wherever the word appears. What we want is an upgraded vector for each token that has absorbed its surroundings: mostly “journey”, blended with a bit of every other word in the sentence, in proportion to how relevant each one is. That upgraded vector is called a context vector, written z.

So for each token we need two things: a relevance number for every other token, and a way to blend with those numbers. That's genuinely all attention is.

Our running example: the sentence “Your journey starts with one step”, already embedded as six 3-dimensional vectors. (Three dimensions is absurdly small — GPT-2 uses 768 — but it fits on a page and your mental arithmetic.)

Step 1 of 3 — a relevance number: the dot product

The problem. We need a single number that says “how relevant is token j to token i?” — computed from nothing but their two vectors.

The idea. Unit 2 gave us the key: embeddings are laid out so that related words point in similar directions. So “how relevant?” can be answered with “how aligned are the two vectors?” — and the standard measure of alignment is the dot product: multiply the vectors element by element, add it all up. Aligned vectors → big positive number. Unrelated vectors → small number.

Worked by hand — “Your” · “journey”

Take x(1) = [0.43, 0.15, 0.89] and x(2) = [0.55, 0.87, 0.66]. Multiply position by position, then sum:

0.43·0.55 + 0.15·0.87 + 0.89·0.66
= 0.2365 + 0.1305 + 0.5874
= 0.9544

One number, measuring alignment. Do this for the query against all six tokens and you get six numbers — the attention scores ω (omega):

scores for “journey”: [0.9544, 1.4950, 1.4754, 0.8434, 0.7070, 1.0865]

“journey”·“journey” = 1.4950 is the biggest — a vector is maximally aligned with itself. “starts” (1.4754) is nearly as high: its embedding happens to lie close to “journey”'s. “one” (0.7070) is the least aligned.

The same thing in code ▶ Run in Colab
query = inputs[1]                            # x(2), "journey" — Python counts from 0
attn_scores_2 = torch.empty(inputs.shape[0])
for i, x_i in enumerate(inputs):
    attn_scores_2[i] = torch.dot(x_i, query)
print(attn_scores_2)

Try “journey” against “starts” (their embeddings are nearly parallel — high score) and then against “one” (low score). This is the Unit 2 payoff: because embeddings encode relatedness as direction, a dot product converts relatedness into a number.

Step 2 of 3 — from scores to weights: softmax

The problem. The six scores are raw and unbounded — they don't sum to anything meaningful, so you can't yet read them as “how much of my attention goes where”. We want each score converted to a share: all positive, summing to exactly 1.

The obvious fix is to divide each score by the total. That works — it produces weights [0.1455, 0.2278, 0.2249, 0.1285, 0.1077, 0.1656] — but it breaks the moment a score is negative (shares below zero make no sense), and it treats scores linearly, which turns out to give poor training signals.

The real fix: softmax. First push every score through eˣ — this makes everything positive (e to any power is positive) and stretches gaps: bigger scores get disproportionately bigger. Then divide by the total.

Worked by hand — softmax of the six scores
softmax(ω)ᵢ = e^ωᵢ / Σⱼ e^ωⱼ

Exponentiate each score:

e^0.9544=2.597 e^1.4950=4.459 e^1.4754=4.373
e^0.8434=2.324 e^0.7070=2.028 e^1.0865=2.964

Sum = 18.745. Divide each by it:

weights α = [0.1385, 0.2379, 0.2333, 0.1240, 0.1082, 0.1581] (sums to 1.0)

Now the numbers read as percentages: “journey” gives 23.8% of its attention to itself, 23.3% to “starts”, 10.8% to “one”. Run the notebook cell and PyTorch prints these exact values.

Why softmax and not plain division?

Three reasons, in increasing order of importance: (1) it works for negative scores; (2) it handles extreme values gracefully; (3) it has favourable gradients during training — softmax's smooth exponential shape gives the training loop a usable slope almost everywhere, which plain division doesn't. In practice you always call torch.softmax rather than writing your own: the naive version overflows on large inputs, and PyTorch's is numerically hardened.

Step 3 of 3 — blend: build the new “journey” out of the whole sentence

The problem. We now know how much each word matters to “journey” — 24% itself, 23% “starts”, 14% “Your”… But that's just a list of percentages. The goal from the start was an upgraded vector for “journey”, one that carries its surroundings. How do percentages become a vector?

The idea — mixing paint. Suppose each word's embedding is a pot of paint, and the weights are your recipe: “take 24% of the journey colour, 23% of the starts colour, 14% of the Your colour…” Mix, and you get one new colour — recognisably close to “journey”'s original shade, but visibly tinted by everything around it. That mixing is precisely what the maths does: scale each token's vector by its percentage, then add them all up.

Look once more at what falls out, because it's the point of the whole mechanism: the tokens with big weights dominate the mixture, the ones with small weights barely tint it. A different sentence would produce different weights — a different recipe — and so a different “journey” vector. The word finally means what its sentence makes it mean.

The weighted sum as paint-mixing: six vectors, each contributing its percentage, added into one new vector — mostly “journey” and “starts”, faintly “one”.
Worked by hand — the context vector z(2)
z(2) = 0.1385·[0.43,0.15,0.89] + 0.2379·[0.55,0.87,0.66]
     + 0.2333·[0.57,0.85,0.64] + 0.1240·[0.22,0.58,0.33]
     + 0.1082·[0.77,0.25,0.10] + 0.1581·[0.05,0.80,0.55]
z(2) = [0.4419, 0.6515, 0.5683]

Compare with the raw embedding x(2) = [0.55, 0.87, 0.66]: same shape, different values — “journey”, now carrying a blend of its sentence. The notebook reproduces this exact vector.

Common confusion

“Why does z come out the same size as the input embedding?” Because it's a weighted average of vectors, and an average of 3-dimensional vectors is itself 3-dimensional. This matters more than it looks: since context vectors have the same shape as embeddings, the output of attention can be fed into another round of attention. That's why transformer blocks stack — Unit 4 stacks twelve of them.

All six tokens at once

We computed z(2) with loops, for one query. Every other token needs the identical treatment — which would be a nested loop, and loops are slow. Matrix multiplication does all of it in one operation, because a matrix product is nothing but every-row-dotted-with-every-column: exactly the all-pairs dot products we want.

The whole simplified mechanism as three matrix operations. Row i of the (6,6) matrices belongs to token i as the query; the shapes are the bookkeeping that keeps you honest.
Three lines replace all the loops ▶ Run in Colab
attn_scores  = inputs @ inputs.T                      # (6,3) @ (3,6) → (6,6), all-pairs dots
attn_weights = torch.softmax(attn_scores, dim=-1)     # softmax each ROW (dim=-1 = last dim)
all_context  = attn_weights @ inputs                  # (6,6) @ (6,3) → (6,3), six blends
all_context =

Common confusion

“In the (6,6) matrix, which direction is which?” Row i, column j answers: how much does token i attend to token j? Rows are queries (the token doing the looking); columns are the tokens being looked at. Each row sums to 1 after softmax — that's what dim=-1 means: normalise along the last dimension, i.e. across each row. Get this orientation into your fingers now; the causal mask in Part 2 makes no sense without it.

Trainable weights — the real mechanism

This is the step where most readers fall off the unit, so we'll climb it one rung at a time. Nothing about the three-step machine changes — we're only upgrading where the vectors come from before the machine runs.

Rung 1 — see the flaw in what we built

The simple version contains not a single learnable number. Walk through what that means: the attention scores were dot products of the raw embeddings, so “how much does journey attend to starts?” is answered entirely by how similar their embeddings happen to be. The attention pattern is frozen at whatever similarity Unit 2 delivered.

And similarity is often the wrong question. Take the sentence “the cat that the dog chased was black”. To predict what follows “was”, the model desperately needs “was” to attend to “cat” — its subject. But “was” and “cat” are not similar words; their embeddings don't especially align. Frozen-similarity attention can never route that connection. Relevance ≠ similarity, and we've built a machine that can only do similarity.

Rung 2 — one knob: transform before you compare

Here's the smallest possible fix. What if, before dotting, we passed every embedding through a trainable transformation — a matrix W — and dotted the transformed vectors instead?

A matrix reshapes a vector space: it can stretch some directions, shrink others, rotate the whole thing. So a trainable W means training can move vectors around before the comparison happens — it could learn a transformation under which verb-vectors land close to their subject-vectors, making “was”·“cat” score high after transformation even though the raw embeddings disagree. The dot product still measures alignment; W decides what gets aligned. That single idea is the whole leap. Everything from here is refinement.

Rung 3 — why one knob isn't enough: the three jobs

Now look closely at how a token's vector actually gets used inside the three-step machine, and you'll notice it is quietly doing three different jobs:

  • acting as the seeker — “as the current token, what am I looking for?” (the query role),
  • acting as the advertisement — “as some other token, here is what I offer for matching” (the key role),
  • acting as the content — “if you pick me, this is what actually gets blended in” (the value role).

With a single W, all three jobs share one transformation — tuning it to improve matching would simultaneously corrupt what each token contributes as content. The jobs pull in different directions. So give each job its own knob: Wq transforms a token when it's the seeker (producing its query), Wk when it's being matched against (its key), Wv for what it contributes to the blend (its value). Three matrices, because three jobs. That's the entire reason Q, K and V exist — nothing deeper.

And to say it before the maths does: training will touch nothing but these three matrices. The dot products, the softmax, the weighted sum — all fixed machinery. When Unit 5's training loop runs, the only thing being learned in this mechanism is what the three transformations should be.

The database analogy behind the names

The vocabulary comes from information retrieval. A query is what you type into the search box. Each stored item has a key it is indexed under, matched against your query. And each item has a value — the content you actually retrieve. Attention is a soft lookup: instead of returning the single best match, it returns a weighted blend of every value, weighted by how well each key matched the query.

One token, three roles, three trainable projections. Every token in the sentence gets all three. The numbers shown are the real values torch.manual_seed(123) produces — you'll compute them below.

The mechanism, re-run with projections

Here's the beautiful part: the three steps do not change. Scores are now query·key instead of input·input; the blend is over values instead of raw inputs; and one new scaling step appears before softmax. Everything else is the machine you already know.

We set d_in = 3 (the embedding size we have) and d_out = 2 (the projection size), deliberately different so you can see which is which in the shapes. In real GPTs they're equal.

The one new step: divide by √dk

Between scoring and softmax, one line appeared: scores are divided by the square root of the key dimension. This is the “scaled” in scaled dot-product attention, the official name of what we just built. It looks cosmetic. It is not — and you can see why with two short observations.

Why dot products grow with dimension

A dot product of d-dimensional vectors is a sum of d products. If each product is a smallish random number, the sum of d of them grows as d grows — statistically, its typical size grows like √d (variances add across the d terms, and the standard deviation is the square root of the variance). So:

d_k = 2 → scores of size ~1 (our toy example)
d_k = 768 → scores of size ~28 (GPT-2 small)
d_k = 12288 → scores of size ~110 (GPT-3)

Dividing by √dk cancels the growth exactly: scores are pulled back to typical size ~1, whatever the dimension.

Why large scores kill learning

Feed softmax two scores that differ by 1 and it answers ~[0.73, 0.27] — a preference. Feed it scores that differ by 20 and it answers [0.9999…, 0.0000…] — a verdict. With unscaled high-dimensional scores, softmax saturates into a step function: one weight ≈ 1, the rest ≈ 0. And a function that has flattened out has gradient ≈ 0 — backpropagation gets no slope to descend, so the attention weights stop changing and training stalls. Scaling keeps softmax in its soft, trainable regime.

Packaging it: SelfAttention_v1 and _v2

Everything so far was loose lines of code, good for understanding, useless for building. Now we fold the mechanism into a PyTorch class — the shape it will keep, with additions, for the rest of the track. Read it top to bottom; there is nothing in it you haven't already computed by hand.

The SelfAttention_v1 class — stop 2 on the route ▶ Run in Colab
import torch.nn as nn

class SelfAttention_v1(nn.Module):                        # nn.Module = PyTorch's building block
    def __init__(self, d_in, d_out):
        super().__init__()
        self.W_query = nn.Parameter(torch.rand(d_in, d_out))   # the three trainable
        self.W_key   = nn.Parameter(torch.rand(d_in, d_out))   # matrices, registered so
        self.W_value = nn.Parameter(torch.rand(d_in, d_out))   # training can update them

    def forward(self, x):                                 # x: (6, 3)
        keys    = x @ self.W_key                          # (6, 3)@(3, 2) → (6, 2)
        queries = x @ self.W_query                        # (6, 2)
        values  = x @ self.W_value                        # (6, 2)
        attn_scores  = queries @ keys.T                   # (6, 2)@(2, 6) → (6, 6)
        attn_weights = torch.softmax(
            attn_scores / keys.shape[-1]**0.5, dim=-1     # scale by √d_k, softmax rows
        )
        context_vec = attn_weights @ values               # (6, 6)@(6, 2) → (6, 2)
        return context_vec
torch.manual_seed(123)

One refinement remains. Initialising weights with plain torch.rand (uniform between 0 and 1) is naive — training converges better from a smarter starting distribution. PyTorch's nn.Linear layer does exactly the same multiplication but with an optimised initialisation scheme (and an optional bias, which GPTs typically switch off). Swapping it in gives version 2 — the form all later units use:

SelfAttention_v2 — the nn.Linear version, stop 3 on the route ▶ Run in Colab
class SelfAttention_v2(nn.Module):
    def __init__(self, d_in, d_out, qkv_bias=False):
        super().__init__()
        self.W_query = nn.Linear(d_in, d_out, bias=qkv_bias)   # same multiply,
        self.W_key   = nn.Linear(d_in, d_out, bias=qkv_bias)   # better initial values
        self.W_value = nn.Linear(d_in, d_out, bias=qkv_bias)

    def forward(self, x):
        keys    = self.W_key(x)                           # layer call instead of @
        queries = self.W_query(x)
        values  = self.W_value(x)
        attn_scores  = queries @ keys.T
        attn_weights = torch.softmax(
            attn_scores / keys.shape[-1]**0.5, dim=-1
        )
        context_vec = attn_weights @ values
        return context_vec

Common confusion

“v1 and v2 print completely different numbers — is one of them wrong?” Neither. They implement the identical mechanism; they merely start from different random weights (different seed, different initialisation scheme). Untrained attention outputs are meaningless either way — what matters is the machinery that training will shape. Try it yourself: copy v2's weight matrices into v1 (minding that nn.Linear stores its matrix transposed) and the two produce identical outputs.

Common confusion

“Weights” means two different things on this page. The weight parameters in Wq, Wk, Wv are learned during training and then frozen — the same for every sentence. The attention weights α are computed fresh for every input, from the input — they're the mechanism's output, not its knobs. When you read “weights” anywhere in the LLM literature, silently ask which of the two is meant.

Part 1 in one line

score = q·k  →  scale by √dk  →  softmax  →  blend the values. That is scaled dot-product attention, the engine inside every GPT. What it still lacks: it can see the future (a problem for generation), and it has only one way of looking (a problem for expressiveness). Both are fixed in Part 2.
