7.1

Naming a recipe — def, the body, the call

Read · ~4 minPractice · ~9 min

The problem. You want to greet three visitors, and the greeting is two lines long. So far your only option is to write those two lines three times — six lines, and if the wording ever changes you must fix it in three places and hope you found them all. Copy-paste is how bugs breed.

The idea, in plain words. Give the block of code a name, once, and then use the name. Our literal-minded kitchen helper already works this way: you don't re-explain how to make tea every time — you wrote a recipe card once, filed it in the cookbook, and now "make tea" is a single instruction. In Python, writing the card looks like this:

def greet():
    print("Hello! Welcome.")
    print("Grab a chair.")

  • def means "define" — here comes a recipe card. Then the function's name (same rules as box labels), parentheses, and a colon.
  • The body is every indented line under it — the steps on the card. Same indentation rule as if and for: the indent marks what belongs inside.
  • Calling — greet(), with the parentheses — means do it now. Python jumps into the body, runs the steps, and comes back to the line after the call.

And the part everyone trips on: defining runs nothing. When Python reads a def block, it files the card in the cookbook and moves on — not one line of the body runs. The body runs only when the name is called, and it runs once per call: the same greeting three times means one function called three times.

Trace it by hand — the card is filed, not cooked
def cheer(): print("Hip hip hooray!") print("before") cheer() print("after")

Lines 1–2: a recipe card named cheer goes into the cookbook. Nothing prints — Python only read the card.

Line 4: before appears. Line 5: the call — Python jumps into the body, prints Hip hip hooray!, and comes back. Line 6: after appears.

before Hip hip hooray! after

Cover line 5 with a finger and the program prints only before and after — a filed recipe nobody asks for is never cooked.

Common confusion

def is writing the recipe card; calling is cooking. Beginners write a beautiful def block, run the program, see nothing, and conclude Python is broken. It isn't — nobody ordered the dish. If a function's output is missing, the first thing to check is whether you actually called it: greet(), parentheses and all. (Writing just greet without parentheses names the card without cooking it — no error, no output.)

Worked example

Task: greet three visitors with a two-line greeting — without writing the greeting three times. Thinking: one recipe card, three calls. Before running, predict how many lines print and in what order; then change the wording once and watch all three greetings update.

7.2

Ingredients — parameters & arguments

Read · ~4 minPractice · ~9 min

The problem. greet() says the same thing to everyone. A real greeting needs the visitor's name — and a recipe that can't take ingredients can only ever cook one dish.

The idea, in plain words. Recipe cards have blanks: "make tea for ___ people". A function gets blanks the same way — names inside the parentheses of the def line:

def greet(name):
    print(f"Hello, {name}!")

Two words you'll meet everywhere, worth getting straight on day one:

  • A parameter is the slot on the card — name in the def line. It's a labeled box that exists inside the function.
  • An argument is what you pass in when calling — greet("Ada") puts "Ada" into the name box for the duration of that call.

Multiple slots work exactly as you'd hope — def order(item, count): — and arguments fill them left to right, fresh on every call. One more comfort: a slot can carry a default value. Write def greet(name, punctuation="!"): and callers who don't supply punctuation get "!" for free, while callers who do supply one override it. Defaults are how one recipe serves both the common case and the fussy one.

Trace it by hand — slots filled per call
def order(item, count): print(f"{count} x {item}") order("dosa", 2) order("tea", 1)

First call: "dosa" → slot item, 2 → slot count (left to right). The body prints 2 x dosa.

Second call: the slots are refilled from scratch — "tea", 1 — and the body runs again:

2 x dosa 1 x tea
Common confusion

Parameter vs argument, once and for all: the parameter is the slot (name in the def line), the argument is what you drop into it ("Ada" at the call). And because arguments fill slots by position, swapping them swaps meanings — order(2, "dosa") would happily try to serve "dosa copies of 2". Python doesn't read minds; it reads order.

Worked example

Task: one greeter for three moods — normal, questioning, trailing off. Thinking: two slots, one with a default. The first call leans on the default; the others override it. Predict all three lines before running.

7.3

return vs print — the handover

Read · ~4 minPractice · ~11 min

The problem. Your functions can show things. But suppose a function computes a room's area and you want to add two areas together. Showing the number on screen doesn't help — the screen is for you, not for the program. The program needs the value handed back, so it can store it in a box and keep working with it.

The idea, in plain words. That handover is return. Think of the kitchen helper again: print is the helper shouting the answer across the kitchen — you hear it, and it's gone. return is the helper bringing the dish to your counter — now it's yours to store, taste, or cook with further:

def area(width, height):
    return width * height

room = area(4, 3)   # the call *becomes* 12, stored in a box

Read the call like arithmetic: area(4, 3) becomes its returned value, right there in the line. That's why it can sit on the right of an =, inside an f-string, or in the middle of a sum. Two more facts complete the picture:

  • return ends the call immediately. It's the function's exit door; lines after it never run.
  • A function with no return hands back None — Python's word for "nothing here". A function that only prints is such a function: the text appears, and the caller receives None.
Trace it by hand — shout vs handover
def shout(word): print(word + "!") def louder(word): return word + "!" result1 = shout("hey") result2 = louder("hey") print(result1) print(result2)

Line 7: shout("hey") runs the body — hey! appears now. The function has no return, so the call becomes None, and that's what lands in result1.

Line 8: louder("hey") prints nothing — it quietly hands back "hey!", which lands in result2.

Lines 9–10: the boxes are read out:

hey! None hey!

Same word, same exclamation mark — but only one version left the caller holding something usable.

Fig. 1 — The full journey of room = area(4, 3): arguments flow into the parameter slots, the body computes, and the returned value flows back to the call site, where it's stored like any other value.
Key idea
print shows a value to a human and forgets it; return hands the value back to the program. If any later line needs the result, the function must return it.
Common confusion

"But I saw the answer on screen — why is my box None?" Because seeing isn't keeping. A function that prints its result still returns None, and None is what gets stored. The tell-tale symptom is None appearing somewhere in your output, or a TypeError mentioning NoneType when you try to compute with it. The fix is always the same: return the value, and let the caller decide whether to print it.

Worked example

Task: a flat has a hall of 9×5 metres and a kitchen of 3×4 — print each area and the total floor space. Thinking: one area function, called twice; because it returns, the results land in boxes we can add. Try replacing the return with a print and watch the arithmetic collapse.

7.4

Scope, gently — boxes on a workbench

Read · ~3 minPractice · ~7 min

The problem. Functions create boxes — parameters, and any box the body makes. If every one of those joined the program's boxes permanently, ten calls would leave forty stray boxes and no way to tell whose was whose. Something must keep a function's mess contained.

The idea, in plain words. Each call gets its own workbench. Boxes created inside a function — parameters included — live on that bench, and when the call ends, the bench is cleared. Ask for one of those boxes afterwards and you get a NameError: it's simply gone. Two rules cover everything you need for now:

  • Reading an outer box works. The bench can see the main room: if the program has greeting = "hello", a function body may print(greeting) freely.
  • A same-named local shadows the outer box. If the body creates its own snack, that bench box hides the room's snack for the rest of the call — and the room's box is untouched throughout.

You may wonder how a function can ever change the outer world, then. It doesn't need to reach out and rearrange the room — it gives results back with return, and the caller stores them wherever it likes. That handover is the clean channel; keep to it and scope will never surprise you.

Trace it by hand — the bench and the room
snack = "biscuit" def picnic(): snack = "mango" print("Inside:", snack) picnic() print("Outside:", snack)

Line 1: the room's box snack holds "biscuit". Lines 3–5: the card is filed; nothing runs.

Line 7: the call opens a workbench. Line 4 makes a bench box snack holding "mango" — the room's box is now shadowed, not changed. Line 5 prints the bench box. Call ends; bench cleared; the mango box is gone.

Line 8: back in the room, snack is the biscuit it always was:

Inside: mango Outside: biscuit
Fig. 2 — Why the trace prints mango then biscuit: two boxes with one name, on two different surfaces. The dashed bench exists only for the duration of the call.
Aside — those little labels you'll see everywhere
In real code you'll soon meet def lines like def area(w: int, h: int) -> int:. The : int and -> int are type hints — labels for humans and tools saying what types are expected in and out. Python doesn't enforce them (pass a string and Python will still try); editors and checkers use them to catch mistakes early. Just read past them for now — you'll meet them everywhere in real code, and we'll start writing them ourselves in the Intermediate units.
Worked example

Task: compute a discounted bill. Thinking: the function makes two bench boxes, discount and final, does its work, and returns one value. After the call, try adding print(discount) at the bottom — you'll get a NameError, and now you know exactly why: the bench is cleared; only the returned value survives, safely stored in bill.

7.5

Your build — the refactor

Read · ~3 minPractice · ~12 min

Remember Unit 5's to-do list? It worked — and it was a tangle: one while loop doing four different jobs, with the adding code, the numbered-listing code and the removing code all elbowing each other inside one long chain of elifs. Adding a feature meant scrolling through everything; testing "remove" meant running the whole program. That tangle is what functions were invented for.

Today we refactor it — change the code's shape without changing what it does. Each job becomes a named recipe — add_task, show_tasks, remove_task — and the loop shrinks to a readable dispatcher: read a command, call the matching function. Same session, same output, byte for byte; that's the definition of a successful refactor. Then a second build from scratch: a menu-driven calculator where each operation is a small returning function.

7.5 · P1The to-do list, packaged

Below is the Unit 5 build, exactly as it stood. Refactor it into three functions — add_task(tasks, name), show_tasks(tasks), remove_task(tasks, name) — with the loop reduced to reading commands and calling them. The scripted session (add two tasks, show, remove one, show, quit) is locked; your refactor passes when the output is identical to the original's. Run the starter first to see the target behaviour.

Command? add Task? buy milk Added: buy milk Command? add Task? call grandma Added: call grandma Command? show 1. buy milk 2. call grandma Command? remove Task? buy milk Removed: buy milk Command? show 1. call grandma Command? quit Bye!
Show solution
def add_task(tasks, name):
    tasks.append(name)
    print(f"Added: {name}")

def show_tasks(tasks):
    if len(tasks) == 0:
        print("Nothing to do!")
    else:
        n = 1
        for task in tasks:
            print(f"{n}. {task}")
            n = n + 1

def remove_task(tasks, name):
    if name in tasks:
        tasks.remove(name)
        print(f"Removed: {name}")
    else:
        print(f"Not found: {name}")

tasks = []
running = True
while running:
    command = input("Command? ")
    if command == "add":
        add_task(tasks, input("Task? "))
    elif command == "show":
        show_tasks(tasks)
    elif command == "remove":
        remove_task(tasks, input("Task? "))
    elif command == "quit":
        running = False
        print("Bye!")

The loop now reads like the menu it is, and each job can be read — or fixed — on its own. One subtlety worth savouring: the functions receive the same list, not a copy (a list argument is another label on the same box, as Unit 5 showed), so append and remove inside the function change the list the loop sees.

7.6

Problem bank — everything at once

Practice · ~12 min

The mixed set: defining, returning, defaults, and functions calling functions — with loops and conditions from earlier units woven in. In order; they get meaner.

B1The even test

Write is_even(n) that returns True or False using % (Unit 2's remainder, Unit 3's comparisons — a comparison already is a True/False value, so return it directly). The checking loop is written for you; don't change it.

7 is odd 10 is even
Show solution
def is_even(n):
    return n % 2 == 0

for number in [7, 10]:
    if is_even(number):
        print(f"{number} is even")
    else:
        print(f"{number} is odd")

No if needed inside the function — n % 2 == 0 already evaluates to True or False, so return it as-is. Functions returning True/False read beautifully at the call site: if is_even(number).

B2Tax, with a default

Write price_with_tax(price, rate=5) that returns the price plus rate percent tax. Print the result for 200 at the default rate, then for 200 at 18 percent — both through :.2f.

210.00 236.00
Show solution
def price_with_tax(price, rate=5):
    return price + price * rate / 100

print(f"{price_with_tax(200):.2f}")
print(f"{price_with_tax(200, 18):.2f}")

The first call leans on the default; the second overrides it. The division makes the result a float either way, and :.2f dresses it as money — format at the exit.

B3Functions calling functions

Keep price_with_tax from B2, and add net_price(price, discount): subtract the discount, then hand the reduced price to price_with_tax (default rate) and return what it returns. Ask for the price and the discount with the prompts shown, convert with float(), and print the result. Inputs fixed: 500, then 100.

Price? 500 Discount? 100 Net: 420.00
Show solution
def price_with_tax(price, rate=5):
    return price + price * rate / 100

def net_price(price, discount):
    reduced = price - discount
    return price_with_tax(reduced)

price = float(input("Price? "))
discount = float(input("Discount? "))
print(f"Net: {net_price(price, discount):.2f}")

500 − 100 → 400, plus 5% tax → 420.0. One recipe using another is the normal state of real code: small functions, each doing one job, composed like sentences.

B4Stretch — greatest of three

Write max2(a, b) that returns the larger of two values, then max3(a, b, c) that finds the largest of three by calling max2 twice — first on a and b, then on that winner and c. Print max3(7, 21, 9) and max3(4, 2, 3). (Yes, Python has a built-in max — today we're building the muscle, not reaching for the shelf.)

21 4
Show solution
def max2(a, b):
    if a > b:
        return a
    return b

def max3(a, b, c):
    return max2(max2(a, b), c)

print(max3(7, 21, 9))
print(max3(4, 2, 3))

Two things to relish: max2 needs no else — if the first return fires, the call is already over; and max3 is one line because a call becomes its returned value, so calls nest like brackets. A tournament of two matches finds the champion of three.
