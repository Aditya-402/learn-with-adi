Functions as Values

Since Unit 7 a function has been something you do. This session says the quieter, stranger thing: a function is something you have — a value that fits in a box, rides inside a list, sits in a dict, gets handed to another function. 19.1

The function IS a value

Read · ~4 minPractice · ~10 min

The problem. You want a helper that applies any operation twice — double it twice, shout it twice, round it twice. You can write apply_twice_to_double, then apply_twice_to_shout, then… no. What you actually want is to hand the operation itself to the helper, the way you hand it a number. Can you put a function in a box?

The idea, in plain words. You can, and you already have — you just didn't notice. When Python reads def greet(): ... it builds a recipe card and then does something very familiar: it puts that card in a labeled box called greet. The def line is an assignment in disguise. Which means everything you know about boxes applies:

  • greet is the card. greet() is the cooking. The name alone hands over the recipe; the parentheses are the instruction "make this now".
  • A second label can point at the same card. shout = greet doesn't copy the recipe or run it — it ties a second label to the one function that already exists. shout() cooks the very same dish.
  • Cards travel. A function can go into a list, into a dict as a value, into another function as an argument, and can come back out of a function as a return value. Sections 19.2–19.5 are four consequences of that one sentence.

A function you hand to another function has a name: it's an argument like any other. And a function that takes a function (or hands one back) is called a higher-order function — a grand phrase for a plain idea, so let's earn it by tracing one.

Trace it by hand — one card, two labels
def greet(): print("Hello!") shout = greet greet() shout()

Lines 1–2: a recipe card is built and stored in the box greet. Nothing is printed — nobody has cooked anything.

Line 4: right side first, as always: greet reads the box and finds the card. No parentheses, so no cooking. That card is stored into a second box, shout. Two boxes, one card — this is the first time in these notes two labels point at the same thing, and the figure below is worth thirty seconds.

Lines 5–6: both calls cook the same recipe:

Hello! Hello!
Fig. 1 — Two labels, one card. Every box picture so far had one label per box; this is the first time two names sit on the same thing, and it is exactly why shout = greet costs nothing and changes nothing.
Common confusion

greet versus greet() — the card versus the cooked dish. x = greet puts the recipe in a box; x = greet() runs the recipe and puts what it returned in the box (often None). And never print(greet): Python answers with something like <function greet at 0x7f2b1c> — a machine address, useful to nobody. If you see that in your output, you forgot a pair of parentheses somewhere.

Worked example

Task: one helper, apply_twice(func, value), that works for numbers and for text. Thinking: the first parameter is an ordinary parameter that happens to receive a card. Inside, func(value) cooks it once; wrapping that in func(...) again cooks it twice. Note the call sites: add_five with no parentheses — we're handing over the card, not the dish.

19.1 · P1A second name for one recipe

Write cheer(name) that prints Go <name>!. Then tie a second label, applaud, to the same function and call the two names once each — cheer with Ada, applaud with Ravi.

Go Ada! Go Ravi!
Show solution
def cheer(name):
    print(f"Go {name}!")

applaud = cheer
cheer("Ada")
applaud("Ravi")

No parentheses on line 4 — that's the whole trick. One card, two labels, identical behaviour.

19.1 · P3Your own higher-order helper

Write apply_twice(func, value) yourself — it returns func applied to value twice. Then feed it two different cards: add_exclaim (glues a ! on the end) with "Wow", and halve (integer-divides by 2) with 100.

Wow!! 25
Show solution
def apply_twice(func, value):
    return func(func(value))

def add_exclaim(text):
    return text + "!"

def halve(n):
    return n // 2

print(apply_twice(add_exclaim, "Wow"))
print(apply_twice(halve, 100))

Read the inner-to-outer order: func(value) first, then that result back through func. One helper, any operation — that's the payoff for treating the card as a value.

19.2

lambda — and the key= trick that makes it worth learning

Read · ~4 minPractice · ~11 min

The problem. You have a list of student dicts and you want them ordered by marks, highest first. sorted() doesn't know what "marks" means — it sorts whole values, and a dict isn't something it can rank. You need to tell it: for each student, this is the thing to compare. That instruction is a function. Writing a three-line def for it feels absurd.

The idea, in plain words. A lambda is a nameless one-line function you write on the spot, at the moment you need to hand one over. lambda x: x * 2 means exactly what def f(x): return x * 2 means — parameters before the colon, one expression after it, and that expression is automatically returned. No def, no name, no return keyword.

It earns its keep in one place above all others: the key= parameter of sorted(), max() and min(). You hand over a card; Python cooks it once per item and sorts by whatever comes back:

sorted(words, key=len) sorted(students, key=lambda s: s["marks"], reverse=True)

The first line hands over a card you didn't even write — len is a function, so key=len means "rank each word by its length". The second writes the card inline: given a student, the thing to compare is their marks, and reverse=True flips the order to biggest-first. That second line is the single most common lambda you will ever see in real code.

The honest rule
If a lambda wants to be two lines, it wants to be a def with a name. Lambdas are for expressions so small that naming them would be noise. Anything with a condition worth explaining, a loop, or a comment deserves a real name — a name is free documentation.
Trace it by hand — what key= actually does
words = ["pear", "fig", "banana"] print(sorted(words, key=len))

Step 1: sorted takes each item and cooks the card once: len("pear") → 4, len("fig") → 3, len("banana") → 6. Three tags: 4, 3, 6.

Step 2: it sorts the items by their tags — 3, 4, 6 — and hands back a brand-new list. The tags are then thrown away; you never see them.

['fig', 'pear', 'banana']

Two things worth pinning down. sorted() returns a new list and leaves words untouched. And key= never changes the items — it only decides their order.

Common confusion

key=len, never key=len(). You are handing sorted the recipe card so it can cook it once per item; len() would try to cook it immediately, with no ingredients, and die with a TypeError. Same for your own: key=lambda s: s["marks"] is a card. The rule from 19.1 has not changed — parentheses mean "now".

Worked example

Task: a list of student dicts (Unit 6's shape), ranked by marks, highest first — plus the topper by name. Thinking: one lambda, reused. max takes the very same key= and returns the whole winning dict, not just the number, so we pull the name back out of it. And we print through a loop with an f-string — a raw list of dicts on screen is unreadable and always was.

19.2 · P1Shortest first

Print these words one per line, shortest first, using sorted with key=len. Watch what happens to the two six-letter words: Python's sort is stable, so ties keep their original order.

fig kiwi banana cherry
Show solution
words = ["banana", "fig", "cherry", "kiwi"]
for w in sorted(words, key=len):
    print(w)

No lambda needed — len was already a function sitting in a box, waiting to be handed over. banana comes before cherry because it came first in the original list.

19.2 · P2Books by length

A list of dicts (Unit 6, back again). Print every title with its page count, thinnest book first, in the exact shape below.

Siddhartha: 152 Dune: 412 Emma: 474
Show solution
books = [
    {"title": "Dune", "pages": 412},
    {"title": "Emma", "pages": 474},
    {"title": "Siddhartha", "pages": 152},
]
for b in sorted(books, key=lambda b: b["pages"]):
    print(f"{b['title']}: {b['pages']}")

The lambda's parameter is one book; what it returns is the number to rank by. Ascending is the default — no reverse= needed.

19.2 · P3max and min take key= too

From the same list, print the highest scorer's name and the shortest name in the group. max and min hand back the whole winning item — so read the field you want off it afterwards.

Top scorer: Ravi Shortest name: Ada
Show solution
students = [
    {"name": "Ada", "marks": 78},
    {"name": "Ravi", "marks": 91},
    {"name": "Mira", "marks": 84},
    {"name": "Bhavana", "marks": 66},
]
top = max(students, key=lambda s: s["marks"])
short = min(students, key=lambda s: len(s["name"]))
print(f"Top scorer: {top['name']}")
print(f"Shortest name: {short['name']}")

Two different cards, same mechanism: rank by marks, rank by name length. Without key=, max on dicts simply refuses — it has no idea what "biggest dict" would mean.

19.2 · P4Stretch — fix the broken sort

This is the mistake everyone makes once: the author passed the data where a card belongs. Run it, read the last line of the report, then fix the key= so it ranks by marks, highest first.

Ravi 91 Mira 84 Ada 78
Show solution
for s in sorted(students, key=lambda s: s["marks"], reverse=True):
    print(s["name"], s["marks"])

key= wants a card that Python will cook once per item — not a value you looked up yourself. The lambda says "when you get to a student, then read their marks".

19.3

Closures — a function that packs a lunchbox

Read · ~4 minPractice · ~10 min

The problem. You need a doubler, a tripler and a ten-timer. Three nearly identical functions, differing by one number. You could write one multiply(n, x) — but sorted's key= wants a card that takes one argument. What you really want is a machine that stamps out ready-made one-argument functions on demand.

The idea, in plain words. Since 19.1, a function can be returned like any other value — so write a factory: a function whose job is to build and hand back another function.

def make_multiplier(n): return lambda x: x * n double = make_multiplier(2)

Now the strange and wonderful part. When make_multiplier(2) finishes, its n box should vanish — that's what happens to every parameter when a function returns (Unit 7). But the little function it produced still mentions n. So Python does the sensible thing: it lets the inner function take the box with it. The returned function walks out of the factory carrying a packed lunchbox containing n = 2, and it eats from that lunchbox for the rest of its life. A function plus the boxes it carried out is called a closure.

Every call to the factory packs a fresh lunchbox. make_multiplier(3) hands you a different function carrying n = 3, and the two never interfere.

Trace it by hand — the lunchbox leaves the kitchen
def make_multiplier(n): return lambda x: x * n double = make_multiplier(2) triple = make_multiplier(3) print(double(5)) print(triple(5))

Line 4: the factory runs with n holding 2. It builds a small nameless card that says x * n and returns it. The factory ends — but n = 2 is packed into that card's lunchbox. The box double now holds that card.

Line 5: the factory runs again, from scratch, with a brand-new n holding 3. A second card, a second lunchbox. triple holds it.

Lines 6–7: double(5) cooks its card with x = 5 and reads n from its own lunchbox → 10. triple(5) reads a different lunchbox → 15.

10 15
Fig. 2 — The factory's frame is long gone, yet each returned function still has its own n. Adopt this picture: a closure is a function carrying a packed lunchbox. It explains every "how does it still remember that?" you will meet from here on.
Key idea
A factory is a function that returns a function. The returned function keeps the boxes it needed from the factory's call — one fresh lunchbox per call — so one factory can stamp out an unlimited family of ready-made, one-argument functions.
Worked example

Task: build two multipliers from one factory and prove they're independent. Thinking: two calls to the factory, two lunchboxes. The last line nests them — triple(2) cooks first and gives 6, then double takes that to 12 — which only works because each carries its own n.

19.3 · P1times3 and times10

Using the factory below, build times3 and times10, then print times3(7), times10(7), and times3(times10(1)). Predict the third one before you run it.

21 70 30
Show solution
def make_multiplier(n):
    return lambda x: x * n

times3 = make_multiplier(3)
times10 = make_multiplier(10)
print(times3(7))
print(times10(7))
print(times3(times10(1)))

One factory, two lunchboxes, zero interference. The last line: times10(1) → 10, then times3(10) → 30.

19.3 · P2A greeter factory

Write make_greeter(greeting) that returns a function taking a name and returning <greeting>, <name>!. Build two greeters — hello and namaste — and print one greeting from each. (Here the inner function deserves a proper def: it's a real sentence-builder, not a scrap.)

Hello, Ada! Namaste, Ravi!
Show solution
def make_greeter(greeting):
    def greet(name):
        return f"{greeting}, {name}!"
    return greet

hello = make_greeter("Hello")
namaste = make_greeter("Namaste")
print(hello("Ada"))
print(namaste("Ravi"))

Note return greet with no parentheses — hand back the card, don't cook it. The inner function's lunchbox holds greeting, and each factory call packs a different one.

19.3 · P3Stretch — predict: whose box is it?

A tagger is built with "WARN". Then a completely separate box named tag is created outside. Does the tagger notice? Predict the output, then run — and be ready to explain your answer to yourself.

Show what happens & why

The lambda eats from its own lunchbox — the tag box that belonged to that factory call. The tag created on line 5 is a different box that happens to share a label, exactly like a parameter shadowing an outer name in Unit 7. Closures carry their boxes, not their names.

19.4

*args and **kwargs — functions that accept anything

Read · ~3 minPractice · ~10 min

The problem. print takes one argument, or five, or none. Your functions can't do that — def total(a, b) insists on exactly two. And there's a sharper version coming: to write a function that wraps another one, you must be able to accept whatever arguments the wrapped function wanted, without knowing what they are.

The idea, in plain words. A star in the parameter list means "and everything else". Two spellings, two containers:

  • *args — collects every extra positional argument into a tuple (Unit 6's read-only list). summary(3, 5, 9) arrives inside as args = (3, 5, 9).
  • **kwargs — collects every extra named argument into a dict. profile(name="Ada", city="Chennai") arrives as kwargs = {"name": "Ada", "city": "Chennai"}.

The names are pure convention — *things works identically — but args and kwargs are what every Python programmer expects to read, so use them.

Now the honest purpose, because collecting numbers is a toy. The reason this pair exists is writing wrappers that pass everything through. A star on the calling side does the opposite job: it unpacks. So a function can take anything and forward it, untouched, to somebody else:

def log_call(func, *args, **kwargs): print("about to call", func.__name__) return func(*args, **kwargs)

Read it slowly: log_call accepts a card plus whatever else, announces something, then cooks that card with exactly the ingredients it was handed. Remember this shape. The next unit is built on it, line for line.

While we're here — map and filter
You will meet map(func, items) and filter(func, items) in other people's code: they cook a card over every item, or keep the items where the card returns True. Both take a card, so both attract lambdas. Wrap them in list(...) to see the results. Honestly, though — [n * 2 for n in nums] reads better than list(map(lambda n: n * 2, nums)), and Unit 12 already gave you the comprehension. Recognise map and filter; reach for a comprehension.
Trace it by hand — what the star collects
def summary(*args): print(args) print(sum(args)) summary(3, 5, 9)

The call: three positional arguments arrive with no named parameters waiting for them. The star sweeps them all into one tuple and puts it in the box args.

Line 2: printing the box shows the tuple itself — round brackets, commas. Line 3: sum works on a tuple exactly as on a list.

(3, 5, 9) 17

Call it as summary() and args is the empty tuple () — no error. That's the point: any number, including none.

Common confusion

The same star means opposite things on the two sides. In a def line, *args packs loose arguments into a tuple. In a call, func(*args) unpacks that tuple back into loose arguments. Forget the star in the forwarding call and the whole tuple arrives as a single argument — one suitcase where three items were expected.

Worked example

Task: one function that accepts any number of scores, one that accepts any set of named fields, and the wrapper shape that is the real reason both exist. Thinking: len(args) and sum(args) treat the tuple like a list; kwargs.items() treats the dict like a dict (Unit 6). Then watch shout get called through log_call without log_call knowing anything about it.

19.4 · P1An average of anything

Write average(*args) that returns the mean of however many numbers it's given — and returns 0 for no numbers at all, rather than crashing on a division by zero.

20.0 5.0 0
Show solution
def average(*args):
    if not args:
        return 0
    return sum(args) / len(args)

print(average(10, 20, 30))
print(average(5))
print(average())

An empty tuple is falsy, so if not args is the idiomatic guard. And / always gives a float (Unit 2) — hence 20.0, not 20.

19.4 · P2A profile of whatever you're given

Write profile(**kwargs) that prints one key -> value line per named argument, in the order given, then a count line. Dicts keep insertion order, so the order is yours to rely on.

name -> Mira city -> Pune 2 fields
Show solution
def profile(**kwargs):
    for key, value in kwargs.items():
        print(f"{key} -> {value}")
    print(f"{len(kwargs)} fields")

profile(name="Mira", city="Pune")

Inside the function kwargs is an ordinary dict — .items(), .get(), len(), everything from Unit 6 works on it.

19.4 · P3Stretch — map out, comprehension in

Here is the same job written the map/filter way. Rewrite both lines as comprehensions (Unit 12) so the output is byte-for-byte identical — then decide for yourself which version you'd rather meet at midnight.

[2, 4, 6, 8] [2, 4]
Show solution
nums = [1, 2, 3, 4]
doubled = [n * 2 for n in nums]
evens = [n for n in nums if n % 2 == 0]
print(doubled)
print(evens)

map becomes the expression at the front; filter becomes the if at the back. Shorter, no lambda, no list(...) wrapper — and it says what it does in English word order.

19.5

Your build — a leaderboard and an event system

Read · ~3 minPractice · ~12 min

Two programs, both of which were impossible an hour ago. The first sorts by two criteria at once; the second keeps functions in a dict and calls whichever one an event asks for.

The tuple-key trick. A leaderboard needs highest score first, and ties broken alphabetically by name. One key= can do both: return a tuple, and Python compares the first item, then — only for ties — the second.

key=lambda p: (-p["score"], p["name"])

Read the minus sign as "flip this one". Scores go descending because negating turns biggest into smallest; names stay ascending. reverse=True couldn't do this — it would flip both.

Functions in a dict. The second build is the pattern behind every button, every menu, every plugin system you have ever used: a dict whose keys are event names and whose values are cards. Looking one up gives you a function; a pair of parentheses cooks it. And Unit 9's .get handles the event nobody wrote a handler for — politely, without a crash.

19.5 · P1The leaderboard

Sort the players by score descending, ties broken by name ascending, and print the ranking with enumerate(..., start=1) (Unit 17) in exactly the shape below. Mira and Ravi are tied on 90 — that's the whole point.

1. Bhavana (145) 2. Ada (120) 3. Mira (90) 4. Ravi (90)
Show solution
players = [
    {"name": "Mira", "score": 90},
    {"name": "Ada", "score": 120},
    {"name": "Ravi", "score": 90},
    {"name": "Bhavana", "score": 145},
]
ranked = sorted(players, key=lambda p: (-p["score"], p["name"]))
for rank, p in enumerate(ranked, start=1):
    print(f"{rank}. {p['name']} ({p['score']})")

One lambda returning a two-item tuple does the work of two sorts. And the printing is a loop with an f-string — never dump the list of dicts itself; nobody can read that.

19.5 · P2The event system

Build handlers: a dict mapping "start" and "stop" to two def'd functions, and "beep" to a lambda that prints Beep!. Then write fire(event) — look the name up with .get, call it if it's there, and print the polite refusal if it isn't. Fire the four events in the list, in order.

Engine started. Beep! No handler for 'fly' (ignored). Engine stopped.
Show solution
def on_start():
    print("Engine started.")

def on_stop():
    print("Engine stopped.")

handlers = {
    "start": on_start,
    "stop": on_stop,
    "beep": lambda: print("Beep!"),
}

def fire(event):
    handler = handlers.get(event)
    if handler is None:
        print(f"No handler for '{event}' (ignored).")
    else:
        handler()

for e in ["start", "beep", "fly", "stop"]:
    fire(e)

Three things at once: cards stored as dict values (no parentheses — parentheses there would run all three the moment the dict was built), .get returning None instead of exploding on "fly", and handler() cooking whichever card came back. Adding a new event now means adding one dict entry — no if/elif chain to grow.

19.6

Problem bank — everything at once

Practice · ~14 min

The mixed set: cards passed in, cards handed back, stars, tuple keys. In order; they get meaner.

B1Length, then alphabet

Print these words one per line, shortest first, and among words of equal length, alphabetically. One sorted, one tuple key — no second pass.

fig date kiwi plum apple banana
Show solution
words = ["kiwi", "fig", "banana", "date", "apple", "plum"]
for w in sorted(words, key=lambda w: (len(w), w)):
    print(w)

The tuple is compared left to right: length decides, and only when lengths tie does the word itself break it. Both ascending here, so no minus sign is needed.

B2apply_to_all — with a lambda and with a def

Write apply_to_all(func, items) that returns a new list with func applied to every item. Call it twice: once with a lambda that squares a number, once with a def'd shout that upper-cases text. Then read the note underneath.

[1, 4, 9] ['HI', 'THERE']
Show solution
def apply_to_all(func, items):
    return [func(item) for item in items]

def shout(text):
    return text.upper()

print(apply_to_all(lambda n: n * n, [1, 2, 3]))
print(apply_to_all(shout, ["hi", "there"]))

The honest comparison: the body is a comprehension, so when the operation is known at the spot, [n * n for n in nums] beats calling a helper. apply_to_all earns its keep only when the operation arrives from elsewhere — which is precisely when a function has to be a value. (Note the printed list of strings keeps its quotes: ['HI', 'THERE'].)

B3The discount factory

Write make_discount(rate), a factory returning a function that takes a price and returns the discounted price. Build ten_off and half_off from it, ask Price? , convert at the door, and print both results to two decimals. Input fixed to 250.

Price? 250 10% off: 225.00 50% off: 125.00
Show solution
def make_discount(rate):
    return lambda price: price - price * rate

ten_off = make_discount(0.1)
half_off = make_discount(0.5)

price = int(input("Price? "))
print(f"10% off: {ten_off(price):.2f}")
print(f"50% off: {half_off(price):.2f}")

Each returned function carries its own rate in its lunchbox. Real shops build these from a config file at startup — one factory, a dozen rules, none of them written by hand.

B4Stretch — two ways to sort descending

These records are (name, marks) tuples, so t[0] is the name and t[1] the marks. Produce the same highest-first ranking twice — once with key=lambda t: -t[1], once with key=lambda t: t[1], reverse=True — tagging the lines A and B. Then read the discussion; the difference matters.

A Ravi 91 A Mira 84 A Ada 78 B Ravi 91 B Mira 84 B Ada 78
Show solution & the discussion
records = [("Ada", 78), ("Ravi", 91), ("Mira", 84)]

for name, marks in sorted(records, key=lambda t: -t[1]):
    print(f"A {name} {marks}")

for name, marks in sorted(records, key=lambda t: t[1], reverse=True):
    print(f"B {name} {marks}")

Same output, different tools. reverse=True is clearer and works for any comparable value — you cannot negate a name. The minus trick only works on numbers, but it has one power reverse= lacks: inside a tuple key it flips one field while leaving the others ascending — which is exactly why 19.5's leaderboard needed (-score, name). Rule of thumb: reverse=True for a single criterion, the minus sign when you're mixing directions.
