22.1

The DataFrame — a table with names

Read · ~4 minPractice · ~10 min

The problem. Six students, each with a name, a class and a score. In Unit 21 you could hold the scores in an array and compute their mean in one stroke — but the names had to live in a separate list, the classes in another, and nothing stopped the three from drifting out of step. Sort the scores and the names no longer match them. Real data comes in rows that belong together, and an array has no idea which value belongs to which row.

The idea, in plain words. A DataFrame is a spreadsheet that lives in a variable. It has named columns across the top and numbered rows down the side, and — the part that matters — a DataFrame is a dict of NumPy arrays that all agree on their row labels. Say that once and mean it: each column is its own array, of its own type; the shared row labels (the index) are the glue that turns three arrays into one table. Sort by score and the names come along, because they were never separate in the first place.

You build one from a dict of lists, and Unit 6 pays out immediately: the keys become the column names, the lists become the columns.

import pandas as pd
df = pd.DataFrame({"name": ["Asha", "Ben"], "score": [72, 45]})

The pd nickname is universal — every pandas program on Earth starts with that line, the way every NumPy program starts with import numpy as np. And df is the near-universal name for "the table I'm working on". Four questions you ask a new table, every time:

  • df.head() — the first five rows. Look before you leap.
  • df.shape — (rows, columns). The same .shape as Unit 21, now with a name for each column.
  • df.columns — what the columns are called.
  • df.dtypes — what type each column holds: int64, float64, or object (which is pandas' word for "text lives here").
Trace it by hand — from dict to table
import pandas as pd data = {"name": ["Asha", "Ben"], "score": [72, 45]} df = pd.DataFrame(data) print(df.shape)

Line 1: pandas arrives under the nickname pd. Nothing else happens.

Line 2: an ordinary Unit 6 dict — two keys, each holding a list. No table yet, just a labeled box holding a dict.

Line 3: pd.DataFrame reads the dict and builds the table. Key "name" becomes a column of two strings; key "score" becomes a column of two whole numbers. Both columns are handed the same row labels, 0 and 1 — that shared labelling is what makes them one table instead of two lists.

Line 4: two rows, two columns, printed as a plain tuple:

(2, 2)

Read .shape the same way every time: rows first, columns second. It never changes its mind.

Fig. 1 — The picture to keep: a dict of arrays that all agree on their row labels. Everything else in this unit is a way of asking that picture a question.

22.2

Selecting — one column, several columns, some rows

Read · ~4 minPractice · ~10 min

The problem. You have the whole table. You almost never want the whole table. You want the score column, or the name and score columns, or only the rows where somebody passed. Three different wants, and they turn out to need three slightly different shapes of bracket.

The idea, in plain words. Square brackets on a DataFrame answer the question "which part?" — and what you put inside them decides which of the three questions you're asking.

  • One column, by name: df["score"]. You get back a single column with its row labels attached. pandas calls that a Series — one array plus one index. A DataFrame is a bundle of Series that share an index.
  • Several columns, by a list of names: df[["name", "score"]]. Note the double brackets: the outer pair means "select", the inner pair is an ordinary Unit 5 list of the names you want. You get back a smaller DataFrame.
  • Some rows, by a condition: df[df["score"] >= 50]. This is Unit 21's boolean mask, unchanged. df["score"] >= 50 produces a column of True/False, one per row, and handing that column back to df[...] keeps the True rows and drops the rest.

That last one is worth a second look, because it's the single most-used line in all of data work. The mask is computed from one column but applied to the whole row — names, classes and all — precisely because the columns agree on their row labels. Filter by score and the names come with.

Trace it by hand — a mask, then the rows it keeps
mask = df["score"] >= 70 rows = df[mask] print(len(rows))

Line 1: pandas walks down the score column — 72, 45, 88, 61, 54, 90 — and tests each against 70. Out comes a column of six True/False values: True, False, True, False, False, True. Row labels 0–5 ride along, untouched.

Line 2: df[mask] keeps rows 0, 2 and 5 whole — name, class and score together — and discards the other three. The kept rows keep their original labels (0, 2, 5), which is your first clue that this really is a slice of the original.

Line 3: len() of a DataFrame is its row count:

3
Common confusion

df["score"] and df[["score"]] are not the same thing and never were. One pair of brackets asks for the column and hands back a Series — a bare column of numbers you can average. Two pairs asks for a table containing that column and hands back a one-column DataFrame. The inner brackets are just a list; you can always read df[["name", "score"]] as "select the list ["name", "score"]". If a method complains that a DataFrame doesn't have .mean() the way you expected, count your brackets.

Common confusion

Combining two conditions uses & (and) and | (or) — not the words and and or from Unit 3. The words work on one True/False at a time; these symbols work on a whole column of them at once, exactly as in Unit 21. And each condition needs its own parentheses, because & binds tighter than >=: write df[(df["score"] >= 50) & (df["class"] == "A")], never without the inner brackets. Forget them and the error message will be memorably unhelpful.

Worked example

Task: the same table, three ways of taking a piece of it. Thinking: watch the shapes — a Series has no column header of its own, a sub-table does, and a filtered table keeps the original row labels.

Look at the row labels on that last block: 0, 2, 3, 4, 5. Row 1 (Ben) is gone, and pandas didn't renumber to hide it. Filtering takes rows out; it doesn't rebuild the table.

22.3

Loading real data — read_csv and the first look

Read · ~3 minPractice · ~10 min

The problem. Typing a dict of lists is fine for six students. Nobody types six thousand. Real data arrives as a file — nearly always a CSV: plain text, one row per line, values separated by commas, first line the column names. Unit 10 taught you to open such a file and pick it apart line by line. That was honest work, and pandas does it in one line.

The idea, in plain words. pd.read_csv("marks.csv") opens the file, treats the first line as the column names, splits every other line on commas, works out for itself which columns are numbers and which are text, and hands you a DataFrame. That single function is how the overwhelming majority of real data enters Python.

There's no file on this page's disk to read, so we'll do what Unit 10 did: write the file and read it back in the same program. The runner's disk starts completely empty every time you press Run, so the write has to happen first, every time. In Colab or on your own machine you'd skip straight to the read.

And once a table is loaded, form a habit before you do anything clever with it — the first look:

  • df.head() — do the rows look like rows?
  • df.info() — how many rows, what type is each column, and how many non-empty values does each have? That last number is where missing data confesses.
  • df.describe() — count, mean, min, max and the quartiles of every numeric column, in one block. Not statistics for their own sake; a smell test. A minimum age of −3 or a maximum score of 4000 tells you something is wrong with the data, before you waste an afternoon blaming your code.
Trace it by hand — write, then read
text = "name,score\nAsha,72\nBen,45\n" with open("marks.csv", "w") as f: f.write(text) df = pd.read_csv("marks.csv") print(df.shape)

Line 1: three lines of plain text in one string. The first, name,score, is the header.

Lines 2–3: Unit 10's write-then-close, exactly as you left it. A file called marks.csv now exists.

Line 4: pandas reads it. The header line becomes two column names; the two remaining lines become two rows. It notices that everything in the second column is a whole number and makes that column int64; the first column stays text.

Line 5: two data rows — the header is not a row:

(2, 2)
Key idea
Header line in, column names out. read_csv is the front door of practically every data project — and head, info, describe are the three things you do the moment you walk through it.
Worked example

Task: write a small CSV, read it back, and give it the full first look. Thinking: a triple-quoted string holds the file contents as they'd appear on disk — which makes it easy to see that the first line is the header and the rest are rows.

Three things to notice in that output. info() reports "6 non-null" for every column — nothing is missing, which we'll break on purpose in 22.4. describe() covers only score, because it's the only numeric column. And the mean it reports, 68.33, is the same number you computed by hand in 22.2 — the table hasn't changed, only how it arrived.

22.4

Missing values — the thing that makes real data real

Read · ~4 minPractice · ~10 min

The problem. Dev was ill on test day. His row exists — he has a name and a class — but the score field in the CSV is empty: Dev,B,. Not a zero. Not a bad mark. Simply no information. What does the table do with that, and what should you do with it?

The idea, in plain words. pandas puts a special marker there: NaN, short for "not a number". Read it as we don't know. It has two immediate consequences worth knowing before you're surprised by them:

  • The column becomes float. A column of whole numbers with a hole in it can't stay int64, because there's no whole number that means "unknown". pandas quietly promotes it to float64, and your scores print as 72.0 instead of 72. Nothing is broken; the type just widened to make room for the hole.
  • Most calculations step around it. df["score"].mean() averages the values that are there and ignores the gap. Convenient — and quietly dangerous, because the number you get is the average of five students, not six, and nothing on screen says so.

So the first thing you do with a new table is count the holes: df.isna() turns the whole table into True/False — True wherever a value is missing — and df.isna().sum() adds those up per column, giving you a tidy missing-value tally. (True counts as 1 when you add it up; that's Unit 3's booleans, still earning their keep.)

Then you choose, and it is a genuine choice with no automatic right answer:

  • df.dropna() — delete the rows with holes. Honest, simple, and it throws away everything else those rows knew. Fine when a handful of rows out of thousands are affected. Ruinous when a fifth of your data has one gappy column.
  • df.fillna(value) — put something in the hole. Zero, the column's mean, the word "unknown" — whatever you can defend. You keep the row, but you have invented a number, and every calculation downstream now partly rests on your invention.

The judgment is: which lie is smaller? Dropping Dev loses a real student from your class average. Filling him with 0 says he scored nothing, which drags the average down and is arguably worse. Filling him with the class mean says "assume he's typical", which flatters him and hides the gap. There is no move that costs nothing — which is exactly why this decision belongs to you and not to a default setting.

Trace it by hand — one hole, three answers
scores = [72, NaN, 88, 61] # as read from a gappy CSV print(len(scores), scores.count(), scores.mean())

The column: four rows, one of them unknown. Its dtype is float64 — the hole forced it.

len(): 4. There really are four rows; one of them just doesn't know its score.

.count(): 3. count() counts the values it actually has. The gap between len() and count() is your missing-data problem, measured.

.mean(): (72 + 88 + 61) ÷ 3 = 73.67 — not ÷ 4. If you wanted the "everyone counts, blanks are zero" number you'd have to ask for it deliberately: .sum() / len(df) gives 55.25 instead. Two defensible numbers, wildly apart, from the same column.

4 3 73.666666...
Fig. 2 — The same hole, two repairs, three different class averages (73.67, 73.67, 55.25). Choosing between them is not a coding decision; it's a decision about what you're willing to say is true.
Common confusion

NaN is not zero and it is not the empty string. Zero is a measurement — the student sat the test and scored nothing. "" is a piece of text that happens to be empty. NaN is the absence of a measurement: we don't know. Treat them as the same and you'll compute averages over students who never sat the paper. Two more oddities follow from this: NaN == NaN is False (two unknowns aren't equal — you don't know that), which is exactly why isna() exists instead of comparing to something; and any arithmetic touching a NaN produces a NaN, because unknown plus five is still unknown.

Worked example

Task: read a CSV with two blanks in it, count the damage, then compare what dropping and filling do to the class average. Thinking: notice that the score column arrives as float64 without being asked, and that three perfectly reasonable methods give three different answers.

The last two lines of that output are the whole lesson. Same file, same column, 51.83 or 77.75 depending on one decision you made about six characters of missing text.

22.5

Sorting, new columns & groupby

Read · ~4 minPractice · ~10 min

The problem. Three questions a real table gets asked constantly. Who did best? (Sort it.) Who passed? (That's a fact about each row that isn't written down yet.) And what's the average score per class? That third one is the interesting one — hold the thought.

The idea, in plain words. Three tools, one per question.

  • Sort: df.sort_values("score", ascending=False) — reorder the rows by one column, biggest first. Whole rows move; names stay glued to their scores, because the index is doing its job.
  • New column: df["passed"] = df["score"] >= 50 — compute a value for every row at once and store it under a new name. If the name doesn't exist yet, the column is created; if it does, it's overwritten. It's Unit 2's = with a whole column on each side.
  • Group: df.groupby("class")["score"].mean() — split the rows into piles by their class, take the score column of each pile, average it, and hand back one row per pile.

Read that last line right to left and it's a sentence: the mean of the score, for each class. It's worth dwelling on how much it replaces. In Unit 6 you'd have answered this with a dict of lists: walk every row, look up the class, append the score to the right list, then walk the dict and average each list. Twelve lines, an easy off-by-one, and a KeyError waiting the first time a new class appears. That whole paragraph of work is what groupby is. Split, apply, combine — split the rows into groups, apply a calculation to each, combine the answers into one small table.

What comes back from groupby("class")["score"].mean() is a Series whose index is the class names, so avg["A"] gets you class A's mean by name, and looping with .items() gives you the pairs — the same shape as looping over a dict, which is exactly the point.

Trace it by hand — split, apply, combine
avg = df.groupby("class")["score"].mean() for cls, m in avg.items(): print(f"Class {cls}: {m:.2f}")

Split. Six rows fall into two piles by their class value. Pile A: Asha 72, Chitra 88, Esha 54. Pile B: Ben 45, Dev 61, Farid 90.

Apply. ["score"] says "only look at the score column of each pile"; .mean() averages each. Pile A: 214 ÷ 3 = 71.333… Pile B: 196 ÷ 3 = 65.333…

Combine. Two answers become a two-row Series, labelled by class name and sorted by that label — A before B, always, so your output is reproducible.

The loop. .items() hands out (label, value) pairs, dict-style. Formatting at the exit with :.2f:

Class A: 71.33 Class B: 65.33
Key idea
groupby is split–apply–combine: split the rows into piles by a column's value, apply a calculation to each pile, combine the results into one small table. It is the single highest-leverage line in pandas.
Worked example

Task: all three tools on one table — rank the students, mark who passed, and report the per-class average. Thinking: each step leaves the table a little more useful than it found it, and none of them needs a loop over rows.

Look at the index down the left of the sorted table: 5, 2, 0, 3, 4, 1. The rows moved; their labels went with them. That's how you know nothing got scrambled — and it's why sort_values is safe in a way that sorting three parallel lists never was.

22.6

Your build — the class report

Read · ~2 minPractice · ~12 min

Everything from this session as one small pipeline, which is what a real data job actually looks like: load → inspect → clean → enrich → answer. A CSV of six students arrives with one score missing. You'll write it, read it, count the hole, fill it with a stated policy, add a pass column, find the top scorer, and print the average per class. Two stages, and the second one is only five lines because the first did the honest work.

One decision is yours and it's the one that matters: the missing student's score becomes 0, because in this school a missed test counts as a zero. That's a rule you can say out loud and defend to the head teacher. It's also visibly not neutral — watch what it does to class B's average.

Rows loaded: 6 Missing scores: 1 Passed: 4 of 6 Top: Farid (90) Class A: 71.33 Class B: 45.00
Show solution
print(f"Rows loaded: {len(df)}")
print(f"Missing scores: {df['score'].isna().sum()}")
df["score"] = df["score"].fillna(0)

df["passed"] = df["score"] >= 50
print(f"Passed: {df['passed'].sum()} of {len(df)}")

ranked = df.sort_values("score", ascending=False)
print(f"Top: {ranked['name'].iloc[0]} ({ranked['score'].iloc[0]:.0f})")

for cls, m in df.groupby("class")["score"].mean().items():
    print(f"Class {cls}: {m:.2f}")

Eleven lines of work, and class B's average reads 45.00 — dragged down by the zero you invented. That number is not wrong, but it is a consequence of your policy, and anyone reading the report deserves to be told. Load, inspect, clean, enrich, answer: this shape will hold for tables a million rows long.

22.6 · P3Stretch — make it yours

No check on this one. Change the pass mark, add a class C, blank out another score, and — the interesting experiment — swap fillna(0) for fillna(df["score"].mean()) and watch class B's average move. Same code, same file, a different story told about Dev. That's the whole of 22.4 in one edit.

Problem bank — everything at once

Practice · ~14 min

The mixed set. Building, selecting, filtering, cleaning, computing, grouping — in combinations, and with Units 12 and 21 wandering back in. In order; they get meaner.

B1Ask, then filter

Ask for a pass mark, then report how many students reached it and who they are. Input fixed to 60 here — but write it so any number works.

Pass mark? 60 4 of 6 scored 60 or more ['Asha', 'Chitra', 'Dev', 'Farid']
Show solution
cut = int(input("Pass mark? "))
above = df[df["score"] >= cut]
print(f"{len(above)} of {len(df)} scored {cut} or more")
print(list(above["name"]))

Convert at the door — input() still hands back text, pandas or no pandas. The mask is built from a variable rather than a literal, which is the only difference between a demo and a tool.

B2Fill it, then prove it

Ben's score is missing (that's what None becomes in a numeric column). Count the holes, fill them with the average of the scores that are known, count again to prove it worked, and print what Ben ended up with.

Missing before: 1 Missing after: 0 Ben's score is now 73.67
Show solution
print(f"Missing before: {df['score'].isna().sum()}")
df["score"] = df["score"].fillna(df["score"].mean())
print(f"Missing after: {df['score'].isna().sum()}")
print(f"Ben's score is now {df['score'].iloc[1]:.2f}")

mean() ignores the hole while computing, so Ben is filled with the average of the other three (221 ÷ 3). Neat — and note the circularity: filling with the mean guarantees the mean doesn't move, which makes the repair invisible in exactly the statistic people check.

B3Marks into percentages

Marks out of 60. Add a percent column computing each as a percentage of the total, then print one readable line per student with two decimals — zip from Unit 12 walks two columns side by side.

Asha: 71.67% Ben: 45.00% Chitra: 83.33%
Show solution
df["percent"] = df["marks"] / total * 100
for who, pct in zip(df["name"], df["percent"]):
    print(f"{who}: {pct:.2f}%")

One division for the whole column, no loop — then a loop only for the printing, which is the right place for one. Format at the exit: the column keeps 71.6666…, the line shows 71.67.

B4Stretch — the best in each class

Not "the highest score per class" — the student who got it, name and all. Two levels: group by class to find where each maximum lives, then go back to the table and fetch those whole rows. idxmax() gives you the row label of the maximum in each group, and df.loc[...] pulls rows out by label. Print one line per class.

Class A: Chitra with 88 Class B: Farid with 90
Show solution
best = df.loc[df.groupby("class")["score"].idxmax()]
for who, cls, sc in zip(best["name"], best["class"], best["score"]):
    print(f"Class {cls}: {who} with {sc}")

Read the first line inside out: groupby(...).idxmax() returns the row labels 2 and 5, and df.loc[[2, 5]] returns those two whole rows — names, classes, scores. This is the payoff of the index doing the gluing: a label found by looking at one column is enough to recover everything else about that row. (sort_values then groupby(...).head(1) is a perfectly good alternative route to the same answer.)
