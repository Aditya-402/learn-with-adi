25.1

Tensors are NumPy arrays with two superpowers

Read · ~4 minPractice · ~10 min

The problem. You open a deep-learning tutorial and the first line is x = torch.tensor([[1., 2.], [3., 4.]]). A new library, a new word — tensor — and a mild panic that this is a new kind of maths you skipped. Is it?

The idea, in plain words. No. A tensor is a grid of numbers with a shape, exactly like a NumPy array. Same vocabulary, same instincts: .shape tells you the dimensions, square brackets index and slice, arithmetic is element-wise, broadcasting stretches a smaller shape to meet a bigger one, @ is matrix multiply. If you know arrays, you already know 90% of tensors — and the remaining 10% is two additions, both practical rather than mathematical:

  • A tensor can live on a GPU. A NumPy array always sits in ordinary memory, worked on by the CPU. A tensor can be moved — x.to("cuda") — onto a graphics card, which does thousands of multiplications at once. Nothing about the numbers changes; only where the arithmetic happens.
  • A tensor can remember how it was computed. Ask for it with requires_grad=True and every operation you do leaves a breadcrumb. That's section 25.2, and it's the whole reason PyTorch exists.

That's the entire conceptual jump. The name "tensor" is borrowed from physics and sounds grander than the thing deserves: a 0-dimensional tensor is a single number, 1-D is a list of numbers, 2-D is a table, 3-D is a stack of tables. Nobody in the room means more than that.

Trace it by hand — the same four lines, twice
import numpy as np | import torch a = np.array([[1., 2.], | a = torch.tensor([[1., 2.], [3., 4.]]) | [3., 4.]]) print(a.shape) | print(a.shape) print(a * 2) | print(a * 2)

Line 2: both build the same 2-row, 2-column grid of decimals. One calls it an array, one calls it a tensor.

Line 3: both report the shape. NumPy says (2, 2); torch says torch.Size([2, 2]) — which is a tuple wearing a name tag, and indexes like one (a.shape[0] → 2 in both).

Line 4: both multiply every element by 2 — element-wise, no loop, exactly the Unit 21 habit:

[[2. 4.] | tensor([[2., 4.], [6. 8.]] | [6., 8.]])

Different printing, identical thinking. That difference in display is the biggest shock of the day, and it's cosmetic.

Fig. 1 — A tensor is not a new kind of number. It is an array that also knows which processor it lives on and what arithmetic produced it.
Common confusion

Tensors and arrays are close cousins but not interchangeable in a function call. Hand a NumPy array to a torch model and you get TypeError; hand a tensor to a scikit-learn function and it may or may not cope. Convert deliberately at the border — torch.from_numpy(a) going in, t.numpy() coming out. It's Unit 2's "convert at the door" rule, one library up.

25.1 · P4Stretch — the two multiplications

One star and one at-sign, two completely different operations. Multiply the grids both ways and print each result with .tolist() (which turns a grid into plain Python lists, so the printing is tidy). Predict both before you run.

25.2

requires_grad and .backward() — the breadcrumb trail

Read · ~4 minPractice · ~10 min

The problem. Suppose a program computes one number — how wrong a prediction was — from a few million other numbers, through a long chain of multiplications and additions. To improve, it needs to know: if I nudge this particular input up a little, does the answer go up or down, and by how much? Asking that by hand, a few million times, is not a plan.

The idea, in plain words. Mark a tensor with requires_grad=True and it starts leaving breadcrumbs. Every operation you then do with it — square it, add to it, multiply it — is recorded: "this result came from that value, by this operation." When you finally have one answer, calling .backward() on it walks that trail in reverse, undoing each step, and works out how much each original input affected the answer. It parks the answer in each input's .grad.

That number — how much the answer changes when I nudge this input — is called the gradient. It is the slope you met in school as a derivative, and PyTorch's one great trick is computing it for you, automatically, no matter how long the chain. The whole feature is called autograd.

Listing 1 · read-only — torch does not run in this page

This is the one unit these notes can't run in the page. PyTorch is too big for the browser, so the notebook is the lab today. Read the listing, read what it prints, then run it for real in Colab and change the 3.0 to something else.

import torch

x = torch.tensor(3.0, requires_grad=True)   # 1
y = x ** 2                                  # 2
y.backward()                                # 3
print(x.grad)                               # 4
tensor(6.)
  • Line 1 — a single number, 3.0, in a tensor, with the recorder switched on. requires_grad=True is the whole opt-in; without it, lines 3 and 4 fail.
  • Line 2 — square it. y now holds 9.0 and a note saying "I was made by squaring x".
  • Line 3 — walk the trail backwards from y. One step to undo: squaring.
  • Line 4 — the answer lands in x.grad. The slope of x² is 2x, and at x = 3 that is 6. Torch prints a bare float tensor as tensor(6.) — the trailing dot just means "this is a float".
▶ Run this in Colab
Fig. 2 — The forward pass computes the answer and records the route. .backward() retraces it, filling in each input's .grad. With a million inputs the picture is wider, not different.
Key idea
.grad answers one question and only one: if this input goes up by a whisker, which way does the final answer move, and how fast? Everything called "learning" is built on that single number.
Common confusion

.backward() does not change any numbers. After it runs, x still holds 3.0 — only x.grad is new. Changing the numbers is a separate step done by an optimizer (25.4). Torch keeps "work out the blame" and "act on the blame" as two different lines on purpose, and beginners routinely expect the first to do the second's job.

Worked example

Task: convince yourself the gradient is just a slope, using nothing but plain Python. Thinking: a slope is "rise over run" — nudge x a hair each way, see how much the answer moved, divide by how far you nudged. Do that for x² at several points and compare with the formula 2x that torch printed above.

25.2 · P1Be the autograd engine

Torch found x.grad = 6 at x = 3 because the slope of x² is 2x. Write the function grad_of_square(x) that returns that slope, and report it at four points. This is you doing by hand what .backward() does by machine.

x=1 -> grad=2 x=2 -> grad=4 x=3 -> grad=6 x=10 -> grad=20
Show solution
def grad_of_square(x):
    return 2 * x

for x in [1, 2, 3, 10]:
    print(f"x={x} -> grad={grad_of_square(x)}")

One line of maths, four points of evidence. Note the gradient is not one number — it depends on where you're standing, which is why torch recomputes it on every pass.

25.2 · P2A longer expression

Now y = 3x² + 5x. Its slope is 6x + 5 (each term differentiated, then added — the rule from school). Report the gradient at x = 0, 1 and 2, in the wording of the goal.

at x=0 the gradient is 5 at x=1 the gradient is 11 at x=2 the gradient is 17
Show solution
def grad(x):
    return 6 * x + 5

for x in [0, 1, 2]:
    print(f"at x={x} the gradient is {grad(x)}")

In torch this whole exercise is y = 3 * x ** 2 + 5 * x then y.backward(), and you never write the slope formula at all. That's the trade: torch does the calculus, you keep the understanding.

25.2 · P3Stretch — measure it, then check the formula

For f(x) = x³ the formula says the slope is 3x². Don't take that on trust: measure it with the nudge trick from the worked example, round to two decimals, and print both side by side so they can be compared. Use h = 0.00001.

1 3.0 3 2 12.0 12 3 27.0 27
Show solution
def f(x):
    return x ** 3

def numeric_slope(x):
    h = 0.00001
    return (f(x + h) - f(x - h)) / (2 * h)

for x in [1, 2, 3]:
    print(x, round(numeric_slope(x), 2), 3 * x ** 2)

The measured value agrees with the formula to the decimals we asked for — the tiny disagreement further out is the price of nudging by a real distance instead of an infinitely small one. Torch uses the formulas, not the nudging, which is why it is both exact and fast.

25.3

nn.Module is just a class you can already read

Read · ~3 minPractice · ~10 min

The problem. Open any deep-learning repository and the centrepiece is a block of code that looks like the hard part — the model definition. Twelve lines, unfamiliar words, and the sense that this is where the real difficulty hides.

The idea, in plain words. It isn't. It's a class. Specifically it's a class that inherits from nn.Module, calls super().__init__() as its first act, stores its layers as attributes, and defines one method called forward. You met every one of those ideas in Units 13–16, in a class about a bank account. The vocabulary is identical; only the nouns changed.

Two conventions are worth naming before you read one. First, a layer is itself an object you build once and call many times — nn.Linear(3, 4) makes a thing that takes 3 numbers in and gives 4 out, with its own internal knobs. Second, forward is the recipe for one pass through the model: input goes in the top, each layer is applied in turn, the answer comes out the bottom.

Listing 2 · read-only — run it in Colab
import torch
import torch.nn as nn

class Net(nn.Module):                       # 1
    def __init__(self):                     # 2
        super().__init__()                  # 3
        self.hidden = nn.Linear(3, 4)       # 4
        self.output = nn.Linear(4, 1)       # 5

    def forward(self, x):                   # 6
        x = torch.relu(self.hidden(x))      # 7
        return self.output(x)               # 8

model = Net()                               # 9
print(model)                                # 10
Net( (hidden): Linear(in_features=3, out_features=4, bias=True) (output): Linear(in_features=4, out_features=1, bias=True) )
  • Line 1 — class Net(nn.Module). Inheritance, exactly as in Unit 16: Net is a kind of Module and inherits everything Module can do (saving itself to disk, listing its own knobs, moving to a GPU).
  • Lines 2–3 — the rule from Unit 15, word for word: a subclass that writes its own __init__ must call super().__init__() first, or the parent never gets set up. Torch is unusually strict about it and says so loudly if you forget.
  • Lines 4–5 — attributes. self.hidden and self.output are boxes on this object, holding two layer objects. 3 numbers in → 4 out, then 4 in → 1 out; the middle numbers must agree, and that's the whole art of stacking layers.
  • Line 6 — a method, with self as the first parameter, taking one input x.
  • Line 7 — self.hidden(x) calls the layer object like a function (Unit 19's "things can be called"), and torch.relu bends the result: negatives become zero, positives pass through. That bend is what stops a stack of layers collapsing into one.
  • Line 8 — the last layer's answer, returned. Read the last line first: whatever forward returns is what the model gives you.
  • Lines 9–10 — build one instance and print it. Torch's __str__ lists the layers it found in the attributes — a free summary you didn't write.
▶ Run this in Colab
Key idea
Take a breath, because this deserves ceremony: the hardest-looking code in machine learning is a class with an __init__ and one method — and you learned to read that in Unit 13. Not a simplified version of it. That exact thing.
Common confusion

You define forward, but you never call it. Real code writes model(x), not model.forward(x) — because nn.Module defines __call__, which does some bookkeeping and then calls your forward. Calling forward yourself skips the bookkeeping and quietly breaks things. Define forward; call the model.

25.3 · P1Layers as attributes

Write a plain-Python Layer class holding n_in and n_out with a describe() method returning Linear(3 -> 4) style text, and a Net class whose __init__ stores two layers (3→4 and 4→1) as attributes hidden and output. Print both descriptions. Same skeleton as Listing 2, zero torch.

Linear(3 -> 4) Linear(4 -> 1)
Show solution
class Layer:
    def __init__(self, n_in, n_out):
        self.n_in = n_in
        self.n_out = n_out

    def describe(self):
        return f"Linear({self.n_in} -> {self.n_out})"

class Net:
    def __init__(self):
        self.hidden = Layer(3, 4)
        self.output = Layer(4, 1)

net = Net()
print(net.hidden.describe())
print(net.output.describe())

An object holding other objects as attributes — the composition pattern from Unit 14. That's all a model is: a bag of layers with a running order.

25.3 · P2super() earns its keep

The parent Module below sets up an empty parts list and announces itself. Write the child Net whose __init__ calls the parent's first, then registers two parts. Print the list at the end.

Module set up ['hidden', 'output']
Show solution
class Module:
    def __init__(self):
        self.parts = []
        print("Module set up")

    def add(self, name):
        self.parts.append(name)

class Net(Module):
    def __init__(self):
        super().__init__()
        self.add("hidden")
        self.add("output")

net = Net()
print(net.parts)

The child gets add for free by inheriting, and super().__init__() is what makes self.parts exist before add touches it. Torch's nn.Module.__init__ does the same job on a grander scale.

25.4

The training loop, read like prose

Read · ~3 minPractice · ~9 min

The problem. Unit 24 let you write model.fit(X, y) and walk away — scikit-learn hid the whole business behind one word. PyTorch doesn't hide it. You write the training loop yourself, and every tutorial assumes you can read those five lines at a glance.

The idea, in plain words. The loop is a rhythm, repeated: guess, measure the mistake, clear the old notes, work out the blame, nudge the knobs. Five lines, always in that order, and once you've seen it you'll recognise it in every repository you ever open.

What this session teaches is the reading of it, not the reason it works. Why nudging knobs against the gradient makes a model better — genuinely one of the loveliest ideas in the subject — belongs to the Deep Learning stage, where it gets the room it deserves. Today you learn what the lines say.

Listing 3 · read-only — run it in Colab
loss_fn = nn.MSELoss()                              # 1
optimizer = torch.optim.SGD(model.parameters(),     # 2
                            lr=0.01)

for epoch in range(100):                            # 3
    pred = model(x)                                 # 4  forward
    loss = loss_fn(pred, y)                         # 5  how wrong
    optimizer.zero_grad()                           # 6  clear old grads
    loss.backward()                                 # 7  work out the blame
    optimizer.step()                                # 8  nudge the knobs
epoch 0 loss 4.7213 epoch 20 loss 0.8104 epoch 40 loss 0.1937 epoch 60 loss 0.0522 epoch 80 loss 0.0158
  • Line 1 — the scorer. MSELoss compares predictions to answers and returns one number: bigger means more wrong.
  • Line 2 — the knob-turner. It is handed model.parameters() — every adjustable number inside every layer — and lr, the step size, which decides how big each nudge is.
  • Line 3 — do the whole thing 100 times. One pass over the data is called an epoch; that's the only new word in the block.
  • Line 4 — forward. Feed the inputs through the model and get predictions. This is where forward from 25.3 finally runs — note it's model(x), not model.forward(x).
  • Line 5 — loss. One number saying how wrong those predictions were. Because it was computed from tensors that remember, it carries the whole breadcrumb trail.
  • Line 6 — zero_grad. Gradients accumulate in torch — each .backward() adds to what's already in .grad rather than replacing it. So wipe last round's numbers first, or this round's blame is mixed with stale blame.
  • Line 7 — backward. Walk the trail from the loss back through every layer, filling in .grad on every knob: how much did you contribute to being this wrong?
  • Line 8 — step. The optimizer reads those .grad values and moves each knob a little in the direction that lowers the loss. Nothing else changes any weights — ever.

The printed output above is what a healthy run looks like: the loss falls. In the notebook you'll watch it fall for real, on numbers you can change.

▶ Run this in Colab
Common confusion

zero_grad() looks like pointless ceremony until it bites you. Leave it out and the gradients from every previous round pile up, the steps get wildly too big, and the loss explodes to nan — with no error message, because nothing illegal happened. Its position is flexible (many people put it first in the loop) but its presence is not.

Worked example

Task: feel the rhythm with no library at all. One knob w, a pretend gradient, a step size — repeated a few times. Thinking: this is line 8 of Listing 3, alone in a room. Watch the number walk downhill.

25.4 · P1Five steps downhill

Same idea, tightened up: start w at 10.0 with lr = 0.1, and for five steps compute grad = 2 * w, subtract lr * grad, and report w to three decimals in the goal's wording.

step 1: w = 8.000 step 2: w = 6.400 step 3: w = 5.120 step 4: w = 4.096 step 5: w = 3.277
Show solution
w = 10.0
lr = 0.1

for step in range(5):
    grad = 2 * w
    w = w - lr * grad
    print(f"step {step + 1}: w = {w:.3f}")

Each step takes 20% off, so the walk downhill slows as it goes — big strides where the slope is steep, small ones near the bottom. That self-slowing is the shape of every training curve you will ever see.

25.4 · P2What zero_grad() is for

The starter mimics torch's accumulating gradients: each round adds to the running total, so it prints 5, 10, 15. Add the one line that plays the part of optimizer.zero_grad() so every round starts clean and reports 5.

step 1: total=5 step 2: total=5 step 3: total=5
Show solution
grad = 5
total = 0

for step in range(3):
    total = 0                 # this is optimizer.zero_grad()
    total = total + grad
    print(f"step {step + 1}: total={total}")

One line, moved inside the loop. Without it you're steering by the sum of every mistake you ever made, which is as bad an idea as it sounds.

25.5

Your build — a batch of data through a layer

Read · ~2 minPractice · ~11 min

Time to put the pieces together on the smallest honest example there is: four samples, three features each, pushed through one 3→1 layer. In the notebook you'll do it with real tensors and a real nn.Linear. Here you'll do the same arithmetic with NumPy — because the shapes, which are the part people actually get wrong, are identical.

One shape rule carries the whole build: a batch is rows. Four samples of three features is a 4×3 grid — one row per sample. A layer that turns 3 numbers into 1 is a 3×1 grid of weights. Multiply them and the middle 3s cancel, leaving 4×1: one answer per sample. That's it. That's the shape arithmetic of every neural network layer ever written.

Listing 4 · read-only — this is the notebook's headline cell
import torch
import torch.nn as nn

torch.manual_seed(0)

x = torch.randn(4, 3)        # 4 samples, 3 features each
layer = nn.Linear(3, 1)      # a 3 -> 1 layer, weights created for you
out = layer(x)               # one forward pass

print(x.shape)
print(layer.weight.shape)
print(out.shape)
torch.Size([4, 3]) torch.Size([1, 3]) torch.Size([4, 1])
  • torch.randn(4, 3) makes random numbers in the shape you ask for — a stand-in for real data while you check the plumbing. The actual values differ every run unless you set the seed, which is why only the shapes are printed here.
  • nn.Linear(3, 1) creates the weights itself, at random, ready to be trained. Torch stores them transposed (1×3), which surprises everyone once and then never again.
  • layer(x) — the layer called like a function. Four rows in, four rows out, one number each.
  • Reading shapes out loud after every step is the single best debugging habit in deep learning. Most bugs are a shape you assumed and never checked.

25.5 · P1The same shapes, in NumPy

Build the batch X as a 4×3 grid of ones, the weights W as a 3×1 grid, add a bias, and report all three shapes. Use np.ones((rows, cols)) and @. This is Listing 4 with the training wheels visible.

X: (4, 3) W: (3, 1) out: (4, 1)
Show solution
import numpy as np

X = np.ones((4, 3))
W = np.ones((3, 1))
b = 0.1

print("X:", X.shape)

The inner numbers must match — 4×3 against 3×1 — and the outer numbers survive: 4×1. The bias is a single number broadcast onto every row, exactly the stretching from 25.1's P2.

25.5 · P2One sample, done twice

Take one sample [1.0, 2.0, 3.0] and weights [0.5, -1.0, 2.0] with bias 0.1. Work the answer out the long way — every feature times its weight, added up, plus the bias, written as one arithmetic expression — then again with np.dot. They must agree. That agreement is what a layer does.

by hand: 4.6 by dot: 4.6
Show solution
import numpy as np

x = np.array([1.0, 2.0, 3.0])
w = np.array([0.5, -1.0, 2.0])
b = 0.1
by_hand = 1.0 * 0.5 + 2.0 * -1.0 + 3.0 * 2.0 + b
by_dot = np.dot(x, w) + b
print(f"by hand: {by_hand}")
print(f"by dot:  {by_dot}")

0.5 − 2.0 + 6.0 + 0.1 = 4.6. A neuron is a weighted sum plus a bias — one line of school arithmetic, done a few million times a second. Nothing more mystical than that is happening inside nn.Linear.

B4Stretch — a shape checker with no torch in sight

Write FakeLinear (holding n_in, n_out, with a forward(shape) that takes a (rows, cols) tuple, returns (rows, n_out) if cols matches n_in, and the text shape mismatch otherwise) and a FakeNet holding a 10→6 layer and a 6→2 layer that runs a shape through both, stopping early on a mismatch. Test it with a good batch and a bad one.

(4, 2) shape mismatch
Show solution
class FakeLinear:
    def __init__(self, n_in, n_out):
        self.n_in = n_in
        self.n_out = n_out

    def forward(self, shape):
        rows, cols = shape
        if cols != self.n_in:
            return "shape mismatch"
        return (rows, self.n_out)

class FakeNet:
    def __init__(self):
        self.a = FakeLinear(10, 6)
        self.b = FakeLinear(6, 2)

    def forward(self, shape):
        shape = self.a.forward(shape)
        if shape == "shape mismatch":
            return shape
        return self.b.forward(shape)

net = FakeNet()
print(net.forward((4, 10)))
print(net.forward((4, 7)))

You have just written, in twenty lines, the part of PyTorch that produces its most famous error message. A model class is a pipeline of objects, each one checking that what arrived is what it expected — and now you know what it feels like from the inside.
