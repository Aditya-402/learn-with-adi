13.1

You've been using objects all along

Read · ~3 minPractice · ~8 min

The problem. Twelve units in, something has been quietly odd and nobody said it out loud. You write len(word) — a function with the thing in brackets. But you also write word.upper() — the thing first, then a dot, then the ability. Two shapes for what looks like the same job. Why?

The idea, in plain words. Because word is not just data sitting in a box. It is data with abilities attached. The dot means "reach inside this particular thing and use one of its own abilities". A string knows how to shout (.upper()), a list knows how to sort itself (.sort()), a dictionary knows how to hand over its pairs (.items()). Nobody passes the data in — the data is the thing you called the ability on.

A bundle like that — some data, plus the abilities that belong to it — is called an object. And every object was stamped out from a blueprint called a class. Ask any value what class it came from and it will tell you:

print(type("hi")) → <class 'str'>

Read that carefully, because it's the reveal of this unit. str is a class. So is list. So is dict. Someone sat down and wrote them — decided what a string holds and what a string can do — and ever since, every quoted piece of text you've typed has been an object stamped from their blueprint. That's all a class is. And from the next section on, you write your own.

  • Attribute — a piece of data that belongs to an object, reached with a dot: account.balance.
  • Method — an ability that belongs to an object, reached with a dot and called with brackets: word.upper().
  • Same dot, two uses. Brackets tell you which one you're looking at.
Trace it by hand — the dot at work
nums = [4, 1, 3] nums.append(2) nums.sort() print(nums) print(type(nums))

Line 1: the box nums holds a list object: the data [4, 1, 3] and every list ability, riding along with it.

Line 2: nums.append(2) — no list is passed in, because nums is the list. The object changes itself: [4, 1, 3, 2].

Line 3: nums.sort() — again, it sorts itself. Now [1, 2, 3, 4]. Note the empty brackets: no arguments needed, but brackets still required, because calling is what brackets mean.

Lines 4–5: the contents, then the blueprint it came from:

[1, 2, 3, 4] <class 'list'>
Key idea
An object is data plus the abilities that belong to that data, travelling together. A class is the blueprint the object was stamped from. str, list and dict are classes someone wrote — nothing about them is magic, and nothing stops you writing your own.
Worked example

Task: take three values you've used since Unit 2 and make each one confess what it is and what it can do. Thinking: type() for the blueprint, the dot for the abilities. Watch how the same dot serves three completely different classes.

13.2

Your first class — class Player:

Read · ~4 minPractice · ~10 min

The problem. You want to track two players in a game: each has a name and a health number. With what you know today, that's four loose boxes — p1_name, p1_health, p2_name, p2_health — and a permanent low-level anxiety that you'll damage the wrong one. Add a third player and it's six boxes. A dictionary per player helps, but nothing stops you spelling a key wrong, and nothing keeps the abilities near the data.

The idea, in plain words. Write the blueprint once. A class is a description of what one player has and what one player can do. Then stamp out as many players as you like, each carrying its own copy of the data.

class Player: def __init__(self, name, health): self.name = name self.health = health p1 = Player("Ada", 100)

Four things are happening there, and each is worth its own sentence.

  • class Player: starts the blueprint. Class names get a Capital Letter by long convention — that's how a reader tells Player the blueprint from player the thing.
  • __init__ is a special method that Python runs automatically the moment an object is created. Its job is to fill in the new object's starting data. You never call it yourself; you just write Player("Ada", 100) and Python calls it for you. (Those double underscores mean "Python knows this name" — Unit 14 is entirely about that family.)
  • self is the new object being built, handed to the method as its first parameter. More on it in 13.3; for now, read self as "this particular one".
  • self.name = name is Unit 2's store-into arrow, aimed inside the object: take the value that arrived as name and put it in a box called name that belongs to this object. That's an attribute.

And here's the payoff: p1 = Player("Ada", 100) and p2 = Player("Alan", 80) create two separate objects, each with its own name box and its own health box. Change one and the other doesn't flinch. The labeled box from Unit 2 hasn't gone anywhere — an object is simply a box of boxes, with abilities attached to the outside.

Trace it by hand — two objects, four boxes
class Player: def __init__(self, name, health): self.name = name self.health = health p1 = Player("Ada", 100) p2 = Player("Alan", 80) p1.health = 60 print(p1.health, p2.health)

The class block: nothing runs. Python reads the blueprint and files it away, exactly as it files a def without running it.

p1 = Player("Ada", 100): Python makes a blank new object, calls __init__ with self = that new object, name = "Ada", health = 100. Two boxes get filled inside the object. The finished object is stored in p1.

p2 = Player("Alan", 80): the whole thing happens again, from scratch, into a different object. Two more boxes, unrelated to the first two.

p1.health = 60: store-into, aimed at one box inside one object. p2 is untouched — it was never involved.

60 80
Fig. 1 — The class holds no data; it is the shape. Every Player(...) call stamps out a fresh object with its own boxes inside. This is the state-of-memory picture from Unit 2, nested one level deeper.
Common confusion

Class vs instance — the distinction that trips everyone for about a week. The class is the cookie cutter; an instance is a cookie. The cutter has a shape but no dough in it; you can't eat it, and asking a cutter what flavour it is makes no sense. Player has no name and no health — Player.health is meaningless. p1, stamped out by that cutter, holds "Ada" and 100. One cutter, unlimited cookies, each with its own filling. "Instance" and "object" mean the same thing here; these notes use both.

Worked example

Task: write the Player blueprint and stamp out two players, then prove they're independent. Thinking: the class block first (it defines, it doesn't run), then the creations, then a change to one and a read of both. Predict the last line before you run it.

13.3

Methods & self — abilities that know whose they are

Read · ~4 minPractice · ~12 min

The problem. Your players have data. Now they need to do things — take damage, heal, report. You could write a plain function take_damage(player, amount) and pass the player in every time. It works. But then the ability lives somewhere else, far from the data, and the whole point of an object was that they travel together.

The idea, in plain words. Move the function inside the class. A function written inside a class is called a method, and it gets one privilege: its first parameter, by universal convention named self, arrives already holding the object it was called on.

def take_damage(self, amount): self.health = self.health - amount

Two parameters in the def. But you call it with one argument:

p1.take_damage(10)

Where did self come from? From the dot. Everything to the left of the dot is quietly handed in as the first argument. p1.take_damage(10) means, in full, "run Player's take_damage with self = p1 and amount = 10". Call it on p2 instead and the exact same code touches p2's boxes. One method definition, correct for every object ever stamped.

So read self as "this particular one". Inside a method, self.health means "the health box of whichever object I was called on". Without the self., health would just be an ordinary local box that vanishes when the method ends — a real and common bug.

Trace it by hand — one method, two objects
class Player: def __init__(self, name, health): self.name = name self.health = health def take_damage(self, amount): self.health = self.health - amount print(f"{self.name} is now on {self.health}") p1 = Player("Ada", 100) p2 = Player("Alan", 100) p1.take_damage(30) p2.take_damage(10) p1.take_damage(25)

p1.take_damage(30): self = p1, amount = 30. Right side first: self.health - amount → 100 − 30 → 70, stored back into p1's health box. Then the print reads p1's two boxes.

p2.take_damage(10): identical code, different self. 100 − 10 → 90, into p2's box. p1 is still on 70.

p1.take_damage(25): self = p1 again, whose health is now 70. 70 − 25 → 45.

Ada is now on 70 Alan is now on 90 Ada is now on 45
Fig. 2 — The dot is an argument-passer. Two parameters in the definition, one argument at the call site, and the gap is filled by whatever sits to the left of the dot.
Common confusion

Forgetting self in the def. Write def add(amount): inside a class, call t.add(5), and Python says: TypeError: add() takes 1 positional argument but 2 were given. That message reads like nonsense — you passed one argument! Decode it with Fig. 2: the dot silently added t as a first argument, so Python really did receive two, while your def only has room for one. Whenever a method complains about "one too many" arguments, the missing self is the answer. Every time.

Worked example

Task: give Player the ability to take damage, and prove one definition serves every object. Thinking: the method goes inside the class, indented to the same level as __init__, with self first. Every box it touches gets a self. in front — that's what makes it this player's health rather than a passing local value.

13.3 · P3Two methods, one object

Write Thermostat: __init__ stores a temp, warmer(self, degrees) raises it, cooler(self, degrees) lowers it. The script at the bottom must then print the goal.

Now 20 degrees
Show solution
class Thermostat:
    def __init__(self, temp):
        self.temp = temp

    def warmer(self, degrees):
        self.temp = self.temp + degrees

    def cooler(self, degrees):
        self.temp = self.temp - degrees

t = Thermostat(22)
t.warmer(3)
t.cooler(5)
print(f"Now {t.temp} degrees")

22 + 3 = 25, then 25 − 5 = 20. Each call reads the box's current contents and stores back — Unit 2's count = count + 1, now living inside an object.

13.3 · P4Stretch — a method that protects its data

A battery can't go below zero. Write Battery with __init__(self, level=100), a use(self, amount) that drains the level but clamps it at 0 (an if inside the method), and report(self) that prints the level as a percentage. Match the goal.

Battery: 0%
Show solution
class Battery:
    def __init__(self, level=100):
        self.level = level

    def use(self, amount):
        self.level = self.level - amount
        if self.level < 0:
            self.level = 0

    def report(self):
        print(f"Battery: {self.level}%")

b = Battery()
b.use(30)
b.use(90)
b.report()

100 → 70 → would be −20, clamped to 0. This is the real reason to keep data inside an object: the rule about what the data is allowed to be lives right next to the data, and nobody can drain the battery past empty by accident.

13.4

Methods that answer vs methods that act

Read · ~3 minPractice · ~10 min

The problem. Your game needs to ask a question — "is this player still alive?" — and act on the answer with an if. You could write a method that prints "alive" or "dead", but an if can't read your screen. Printing is for humans; deciding needs a value.

The idea, in plain words. This is Unit 7's return-versus-print rhythm, replayed one level up. Methods come in two flavours, and knowing which you're writing is half of designing a class well.

  • Methods that act — they change the object's state and hand back nothing. take_damage(), heal(), deposit(). You call them on a line of their own.
  • Methods that answer — they compute something from the object's state and return it, changing nothing. is_alive(), area(), total(). You call them inside something else: an if, an f-string, a sum.

A method that answers is written exactly like a plain function that answers:

def is_alive(self): return self.health > 0

Note what's not there: no if, no True/False written by hand. self.health > 0 already is a True or a False (Unit 3), so returning the comparison directly is both shorter and clearer. Then if p.is_alive(): reads like English, and that is the whole aim.

A naming habit worth stealing: methods that answer a yes/no question start with is_ or has_. A reader then knows, without opening the method, that calling it is safe and that the answer is what matters.

Trace it by hand — asking, then acting
p = Player("Ada", 30) p.take_damage(40) print(p.is_alive()) if not p.is_alive(): p.heal(50) print(p.health, p.is_alive())

Line 2: a method that acts. 30 − 40 → health is now −10. Nothing comes back; the line's whole purpose was the change.

Line 3: a method that answers. −10 > 0 → False. That value travels out of the method and into print, which shows False — capital F, as always.

Line 4: the same answer, this time feeding an if. not False → True, so the body runs.

Line 5: acts again. −10 + 50 → 40.

Line 6: reads the attribute directly and asks the question again — 40 > 0 → True:

False 40 True
Common confusion

A method that prints hands back None. Write def area(self): print(self.side * self.side) and then total = s.area() + 10 explodes with TypeError: unsupported operand type(s) for +: 'NoneType' and 'int'. The number was shown on screen and then thrown away — printing is not returning. Unit 7 warned you; the warning does not expire just because the function moved inside a class. Rule of thumb: if anything other than a human might want the value, return it.

Worked example

Task: a Player with two acting methods and one answering method, driven by an if. Thinking: take_damage and heal change state and return nothing; is_alive returns the comparison itself and changes nothing. Watch how the answering method slots straight into the if.

13.4 · P3Stretch — an answer inside an f-string

Give Temperature a method to_fahrenheit(self) that returns the converted number (celsius × 9 / 5 + 32). Call it straight inside the f-string, formatted to one decimal place, to match the goal.

37C is 98.6F
Show solution
class Temperature:
    def __init__(self, celsius):
        self.celsius = celsius

    def to_fahrenheit(self):
        return self.celsius * 9 / 5 + 32

t = Temperature(37)
print(f"{t.celsius}C is {t.to_fahrenheit():.1f}F")

Method calls are allowed inside braces, brackets and all — the returned number then meets :.1f and gets dressed for the exit. Format at the exit, as always; the method itself hands back the honest float.

13.5

Your build — a bank account and a small battle

Read · ~2 minPractice · ~12 min

Two builds, because objects only really click when you've made the same idea twice in different clothes. First a BankAccount — an owner, a balance, and three abilities that guard it. Then a two-player skirmish using everything from 13.3 and 13.4.

Keep the BankAccount tidy: it comes back in Units 15 and 16, first learning to print itself properly and later inheriting a whole family of accounts. What you write here is a foundation, not a throwaway.

13.5 · P1Build 1 — BankAccount

Write the class: __init__(self, owner, balance=0); deposit(self, amount) adds to the balance; withdraw(self, amount) subtracts it, but if the amount is more than the balance it prints Insufficient funds and changes nothing; report(self) prints the owner and balance with exactly two decimals. The script below is fixed — don't change it.

Insufficient funds Ada: 380.00 Alan: 200.00
Show solution
class BankAccount:
    def __init__(self, owner, balance=0):
        self.owner = owner
        self.balance = balance

    def deposit(self, amount):
        self.balance = self.balance + amount

    def withdraw(self, amount):
        if amount > self.balance:
            print("Insufficient funds")
        else:
            self.balance = self.balance - amount

    def report(self):
        print(f"{self.owner}: {self.balance:.2f}")

Ada: 0 → 500 → 380, then the 1000 is refused and the balance stays put. Alan starts at 250 and ends at 200. The :.2f makes an int balance print as money — and note the guard lives inside withdraw, so no caller anywhere can ever overdraw the account.

13.5 · P2Build 2 — the tiny battle

Rebuild Player from memory — name, health, take_damage, heal, is_alive — and let the fixed script below run the skirmish. Health is allowed to go negative here; the question is_alive asks is simply whether it's still above zero.

Ada 70 True Alan -10 False Alan revived at 30
Show solution
class Player:
    def __init__(self, name, health):
        self.name = name
        self.health = health

    def take_damage(self, amount):
        self.health = self.health - amount

    def heal(self, amount):
        self.health = self.health + amount

    def is_alive(self):
        return self.health > 0

Ada: 100 − 30 = 70, alive. Alan: 60 − 70 = −10, not alive — so the if fires and heals him to 30. One class, two objects, three methods, and a program that reads like a description of what's happening. That's the whole argument for objects.

Problem bank — everything at once

B1The Book class

Dune by Frank Herbert Title? The Hobbit Author? Tolkien The Hobbit by Tolkien

B2Rectangle, and answers that add up

Write Rectangle with width and height, plus area(self) and perimeter(self) — both must return, not print, because the last line adds two areas together. Match the goal.

Area: 28 Perimeter: 22 Total area: 53
Show solution
class Rectangle:
    def __init__(self, width, height):
        self.width = width
        self.height = height

    def area(self):
        return self.width * self.height

    def perimeter(self):
        return 2 * (self.width + self.height)

4 × 7 = 28, 2 × (4 + 7) = 22, and 28 + 25 = 53. Had area printed instead of returned, the last line would have died on None + None — the exact failure from 13.4's confusion box.

B3Counter — Unit 2's ache, cured

Remember Unit 2, where raising a count meant typing count = count + 1 three times? Write Counter with __init__(self) taking no extra arguments and starting total at 0, a click(self) that adds one, and a reset(self) that returns it to zero. The script below then does the rest.

5 5 1 0 1
Show solution
class Counter:
    def __init__(self):
        self.total = 0

    def click(self):
        self.total = self.total + 1

    def reset(self):
        self.total = 0

An __init__ with only self is perfectly ordinary — some objects need no ingredients, just a sensible starting state. And two counters count separately without a single extra line of bookkeeping: that's the four-loose-boxes problem solved for good.

B4Stretch — the Playlist holds a list

An attribute can hold anything, including a list. Write Playlist: __init__(self, name) stores the name and starts an empty songs list; add(self, song) appends to it; show(self) prints a header with the count, then every song numbered from 1. Match the goal exactly.

Study (3 songs) 1. Nightcall 2. Clair de Lune 3. Weightless
Show solution
class Playlist:
    def __init__(self, name):
        self.name = name
        self.songs = []

    def add(self, song):
        self.songs.append(song)

    def show(self):
        print(f"{self.name} ({len(self.songs)} songs)")
        for i, song in enumerate(self.songs, start=1):
            print(f"{i}. {song}")

Note that self.songs = [] lives in __init__, so every playlist gets its own fresh list. enumerate(..., start=1) hands over position and song together, counting from 1 for humans while the list itself stays 0-based underneath. (A range(len(...)) loop with i + 1 works too — enumerate just says it more plainly.)
