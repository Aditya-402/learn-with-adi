14.1

The ugly print problem — __str__

Read · ~3 minPractice · ~9 min

The problem. You build a Money object holding 250 rupees, you print it to check your work, and Python answers with <__main__.Money object at 0x7f3a1c0d5e50>. Technically true. Completely useless. Every object you make from here on will print like this until you do something about it.

The idea, in plain words. That gibberish is Python's fallback: "it's a Money, it lives at this address in memory, and nobody told me how to describe it." Nobody told it — so tell it. Add a method called __str__ to your class that returns a string, and print will use your sentence instead of its own.

def __str__(self): return f"{self.amount} rupees"

Those two underscores on each side make it a dunder method — "double underscore", and Python programmers really do say it out loud. Dunder names are not decoration and not magic: they are the names Python itself goes looking for. You will never call __str__ by hand. You write it once; print, str() and every f-string call it for you, forever.

One honest footnote while we're here. Python has a sibling method, __repr__. The split is: __str__ is for humans — the friendly sentence a user should read — and __repr__ is for developers — the precise, unambiguous version you'd want in a debugger. When only __str__ exists, printing works and that's what we need today. Learn __repr__ the day you're staring at a list of objects and want detail; __str__ is enough for now.

Trace it by hand — where the sentence comes from
class Money: def __init__(self, amount): self.amount = amount def __str__(self): return f"{self.amount} rupees" wallet = Money(250) print(wallet)

The class lines: nothing runs yet — the cutter is being shaped, no cookies exist.

wallet = Money(250): a new object; __init__ runs and puts 250 into its amount attribute.

print(wallet): print needs text, so it asks the object: do you have a __str__? It does. Python runs wallet.__str__() — with self being wallet — which returns the string "250 rupees". Print prints that.

250 rupees

Delete the __str__ method and the last line becomes the memory-address gibberish again. Nothing else changes.

Common confusion

__str__ must return a string, not print one. Writing print(f"{self.amount} rupees") inside it looks like it works — the text appears! — but the method hands back None, and Python complains: TypeError: __str__ returned non-string (type NoneType). Same rule as every function in Unit 10: a method that prints gives you nothing to use; a method that returns gives you everything.

Worked example

Task: see the ugly print with your own eyes, then fix it. Thinking: run this exactly as written first — the second half of the output is the useless version. (No check button on this one: the memory address is different every single run, on every machine. That's the whole point.)

14.2

The equality surprise — __eq__

Read · ~3 minPractice · ~10 min

The problem. You make Point(3, 4). Your friend makes Point(3, 4). Same class, same numbers, same everything. You ask Python whether they're equal and it says False. It is not being difficult; it genuinely doesn't know that you consider them the same.

The idea, in plain words. Remember the house picture: an object is a box of boxes with abilities attached. When you write p == q and nobody has said otherwise, Python compares the boxes themselves, not their contents — it asks "are these two names pointing at the one same box?" Two separately-built Points are two separate boxes, so the answer is honestly False. Identical twins are not the same person.

To make == mean what you mean, write __eq__. It takes a second parameter — traditionally called other — which is whatever sits on the right of the ==. Compare the attributes you care about, and return the True/False answer:

def __eq__(self, other): return self.x == other.x and self.y == other.y

Note what this does not do: it doesn't compare every attribute automatically, and it doesn't decide anything on its own. You declare what "the same" means for your class. Two bank accounts with equal balances — same, or not? Two songs with the same title but different artists? Only you know. That's the job __eq__ hands you.

Trace it by hand — three names, two boxes
p = Point(3, 4) q = Point(3, 4) r = p print(p == q) print(p == r)

Line 1: a box is built, filled with x=3 and y=4, labeled p.

Line 2: a second, brand-new box is built, filled identically, labeled q. Same contents. Different box.

Line 3: no box is built. r is a second label stuck on the box that p already names.

Line 4: with no __eq__, Python asks "same box?" — p's box and q's box are different objects →

False

Line 5: same question, and this time it's literally the same box →

True

Now add __eq__ comparing x and y, and line 4 flips to True — because you changed the question being asked.

Fig. 1 — By default == asks "which box?" — an identity question. __eq__ replaces it with a contents question of your own design.
Common confusion

"But "abc" == "abc" is True and I never wrote an __eq__!" Correct — because the people who built str, int, list and dict wrote one for you, long ago. Every built-in type you've compared since Unit 3 has been running somebody's __eq__. The default "same box?" behaviour only shows up for classes nobody has taught yet — which, from Unit 13 onward, means yours.

Worked example

Task: watch == change its mind. Thinking: the same two comparisons run twice — once on a bare class, once on a class with three extra lines. Nothing about the data differs; only the question does.

class Point:
    def __init__(self, x, y):

14.3

The protocol reveal — how len() finds __len__

Read · ~4 minPractice · ~10 min

The problem. There's a question you should have asked back in Beginner and probably didn't: how on earth does len() work on a string, a list and a dictionary? Three completely different things. One function. Does len() contain a giant list of every type it knows about? And if it does — your Playlist isn't on that list, so len(playlist) is hopeless, right?

The idea, in plain words. No giant list. Built-in functions are polite knockers. len(x) doesn't know anything about x; it walks up to the object, knocks, and asks a single question — "do you have a __len__?" If the object answers, len() returns whatever it says and leaves. Strings answer. Lists answer. Dictionaries answer. That's the entire mystery: three different classes, each with its own __len__, one polite knocker at the door.

The same is true of everything you've met today. print knocks with __str__. == knocks with __eq__. + knocks with __add__ (next section). This arrangement — "if you implement these names, this feature works on you" — is called a protocol. Nobody has to register anything, nobody inherits anything. You just answer the knock.

you writePython knocks withyou get, free
print(x), f"{x}", str(x)x.__str__()readable output everywhere
x == yx.__eq__(y)!=, in, .count(), .remove()
len(x)x.__len__()counting — and truth (see P3)
x + yx.__add__(y)arithmetic in your own domain

So the answer to "is my Playlist hopeless?" is: only until you write four lines. Add __len__ returning the length of the inner list, and len(playlist) works — not by permission, but because that was always how len() worked.

Fig. 2 — The protocol. The left column is the code you and every other Python programmer write; the right is the question Python turns it into. Your classes get to answer.
Key idea
Python's own machinery is open to your classes. Built-ins don't have a private list of blessed types — they knock, using dunder names, and anything that answers is treated as a first-class citizen. This is why len() worked on strings, lists and dictionaries back in Beginner: not three special cases, one protocol.
Common confusion

You write dunder methods; you don't call them. playlist.__len__() runs, but writing it is like ringing your own doorbell — len(playlist) is the sentence Python programmers read. Same for __str__ (use print or str()) and __eq__ (use ==). Dunders are the wiring behind the switch, and you don't reach into the wall to turn on a light.

Worked example

Task: make len() work on Unit 13's Playlist. Thinking: the playlist already keeps its songs in a list, and lists already answer len() — so __len__ has nothing clever to do. It just passes the question along to the list inside. Most dunder methods are this short.

14.4

Making + mean something — __add__

Read · ~3 minPractice · ~9 min

The problem. Two Money objects, 40 rupees and 35 rupees. The natural thing to write is Money(40) + Money(35). Python refuses: TypeError: unsupported operand type(s) for +: 'Money' and 'Money'. It's the Unit 2 refusal all over again — + means "add" for numbers and "glue" for strings, and for your class it means nothing at all until you say.

The idea, in plain words. Same knock, new name. a + b makes Python ask a.__add__(b). Write that method and + means whatever you decide — combining money, stacking distances, adding vectors. This is called operator overloading: the operator is old, the meaning is yours.

There's a rule of good manners attached, and it's the important half of this section. __add__ should build and return a brand-new object — it must not quietly change either of the ones being added:

def __add__(self, other): return Money(self.amount + other.amount)

Why? Because that's what + has always meant. 3 + 4 doesn't turn the 3 into a 7, and "a" + "b" leaves both strings exactly as they were — Unit 8's immutability wisdom, stated as a promise: an expression produces a new value; it doesn't vandalise its inputs. If your __add__ did self.amount = self.amount + other.amount, then total = a + b would silently corrupt a, and the bug it caused would be found three files away, at midnight. Build new. Return it.

Trace it by hand — three objects, not two
tea = Money(40) snack = Money(35) bill = tea + snack print(tea.amount, snack.amount, bill.amount)

Lines 1–2: two boxes, holding 40 and 35.

Line 3: Python turns tea + snack into tea.__add__(snack). Inside, self is tea and other is snack. The method computes 40 + 35 → 75 and hands that to Money(...), which builds a third box. The return passes it out, and bill labels it.

Line 4: all three are still standing, untouched:

40 35 75

Three objects exist at the end. That's the signature of a well-behaved +.

Common confusion

Forgetting the return is the classic. A __add__ that computes the sum and stops gives you total = a + b where total is None — no error at the scene of the crime, just a baffling AttributeError: 'NoneType' object has no attribute 'amount' on some later line. Unit 10's law, restated for dunders: if you didn't return it, you didn't produce it.

Worked example

Task: add __add__ to Money and prove it built something new. Thinking: the method has exactly one job — compute the combined amount and pass it to the class to build a fresh object. Watch the two originals survive.

14.5

Your build — Money, and a Playlist that prints itself

Read · ~2 minPractice · ~12 min

Everything from this session in two classes. First Money, complete: __init__ to hold the amount, __str__ so it prints like currency, __eq__ so equal amounts compare equal, __add__ so bills add up. Four dunders and the class stops feeling like something you bolted together — it feels like a type Python shipped with.

Then Playlist, where __str__ gets ambitious: a multi-line, numbered listing. A returned string may contain \n newline characters, and print will honour every one of them — so a single print(p) can produce a whole formatted report.

14.5 · P1Stage 1 — the complete Money class

Write all four methods. __str__ must return the amount to two decimal places followed by  rupees (Unit 2's :.2f, still the money formatter). __eq__ compares amounts; __add__ returns a new Money. The script below is fixed — don't change it, make it work.

12.50 rupees 45.50 rupees 58.00 rupees True False
Show solution
class Money:
    def __init__(self, amount):
        self.amount = amount
    def __str__(self):
        return f"{self.amount:.2f} rupees"
    def __eq__(self, other):
        return self.amount == other.amount
    def __add__(self, other):
        return Money(self.amount + other.amount)

tea = Money(12.5)
cake = Money(45.5)
bill = tea + cake
print(tea)
print(cake)
print(bill)
print(bill == Money(58))
print(tea == cake)

Read the last two lines again — bill was never told about the number 58, yet bill == Money(58) is True, because __add__ produced a real Money holding 58.0 and __eq__ knows how to look inside it. Four small methods, and the class now behaves in the arithmetic, the printing and the comparing. That's what "feels native" means.

14.5 · P2Stage 2 — a Playlist that prints itself

Give Playlist its __len__ and a __str__ that returns a heading line (name (count songs)) followed by one numbered line per song. Build the string with a counter and \n, and return it once at the end — one print(p) must produce all four lines.

3 Monsoon (3 songs) 1. Rain Song 2. Cloudburst 3. Petrichor
Show solution
class Playlist:
    def __init__(self, name):
        self.name = name
        self.songs = []
    def add(self, song):
        self.songs.append(song)
    def __len__(self):
        return len(self.songs)
    def __str__(self):
        text = f"{self.name} ({len(self.songs)} songs)"
        number = 1
        for song in self.songs:
            text = text + f"\n{number}. {song}"
            number = number + 1
        return text

p = Playlist("Monsoon")
p.add("Rain Song")
p.add("Cloudburst")
p.add("Petrichor")
print(len(p))
print(p)

The loop grows one string, adding a \n before each new line so the heading keeps its place. Note __str__ calling len(self.songs) for the count — dunders are ordinary methods and may use anything a method can. (If you reached for "\n".join(...) instead, that's the same idea written shorter, and it's perfectly good.)

B2Distances that add up

A Distance holding kilometres. Give it __str__ (8 km — no decimals, just the number and the unit), __eq__ and __add__. The script is fixed; make it produce the goal.

8 km True False
Show solution
class Distance:
    def __init__(self, km):
        self.km = km
    def __str__(self):
        return f"{self.km} km"
    def __eq__(self, other):
        return self.km == other.km
    def __add__(self, other):
        return Distance(self.km + other.km)

morning = Distance(5)
evening = Distance(3)
day = morning + evening
print(day)
print(day == Distance(8))
print(morning == evening)

Structurally identical to Money — which is the lesson. Once you've seen the shape (__str__ to show, __eq__ to compare, __add__ to combine), you can hand it to any "a quantity with a unit" class in ten lines.

B3The shopping cart

A Cart that collects prices. It needs add(price), a __len__ for how many items, and an ordinary method total() returning the sum. Three prices come from input(); the fixed inputs here are 40, 25 and 15. Note the deliberate mix: counting is a protocol, but "total" isn't a Python built-in — so it stays a plain method with a plain name.

Price 1? 40 Price 2? 25 Price 3? 15 3 items Total: 80
Show solution
class Cart:
    def __init__(self):
        self.prices = []
    def add(self, price):
        self.prices.append(price)
    def __len__(self):
        return len(self.prices)
    def total(self):
        running = 0
        for price in self.prices:
            running = running + price
        return running

cart = Cart()
cart.add(int(input("Price 1? ")))
cart.add(int(input("Price 2? ")))
cart.add(int(input("Price 3? ")))
print(f"{len(cart)} items")
print(f"Total: {cart.total()}")

Convert at the door — int(input(...)) — so the cart never holds text pretending to be a price. And the naming rule worth carrying forward: give a method a dunder name only when Python already has a syntax knocking for it. Everything else gets an honest English name.

B4Stretch — Vector, and a promise about later

A Vector has an x and a y. Adding two vectors adds the x's and the y's separately, and a vector prints as (x, y) — parentheses, comma, one space. Write __add__ and __str__.

(1, 2) (2, 5) (3, 7)
Show solution
class Vector:
    def __init__(self, x, y):
        self.x = x
        self.y = y
    def __add__(self, other):
        return Vector(self.x + other.x, self.y + other.y)
    def __str__(self):
        return f"({self.x}, {self.y})"

a = Vector(1, 2)
b = Vector(2, 5)
print(a)
print(b)
print(a + b)

Keep this class. It comes back twice: in the bridge unit where NumPy does exactly this to whole arrays of numbers at once — and again in the LLM series, where "a vector with an x and a y" becomes "a vector with 4096 numbers", and adding them is a thing computers do a billion times a second. You have just written, by hand, the smallest honest version of the object that machine learning is built on.
