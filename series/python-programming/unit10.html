10.1

Writing files — a box that outlives the program

Read · ~4 minPractice · ~8 min

The problem. The to-do app from Unit 7 works beautifully — until you close it. Every labeled box lives in the program's memory, and that memory is a whiteboard wiped clean the instant the program ends. Add ten tasks today, run the program tomorrow: empty list. Real apps remember. Where do they put things?

The idea, in plain words. In files. A file is a box that lives on the disk instead of inside the program — it has a label (its name), it holds contents, and crucially it's still there after the program dies, after the computer restarts, after a year. Three lines create one:

  • f = open("notes.txt", "w") asks the operating system: give me a file called notes.txt, opened for writing. "w" is the mode — write mode hands you a blank page. The box f holds the open door to it.
  • f.write("buy milk\n") puts exactly those characters on the page. Unlike print(), write() gives you no free newline — the \n is yours to add, every line. Forget it and your lines fuse into one.
  • f.close() closes the door. Until then, your words may still be sitting in a holding area rather than safely on disk.

That's the raw mechanism — and Python offers a better shape for it immediately. Write the same thing as a block, and the closing happens for you:

with open("notes.txt", "w") as f:
    f.write("buy milk\n")

When the indented block ends, the file is closed — automatically, even if an error strikes mid-write. The full story of with comes in Unit 20; for now the working summary is: it closes the door behind you. These notes use it everywhere from here on, and so should you.

Trace it by hand — three writes, one page
with open("notes.txt", "w") as f: f.write("buy milk\n") f.write("water plants") print("saved")

Line 1: the operating system hands over a fresh, blank notes.txt — blank even if a notes.txt already existed. f is the open door.

Line 2: the characters buy milk land on the page, then a line break — because you typed \n.

Line 3: water plants lands, no \n this time — the page ends mid-line. Block ends, door closes.

Line 4: the only thing that reaches the screen:

saved

Files are quiet — writing prints nothing. The file itself now holds two lines: buy milk and water plants. Reading it back is the next section; until then, our problems borrow one peek line.

Fig. 1 — Memory is a whiteboard, wiped at the end of every program; the disk is a notebook. (One honest caveat: this page's practice runner wipes its little pretend disk between Runs too — Colab and your own machine keep the notebook.)
Common confusion

Mode "w" wipes the file at the moment of opening — not when you first write. open("diary.txt", "w") followed by nothing at all still leaves you with an empty diary. Opening the same file in "w" twice in one program is therefore a classic self-inflicted wound: the second open erases everything the first one wrote. (The mode that adds instead of wiping is "a" — section 10.3.)

Worked example

Task: save a note the old way, then the better way — and watch "w" wipe. Thinking: the first three lines are the manual open–write–close dance. Then a with block opens the same file in "w" again — blank page — and writes something else. The last line is our borrowed peek (reading proper is next section). Predict what it shows before you run.

10.2

Reading it back — and the invisible \n returns

Read · ~4 minPractice · ~10 min

The problem. Saving is only half a memory. The program that starts tomorrow needs to read what yesterday's program wrote — the peek line we've been borrowing, explained and owned.

The idea, in plain words. Open the file without a mode (reading is the default) and you have three tools:

  • f.read() — the whole file as one string, line breaks and all.
  • f.readlines() — a list with one string per line. A file becomes a Unit 5 list; everything you know about lists applies.
  • for line in f: — loop over the open file itself, one line per lap. No list built, works for any size — the house favourite.

One catch, and it's Unit 8's invisible-character bug wearing a new coat: every line arrives with its \n still attached. Print it and you get the line's own newline plus print's free one — double-spaced output. The cure you already own: line.strip(). And remember Unit 2's law: everything read from a text file is text. The file says 42, the program receives "42" — convert at the door before maths.

Trace it by hand — write, then read in the same program
with open("menu.txt", "w") as f: f.write("idli\n") f.write("dosa\n") with open("menu.txt") as f: for line in f: print(line.strip())

Block 1: the page gets two lines: idli and dosa. Door closes.

Block 2: the same file, reopened for reading. Lap 1: line holds "idli\n" — four letters and the newline. strip() peels it off; print shows a clean idli. Lap 2: same for "dosa\n".

idli dosa

Drop the .strip() and each printed line is followed by a blank one — the file's \n plus print's \n. If your file output ever looks double-spaced, this is why. Every time.

Common confusion

Reading a file doesn't empty it — but an open file keeps a bookmark. After f.read() the bookmark sits at the end, so a second f.read() on the same open file returns "" — looks like your data vanished. It didn't. Reopen the file (a fresh with block) and the bookmark starts at the top again.

Worked example

Task: save a three-line menu, then read it back two ways — as a raw list of lines, and as a clean loop. Thinking: the readlines() print is deliberately ugly: it shows the \n hiding at the end of every item, exactly like Unit 8's invisible characters. The loop with strip() is how you'd actually serve it.

10.3

Appending & guarding — mode "a" and the file that isn't there

Read · ~4 minPractice · ~10 min

The problem. Two gaps remain. First: a diary opened in "w" wipes itself every session — a diary should grow. Second: the very first time your app runs, the save file doesn't exist yet — and opening a missing file for reading crashes the program.

The idea, in plain words. Mode "a" — append — opens the file with the pencil already at the end of the page: old contents untouched, new writes added after them. And if the file doesn't exist, "a" quietly creates it. That's the diary, the visit log, the grocery list across trips.

The missing file is Unit 9's territory. open("scores.txt") with no scores.txt on disk raises FileNotFoundError — a crash report you can now read fluently. But here's the shift in thinking: for a program with saved data, a missing file isn't really an error. It just means first run — nothing saved yet. So real apps wrap the load in Unit 9's guard:

try:
    with open("scores.txt") as f:
        data = f.read()
except FileNotFoundError:
    data = ""   # no saved data yet — start fresh

Load if you can, start fresh if you can't. Your game's save slot, your browser's history, a streak app on day one — this exact pattern, everywhere.

Trace it by hand — the first run of an app
try: with open("scores.txt") as f: print(f.read().strip()) except FileNotFoundError: print("no saved data yet - starting fresh")

Line 2: the runner's disk is clean — no scores.txt anywhere. The open raises FileNotFoundError and the try block stops on the spot.

Line 4: the guard catches exactly that error, and the program carries on:

no saved data yet - starting fresh

On this page the except branch runs every time (clean disk, remember). On your machine, it runs once — the first time — and every later run finds the file and takes the try branch. One program, two lives.

Key idea
A missing save file isn't a failure — it means first run, start fresh. try/except FileNotFoundError turns the crash into that decision. This is THE pattern real apps use to load their data.
Worked example

Task: a visit log that grows — two separate "sessions" append to it, then one read shows everything. Thinking: each with open(..., "a") block is a pretend program-run of its own. The first append even creates the file. Change either "a" to "w" and re-run to watch history get eaten.

Show solution
def bump_streak():
    try:
        with open("streak.txt") as f:
            streak = int(f.read())
    except FileNotFoundError:
        streak = 0
    streak = streak + 1
    with open("streak.txt", "w") as f:

    print(f"Day {streak} of your streak")

bump_streak()

First call: no file, guard fires, streak starts at 0 → Day 1, saved. Second call: the file is found, int("1") → 1 → Day 2. On your machine this program genuinely counts real runs — try it in Colab.

10.4

Structured data — json, the round trip

Read · ~4 minPractice · ~10 min

The problem. One-line-per-task worked for the to-do list. But try saving your settings dict from Unit 6, or a list of scores that must come back as numbers, or a task that contains a comma or a line break — plain text starts to buckle. Worse, the obvious shortcut lies to you: f.write(str([90, 85])) writes something that looks exactly like a list, but what you read back is one string, "[90, 85]" — the structure and the types are gone.

The idea, in plain words. What you need is a text format that both the writer and the reader agree on — an envelope with a standard layout, so the receiving side can unpack it perfectly. Python ships one: json (JavaScript Object Notation — invented elsewhere, adopted everywhere). Two calls do everything:

  • json.dump(value, f) — write a list, dict, string, number or True/False (nested freely) into an open file.
  • value = json.load(f) — read it back, types and structure intact. A list returns as a list, an int as an int.

Put import json at the top of the program (a preview of Unit 11's big idea) and the round trip is yours. The file on disk is still plain text — you could open it in Notepad — it just follows JSON's strict little grammar: double quotes around strings, true/false in lowercase, square brackets and braces where you'd expect.

Trace it by hand — a dict does the round trip
import json settings = {"name": "Adi", "volume": 7} with open("settings.json", "w") as f: json.dump(settings, f) print(open("settings.json").read())

Line 3: an ordinary Unit 6 dict in memory. Lines 4–5: json.dump converts it to JSON text and writes it — one call, formatting handled.

Line 7: the raw file contents, straight off the disk:

{"name": "Adi", "volume": 7}

Readable, almost-Python — note the double quotes (JSON's rule) and the space after each colon and comma (json's standard spacing). json.load would now rebuild the exact dict, 7 arriving as a real int.

Fig. 2 — The round trip. On disk it's text you could edit in Notepad; note JSON's double quotes versus Python's single-quote display of the same list. json.load rebuilds the living value, types intact.
Common confusion

"If the file is still just text, what did json buy me?" The agreement. str(tasks) also writes text, but nothing promises to read it back — it's a photo of your list, not the list. JSON text follows rules both sides know, so json.load can rebuild the real thing: list stays a list, 7 stays an int, a task containing a comma doesn't shatter into two. Photograph vs. flat-packed furniture with the assembly manual included.

Worked example

Task: round-trip a task list, and inspect every stage: the raw file, the rebuilt list, its type, its first item. Thinking: the two prints in the middle look almost identical — the difference in quotes tells you which one is JSON text (double) and which is a living Python list (single). That tiny detail is your debugging compass forever.

10.4 · P2The profile round trip

Save profile to profile.json with json.dump, load it back into a box called loaded, then print the goal line — computing level + 1 from the loaded dict. If the maths works, the int survived the trip.

profile = {"name": "Mira", "level": 3}

10.5

Your build — the to-do list that survives a restart

Read · ~2 minPractice · ~12 min

The arc that began in Unit 5 completes here. One program, two phases. Phase 1 is a session of the to-do app: add tasks, save with json.dump, say goodbye. Then a divider line — --- program restarts --- — and Phase 2 pretends to be tomorrow: memory wiped, list rebuilt from the file, guarded by try/except FileNotFoundError. On your machine these would be two real runs of one program; here we fold them into one so the clean-disk runner can show the whole story. The code is identical either way — that's the point.

10.5 · P1Phase 1 — save on the way out

The session collects two tasks (inputs are fixed). Save tasks to todo.json with json.dump, print the count line using len(), then print the raw file prefixed with On disk: — proof it's really on the page.

Add a task: buy milk Add a task: water plants Saved 2 tasks On disk: ["buy milk", "water plants"]
Show solution

tasks = []
tasks.append(input("Add a task: "))
tasks.append(input("Add a task: "))

    json.dump(tasks, f)

One json.dump call and the whole list — commas, spaces and all — is safely in the box that outlives the program.

10.5 · P2Phase 2 — the restart

Phase 1 is done for you. After the divider, the app "restarts" with wiped memory. Write the load: try to json.load from todo.json; on FileNotFoundError print No saved list - starting fresh and use an empty list. Then print Welcome back! Your tasks: and each task numbered 1., 2. — a counter box does it.

Add a task: buy milk Add a task: water plants Saved 2 tasks. Bye! --- program restarts --- Welcome back! Your tasks: 1. buy milk 2. water plants
Show solution
import json

# ---- PHASE 1: a session of the app ----
tasks = []
tasks.append(input("Add a task: "))
tasks.append(input("Add a task: "))
with open("todo.json", "w") as f:
    json.dump(tasks, f)
print(f"Saved {len(tasks)} tasks. Bye!")

print("--- program restarts ---")

# ---- PHASE 2: tomorrow. Memory is wiped: ----
tasks = []
try:
    with open("todo.json") as f:
        tasks = json.load(f)
except FileNotFoundError:
    print("No saved list - starting fresh")

print("Welcome back! Your tasks:")
n = 1
for t in tasks:
    print(f"{n}. {t}")
    n = n + 1

Save on exit, load-or-fresh on start. Every app you've ever used that "remembered" you was doing some dressed-up version of these fifteen lines.

B4Stretch — the high-score file

Arcade logic: each round, load the record from highscore.txt — or 0 if there's no file yet — then compare. A new record gets saved and announced with New high score: <score>!; anything less prints Score <score> - the record is still <best>. Three rounds run back to back; the middle one must lose.

New high score: 120! Score 90 - the record is still 120 New high score: 150!
Show solution
def play_round(new_score):
    try:
        with open("highscore.txt") as f:
            best = int(f.read())
    except FileNotFoundError:
        best = 0
    if new_score > best:
        with open("highscore.txt", "w") as f:
            f.write(str(new_score))
        print(f"New high score: {new_score}!")
    else:
        print(f"Score {new_score} - the record is still {best}")

play_round(120)
play_round(90)
play_round(150)

Load-or-default, compare, save-if-better — Units 3, 7, 9 and 10 in twelve lines. Round two finds 120 on disk and concedes; round three beats it and the file updates. This is every saved game you've ever played.
