17.1

What for really does

Read · ~4 minPractice · ~10 min

The problem. for item in things: has worked on lists, strings, dictionaries, ranges, files. Five different kinds of thing, one loop. Either for contains five special cases — or there is one agreement that all five signed. Which is it?

The idea, in plain words. One agreement, and it is refreshingly small. Think of a bookshelf and a bookmark.

  • The iterable is the bookshelf — the thing that holds the items. A list, a string, a dictionary. It has no idea where you are.
  • The iterator is a bookmark — a small separate object whose entire job is remembering which item is next.
  • iter(shelf) asks the bookshelf for a fresh bookmark, parked before the first item.
  • next(bookmark) reads out one item and shuffles the bookmark forward one slot.
  • When the bookmark runs off the end, next() raises StopIteration — the polite signal for "shelf's empty, we're done".

And that is the whole of for. When you write for n in nums:, Python calls iter(nums) once to get a bookmark, then calls next() on that bookmark over and over, handing you each value, until StopIteration arrives — at which point the loop ends quietly. The StopIteration never reaches you; for swallows it. That pair of functions is called the iteration protocol, and "protocol" here just means "the agreement everything loopable signed".

Trace it by hand — be the for loop
it = iter([10, 20, 30]) print(next(it)) print(next(it)) print(next(it))

Line 1: the list is the shelf. iter() hands back a bookmark object and stores it in the box it. Nothing has been read yet; the bookmark sits before item one.

Line 2: next(it) reads 10 and moves the bookmark to slot 2. Printed bare — 10, no quotes, because it is the actual value out of the list.

Line 3: reads 20, bookmark moves to slot 3. Line 4: reads 30, bookmark moves past the end.

10 20 30

A fourth next(it) now has nothing to read, so it raises StopIteration. In a real for loop you would never see that — the loop catches it and stops. Hand-driving like this, you see it raw. That is the entire mechanism you have been using for fourteen units.

Fig. 1 — The shelf is unchanged throughout; only the bookmark's position changes. Grey items are behind the bookmark — read already, and unreachable from this bookmark forever.
Key idea
for is not magic and not a special case per type. It calls iter() once to get an iterator, then next() repeatedly until StopIteration. Everything loopable in Python — every single thing — plays exactly this game.
Worked example

Task: drive a list by hand, the way a for loop would. Thinking: one iter() to get the bookmark, then one next() per item. Watch the values come out bare — these are the real list values, not text.

17.2

Iterators are one-shot

Read · ~3 minPractice · ~10 min

The problem. You loop over something, everything is fine. You loop over the same thing again, five lines later — and this time it prints nothing at all. No error, no warning, no crash. Just silence. This bug has cost more evenings than it has any right to.

The idea, in plain words. The bookmark only moves forward. It has no rewind button, and it never gets one. Once a bookmark is sitting past the last item, every further next() raises StopIteration immediately — so a for loop over an exhausted iterator does zero rounds and ends without complaint. An iterator is one-shot: use it, and it is spent.

Lists don't behave this way, and now you can say exactly why. A list is a bookshelf, not a bookmark. Every for loop over a list starts by calling iter(the_list), which mints a brand-new bookmark at position zero. Loop the same list ten times and you get ten fresh bookmarks. Loop the same iterator twice and the second loop finds a bookmark that has already run out of shelf.

Trace it by hand — the vanishing second loop
it = iter([1, 2, 3]) for n in it: print(n) for n in it: print("again", n) print("done")

Loop 1: for calls iter(it) — and an iterator asked for an iterator hands back itself, the same bookmark. Then three next() calls print 1, 2, 3, and the fourth raises StopIteration. Loop ends. The bookmark is now past the end.

Loop 2: for calls iter(it) again, gets the same exhausted bookmark, calls next() once — StopIteration straight away. Zero rounds. The body never runs. Not one again line appears.

1 2 3 done

Nothing went wrong. Nothing was reported. The second loop simply had nothing left to do, and Python saw no reason to mention it.

Common confusion

This is the one to carry out of the unit. An empty second loop is not a bug in your loop — it is proof that you were looping over an iterator, not a collection. The symptom is always the same: the data "vanishes" after first use. It shows up most often with zip() and enumerate() (next section — both hand back iterators), and with sum(), max() or list(), which quietly drain an iterator to the last item as part of doing their job. If you need the values twice, either build a real list once with list(...) and loop over that, or call iter() again on the original shelf for a fresh bookmark. What you must never do is expect a spent bookmark to rewind.

Worked example

Task: show the same three values surviving a second pass — and then not surviving one. Thinking: loop the list twice (two fresh bookmarks, works), then loop an iterator twice (one spent bookmark, silence). Same data, opposite outcomes.

17.3

enumerate & zip, demystified

Read · ~4 minPractice · ~10 min

The problem. Since Unit 5 you have been hand-building position numbers: a count box, count = count + 1 at the bottom of the loop, and a count + 1 in the f-string because humans start lists at one and Python starts at zero. Three lines of ceremony to print "1. idli". Python has had a one-word answer the whole time — and now you have the background to understand what it actually hands back.

The idea, in plain words. Two built-ins, both of which return iterators — bookmarks, not shelves.

  • enumerate(items) walks items and hands out a pair each time: the position and the item. enumerate(menu) gives (0, 'idli'), then (1, 'dosa'), and so on. Add start=1 — enumerate(menu, start=1) — and the numbering begins at one. That is the counter box you have been maintaining by hand for twelve units, retired in a single argument.
  • zip(a, b) walks two shelves side by side and hands out a pair from each round: ('Ada', 90), then ('Ben', 85). It stops at the shortest — the moment either shelf runs out, zip is done, and the leftovers on the longer one are silently ignored. Give it three lists and it hands out triples; the shortest rule still holds.

Both are lazy: they compute nothing until something asks for the next item. That is a gift on huge data — you never build a giant list you only walk once — and it is exactly the trap 17.2 warned about. If you want to see what one contains, wrap it in list(...): list(enumerate(menu)) shows you the pairs. Printing the raw enumerate object shows you nothing useful, just a type name and a memory address — the bookmark, not the books.

Trace it by hand — looking inside the lazy ones
menu = ["idli", "dosa", "vada"] print(list(enumerate(menu))) print(list(enumerate(menu, start=1))) for n, item in enumerate(menu, start=1): print(f"{n}. {item}")

Line 2: enumerate returns a bookmark; list() drains it and collects every pair it produced. Pairs print in round brackets, and the text keeps its quotes because you are looking at the contents of a list, not at printed text.

Line 3: the same walk, numbered from one instead of zero.

Line 4: the loop takes each pair and unpacks it into two boxes at once — n gets the number, item gets the string — which is why for n, item in ... has two names before the in.

[(0, 'idli'), (1, 'dosa'), (2, 'vada')] [(1, 'idli'), (2, 'dosa'), (3, 'vada')] 1. idli 2. dosa 3. vada
Common confusion

enumerate(menu) is not a list of pairs — it is a bookmark that will produce pairs on demand. Two consequences bite beginners. First, you cannot index it: enumerate(menu)[0] is a TypeError, because a bookmark has no slots to index. Second, and worse, storing it in a box does not freeze the data: pairs = zip(names, scores) followed by list(pairs) and then a for over pairs gives you a full list and then absolute silence — the classic vanishing bug from 17.2, wearing a different hat. If you need the values more than once, say pairs = list(zip(names, scores)) and keep a real shelf.

Worked example

Task: a numbered menu and a paired scoreboard, the grown-up way. Thinking: start=1 removes the counter box entirely; zip removes the index arithmetic that used to pair two lists. Compare this to how you would have written it in Unit 8.

Two bookmarks stacked: zip produces pairs, enumerate numbers whatever it is given. The inner brackets tell Python "this second thing is itself a pair — take it apart too".

17.4

Writing your own — the Countdown class

Read · ~4 minPractice · ~10 min

The problem. Everything so far has been Python's own objects playing Python's own game. But you have spent four units building classes. If the iteration protocol really is just an agreement — two functions and a signal — then there is nothing stopping your class from signing it. And if it does, for will loop over your object without being told a thing about it.

The idea, in plain words. Unit 15's lesson was that built-in functions are polite knockers: len(x) knocks on x.__len__(), print(x) knocks on x.__str__(). Two more knocks complete the picture:

  • iter(x) knocks on x.__iter__() — "give me a bookmark". Your object answers return self: I am my own bookmark, I'll keep my own place.
  • next(x) knocks on x.__next__() — "one item, please". Your method returns the next value, updating whatever it stores to remember where it is.
  • When there is nothing left, __next__ says raise StopIteration — the agreed way to say "shelf's empty". raise means "signal this condition"; the for loop hears it and stops.

Define those two methods and your class is, as far as Python is concerned, a first-class citizen of the loop. Not simulated. Not special-cased. The same machinery that walks lists and files and dictionaries will walk your object, because it is asking the same two questions and your object is answering them.

Trace it by hand — a class that counts down
class Countdown: def __init__(self, start): self.n = start def __iter__(self): return self def __next__(self): if self.n <= 0: raise StopIteration value = self.n self.n -= 1 return value for n in Countdown(3): print(n) print("Liftoff!")

The cookie: Countdown(3) runs __init__ and bakes one object whose self.n holds 3. That box is the object's memory of where the bookmark sits.

The loop starts: for calls iter() on it, which knocks on __iter__, which returns self — the object hands back itself as its own bookmark.

Round 1: for calls next() → __next__ runs. self.n is 3, not ≤ 0, so: remember 3 in value, drop self.n to 2, return 3. Printed: 3.

Rounds 2 and 3: the same, returning 2 then 1, leaving self.n at 0.

Round 4: self.n is 0, so raise StopIteration. The for loop hears the signal, stops without fuss, and execution moves to the line after the loop.

3 2 1 Liftoff!
Fig. 2 — One knock on __iter__, then a knock on __next__ per round. The dashed arrow is the exit: StopIteration travels back up to the loop, which absorbs it and moves on.
Key idea
Define __iter__ (return the bookmark — usually self) and __next__ (return the next value, or raise StopIteration), and your own class plugs directly into Python's for loop. This is what the last four units were building towards: not a class that merely holds data, but a class the language itself knows how to use.
Common confusion

raise StopIteration looks alarming — it has the shape of an error. It isn't one. It is a message with a fixed meaning, and the for loop is its intended recipient; nobody upstream ever hears it. The other half of the confusion is __iter__ returning self. Why would an object hand back itself? Because for a class like this the shelf and the bookmark are the same object — self.n is the position. That is also why a Countdown is one-shot exactly like the iterators in 17.2: loop it twice and the second loop gets nothing, because self.n is already 0.

Worked example

Task: the full Countdown, running under a plain for loop. Thinking: __init__ sets the starting position; __iter__ hands back the bookmark; __next__ checks whether anything is left, returns the current value, and steps down. Read it twice — every line of 17.5 is built from this shape.

17.4 · P1The missing knock

This class has __init__ and __next__ but no __iter__, so for refuses it: TypeError: 'Countdown' object is not iterable. Add the two lines that answer the first knock.

3 2 1 Liftoff!
Show solution
    def __iter__(self):
        return self

Insert it between __init__ and __next__, indented one level inside the class. Without it, iter() knocks and nobody answers — and "not iterable" is Python's way of saying exactly that.

17.4 · P2The missing brakes

Here __next__ never says stop, so this countdown sails past zero into the negatives forever. Add the two lines that raise StopIteration when there is nothing left, so it halts at 1.

3 2 1 Liftoff!
Show solution
    def __next__(self):
        if self.n <= 0:
            raise StopIteration
        value = self.n
        self.n -= 1
        return value

The guard goes first, before anything is read or changed. An iterator with no StopIteration is an endless loop with extra steps — which, as Unit 18 will show, is occasionally exactly what you want.

The first list() drove self.n down to 0; the second one asks for an item, hits the guard immediately, and collects nothing. Your class inherited the one-shot behaviour of 17.2 for free — because it works the same way underneath. Want a second countdown? Build a second object: Countdown(3) again.

17.5

Your build — three iterators of your own

Read · ~2 minPractice · ~12 min

Three programs, each one a class that Python's own machinery agrees to walk. First Countdown driven three different ways — proof that a for loop, a hand-driven next() and a list() are three doors into the same room. Then two classes written from scratch, the same shape with different arithmetic inside. Copy the Countdown skeleton and change what __next__ does; that is genuinely all there is to it.

17.5 · P1Countdown, three ways

The class is written for you. Below it, drive it three ways: a for loop over Countdown(3); a fresh Countdown(2) hand-driven with two next() calls; and list(Countdown(4)). Each way needs its own object — remember 17.4's P3.

3 2 1 2 1 [4, 3, 2, 1]
Show solution
for n in Countdown(3):
    print(n)

it = Countdown(2)
print(next(it))
print(next(it))

print(list(Countdown(4)))

Three doors, one room. The for loop and list() both do the iter()-then-next() dance for you; the middle block is you doing it by hand. Your class cannot tell the difference, and doesn't need to.

17.5 · P2Evens(limit)

Write an Evens class that produces the even numbers from 2 up to and including limit. Same skeleton as Countdown: __init__ remembers where you are, __iter__ returns self, __next__ steps by 2 and raises StopIteration once you pass the limit.

2 4 6 [2, 4, 6, 8, 10]
Show solution
class Evens:
    def __init__(self, limit):
        self.limit = limit
        self.current = 0

    def __iter__(self):
        return self

    def __next__(self):
        self.current += 2
        if self.current > self.limit:
            raise StopIteration
        return self.current

for n in Evens(6):
    print(n)
print(list(Evens(10)))

Starting current at 0 and adding 2 before the check is the tidiest version: the first call returns 2, and the moment the step would overshoot the limit, the guard fires. Two separate objects here, so both drives start fresh.

17.5 · P3Stretch — Repeat(word, times)

Write a Repeat class that hands out the same word a fixed number of times, then stops. Two things to remember in __init__: the word, and how many hand-outs are left. Note that the value returned never changes — only the count does.

hi hi hi
Show solution
class Repeat:
    def __init__(self, word, times):
        self.word = word
        self.left = times

    def __iter__(self):
        return self

    def __next__(self):
        if self.left <= 0:
            raise StopIteration
        self.left -= 1
        return self.word

for w in Repeat("hi", 3):
    print(w)

The countdown moved into self.left, out of sight of whoever is looping — they just receive three his. An iterator's internal bookkeeping is nobody else's business, which is Unit 16's encapsulation lesson showing up again.

B2The numbered menu, with an order

Print the menu numbered from 1 using enumerate, then ask Pick a number: and report the chosen dish. Mind the off-by-one: the human types 2, the list stores that dish at index 1. Input is fixed to 2.

1. idli 2. dosa 3. vada Pick a number: 2 You picked: dosa

B3The report card

Three parallel lists, one report. zip takes as many lists as you give it — hand it all three and unpack three names in the loop header.

Ada: 91 (A) Ben: 78 (C) Cara: 85 (B)
Show solution
names = ["Ada", "Ben", "Cara"]
scores = [91, 78, 85]

    print(f"{name}: {score} ({grade})")

Parallel lists plus zip is the honest, readable way to walk related data — no index arithmetic, no chance of reading row 3 of one list against row 4 of another.

B4Stretch — SkipOdd

Write a SkipOdd class that stores a list and hands out only its even numbers. The twist: __next__ may have to skip several items before it finds one worth returning — so it needs a small loop inside, walking forward until it finds an even number or runs off the end.

[4, 10, 12] 2 8
Show solution
class SkipOdd:
    def __init__(self, numbers):
        self.numbers = numbers
        self.i = 0

    def __iter__(self):
        return self

    def __next__(self):
        while self.i < len(self.numbers):
            value = self.numbers[self.i]
            self.i += 1
            if value % 2 == 0:
                return value
        raise StopIteration

The while walks forward; a return from inside it ends the method immediately, with self.i already parked on the next candidate. Only when the walk runs out of shelf does the raise line get reached. This is the shape of every filtering iterator ever written — and Unit 18 collapses the whole class into four lines.
