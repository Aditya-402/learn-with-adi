9.1

Reading a traceback, properly

Read · ~4 minPractice · ~10 min

The problem. In Unit 1 your programs were three lines long, so the error reports were short and the advice was simple: read the last line first. But your programs now have functions calling functions. When something breaks three layers deep, the report is a wall of text a dozen lines tall — and most beginners' eyes glaze over at exactly the moment the machine is being most helpful.

The idea, in plain words. An error report — Python calls it a traceback — is not a scolding. It's the machine holding up its end of the conversation: the kitchen helper handing back the recipe with a bookmark at the exact step it got stuck, plus a note listing every recipe card it was in the middle of following when it happened. The report has a fixed shape:

  • The last line names what went wrong: the error's type and a one-sentence reason. Still read this first — that habit survives intact.
  • The File …, line …, in … lines above it are the call chain — the trail of function calls that led to the crash. The very first line of the report tells you how to read them: most recent call last. Oldest call at the top, the call that actually crashed at the bottom.
  • So the full reading order is: last line first (the what), then the bottom-most File line (the where), then walk upward to see how the program got there (the how).
Trace it by hand — a crash three layers deep
def share_per_person(total, people): return total / people def print_share(total, people): each = share_per_person(total, people) print("Each pays:", each) print_share("900", 3)

Last line of the file: print_share is called with "900" — a string. Someone forgot to convert at the door.

Inside print_share: the string travels on, into share_per_person.

Inside share_per_person: "900" / 3 — dividing text by a number. Here, and only here, Python must give up:

Traceback (most recent call last): File "bill.py", line 8, in <module> print_share("900", 3) File "bill.py", line 5, in print_share each = share_per_person(total, people) File "bill.py", line 2, in share_per_person return total / people TypeError: unsupported operand type(s) for /: 'str' and 'int'

Last line: a TypeError — text divided by a number. Bottom frame: the crash happened in share_per_person, line 2. Walk up: it was called by print_share, which was called at the top level — where the "900" entered. The crash site is line 2; the culprit is line 8.

Fig. 1 — Anatomy of a traceback. Three moves, always the same: last line for the what, bottom frame for the where, then upward for the how. The wall of text becomes a breadcrumb trail.
Common confusion

The crash site is not always the culprit. The bottom frame shows where Python gave up — but the bad value often entered several calls earlier. In the trace above, line 2 crashed, yet line 2 is innocent; the "900" snuck in at the top-level call. Fix where the bad value entered, not where it finally exploded — that's why you walk the chain.

Key idea
A traceback reads bottom-up: last line = what went wrong, bottom File line = where it died, the frames above = the journey that got it there. Newest call last — Python says so in its opening line.
Worked example

Task: run the crashing bill-splitter and read its report against Fig. 1 — out loud if nobody's watching. Thinking: before running, predict all three answers: what will the last line say? Which function will the bottom frame name? Where did the bad value enter? (The in-page runner's report may add a line or two of its own machinery — the shape is always the same: frames oldest-to-newest, error last.)

9.2

The rogues' gallery — five errors you'll meet weekly

Read · ~4 minPractice · ~10 min

The problem. Reading the report's shape is half the skill; the other half is recognising the name on the last line. Five names cover the overwhelming majority of beginner crashes — meet them deliberately here, in a safe room, and they'll never ambush you again.

The idea, in plain words. Each error name states exactly which promise got broken:

the roguethe broken promiseclassic trigger
NameErrora label that doesn't exist — typo, or never createdprint(mesage)
TypeErrorright values, wrong types mixed"7" + 7
ValueErrorright type, unusable valueint("hello")
IndexErrora list position that doesn't existmenu[3] of 3 items
KeyErrora dictionary key that doesn't existprices["Dosa"]

One of these is new: ValueError. Hand int() a string — perfectly legal, that's its whole job — but a string with no number in it, like "hello", and the type was fine while the value was hopeless. That's the distinction the next confusion box nails down, and it matters enormously in 9.3: users type "hello" at number prompts all the time.

Trace it by hand — the newest rogue
text = "hello" number = int(text) print(number)

Line 1: box text holds the string "hello".

Line 2: int() reads the box. A string is exactly what it accepts — no type complaint. But it scans the characters for a number and finds… greetings. Nothing to convert. It gives up:

Traceback (most recent call last): File "rogue.py", line 2, in <module> number = int(text) ValueError: invalid literal for int() with base 10: 'hello'

Line 3 never runs. Programs die mid-flight — everything before the crash happened; nothing after it does.

Common confusion

ValueError vs TypeError — they sound interchangeable and aren't. "7" + 7 is a TypeError: the kinds of things don't combine, whatever their contents. int("hello") is a ValueError: the kind is fine (int() happily takes strings — int("42") works), but this particular content is unusable. Wrong category of thing → TypeError. Right category, hopeless contents → ValueError.

Worked example

Task: watch int() succeed twice and fail once, and read the ValueError report closely — it quotes the offending string back at you. Thinking: predict which of the three lines survives before you run. Remember: the program dies at the first failure.

9.3

try / except — the safety net under the risky line

Read · ~4 minPractice · ~10 min

The problem. You can read crash reports now — but your users can't, and shouldn't have to. A user typing twenty at an age prompt is being human, not hostile; rewarding them with a ten-line traceback and a dead program is bad manners. Crashes are for you at your desk. Users deserve a friendly sentence and a second chance.

The idea, in plain words. Tell the kitchen helper in advance: attempt this step, and if it fails in this particular way, don't fling the pan down — do plan B instead. That's try/except:

try:
    age = int(text)    # the risky line
except ValueError:
    print("Numbers only, please.")

If the risky line succeeds, the except block is skipped entirely. If it raises a ValueError — and only that — the rest of the try block is abandoned, the except block runs instead, and then the program carries on. No traceback, no death. Two rules make it professional: guard the risky line, not your whole program; and name the specific error you expect. And here's Unit 4's promised payoff — wrap the guarded attempt in while True:, break on success, complain on failure, and you get the politest pattern in programming: keep asking until a number arrives.

Trace it by hand — the net catches
text = input("Age? ") # user types: twenty try: age = int(text) print("Stored!") except ValueError: print("That wasn't a number.") print("Program still alive.")

Line 1: box text holds "twenty".

Line 3: int("twenty") raises ValueError — but this time there's a net. print("Stored!") is abandoned, execution jumps to the except block.

Line 6: the friendly message prints. Line 7: life goes on:

Age? twenty That wasn't a number. Program still alive.
Fig. 2 — The two paths through try/except. Success takes the high road and never touches the except block; the named error takes the detour — and both roads lead on. Nobody dies.
Common confusion

A bare except: — no error name — catches everything, and that's a trap, not a convenience. Typo a label inside the try block and the NameError also gets caught, so your program calmly prints "Numbers only, please" while the real bug — your typo — hides forever. Name the error you expect (except ValueError:) and let the ones you don't expect crash loudly. During building, a loud crash is a gift.

Worked example

Task: the safe age-asker — the guarded version of Unit 2's birthday bot. Input is fixed to twenty; run it, then trace the path it took through Fig. 2. Thinking: the only risky line is the conversion, so only the conversion (and what depends on it) lives inside try.

9.3 · P1Guard the ticket booth

This program dies when someone types two instead of 2. Add a try/except ValueError so it answers politely instead. Input fixed to two.

How many tickets? two Numbers only, please.
Show solution
tickets = input("How many tickets? ")
try:
    count = int(tickets)
    print(f"Booking {count} tickets")
except ValueError:
    print("Numbers only, please.")

The conversion and the print that depends on it go inside try; the plan B goes in except ValueError. The input line itself isn't risky — it stays outside.

9.3 · P2Keep asking — the retry pattern

Unit 4's payoff. Finish the loop: try the conversion; if it works, break out; if not, complain and let the loop ask again. Inputs fixed: first abc, then 42.

Age? abc Numbers only, try again. Age? 42 Next year: 43
Show solution
while True:
    text = input("Age? ")
    try:
        age = int(text)
        break
    except ValueError:
        print("Numbers only, try again.")

print(f"Next year: {age + 1}")

Round one: "abc" fails, the except complains, the loop swings back. Round two: "42" converts, break escapes. This while-try-break trio guards nearly every input prompt in real programs — you'll write it for the rest of your life.

Predict what this prints, then run. The text is a perfectly good number — so why the complaint? Then change except: to except ValueError:, run again, and watch the honest report appear.

Narrow the net to except ValueError: and the NameError crashes loudly, pointing straight at the typo. This is the confusion box made flesh — catch what you expect, nothing more.

9.4

Debugging by printing — and raising your own

Read · ~4 minPractice · ~10 min

The problem. Not every bug announces itself. The nastiest ones produce no traceback at all — the program runs to the end, smiles, and prints the wrong number. No last line to read, no chain to walk. How do you hunt a bug that won't confess?

The idea, in plain words. Make memory visible. Since Unit 2 you've traced programs by hand, drawing the boxes after every line — a debug print is the machine doing that trace for you, live, from inside the running program. Python even has a gift for it: put = after a name inside an f-string — f"{total=}" — and it prints the label and the contents: total=240. Drop print(f"DEBUG: {total=}") at a checkpoint and compare what memory actually holds against what your hand-trace says it should hold. The bug lives between the last matching print and the first surprising one. When the hunt is over, delete the DEBUG lines — they're scaffolding, not furniture.

And the reverse skill: sometimes you know a value is wrong before Python does. An age of -3 is a perfectly legal int — Python has no objection — but it breaks your rules. raise ValueError("age cannot be negative") lets you throw the flag yourself: the function stops on the spot, and the report's last line carries your sentence, exactly where you've learned to look. Errors are the machine holding up its end of the conversation — raise is how your own functions join in.

Trace it by hand — raise in action
def book(seats): if seats > 4: raise ValueError("max 4 seats per booking") print(f"Booked {seats} seats") book(2) book(6)

Call book(2): the condition is False, the raise never fires, the print runs.

Call book(6): condition True — raise builds a ValueError carrying your message and stops the function right there. Nothing catches it, so it climbs out and the program dies with your words on the last line:

Booked 2 seats Traceback (most recent call last): ... ValueError: max 4 seats per booking

Your own errors read exactly like Python's — and they're catchable with the same except ValueError: net, which the problem bank will use.

Key idea
print(f"DEBUG: {box=}") shows the true state of memory mid-flight — the hand-trace, automated. raise ValueError("…") enforces your rules with the same machinery Python uses for its own.
Worked example

Task: watch the {name=} trick narrate a small computation. Thinking: the DEBUG line prints both labels with their contents in one go — this is the state-of-memory diagram from Unit 2, drawn by the machine. In a finished program you'd delete it; here it is the lesson.

9.5

Your build — bulletproof the to-do app

Read · ~2 minPractice · ~12 min

Unit 5 built the to-do list; Unit 7 rebuilt it from functions. It works beautifully — for polite users. (We've tightened the menu prompt a little along the way — the functions are Unit 7's.) Today we hire a rude one. Three ways a real person will break it: typing a menu choice that doesn't exist, removing a task that isn't there (that's .remove() raising a rogue you now know), and adding a task with no name at all. A program that only survives polite users isn't finished — armour all three paths so every failure gets a friendly sentence and the program marches on.

9.5 · P1Stage 1 — armour the remove

A surprise: tasks.remove(name) on a missing task raises ValueError — Python reuses the rogues you already know. Wrap the risky line in try/except ValueError so the second call answers politely instead of crashing, and the final print still runs.

Removed: call home Not on the list: walk dog ['buy milk']
Show solution
def remove_task(tasks, name):
    try:
        tasks.remove(name)
        print("Removed:", name)
    except ValueError:
        print("Not on the list:", name)

tasks = ["buy milk", "call home"]
remove_task(tasks, "call home")
remove_task(tasks, "walk dog")
print(tasks)

The net lives inside the function, so every caller is protected forever. And note the last line still prints the list with quotes — Python's way of showing you the strings inside.

9.5 · P2Stage 2 — refuse nonsense politely

Two more armour plates: in add_task, refuse an empty name with A task needs a name. — and in the menu, answer unknown choices with Unknown choice. Try add, show or quit. instead of silence. The scripted session presses both bruises, then behaves.

Show solution
def add_task(tasks, name):
    if name == "":
        print("A task needs a name.")
    else:
        tasks.append(name)
        print("Added:", name)

def show_tasks(tasks):
    for t in tasks:
        print("-", t)

tasks = []
while True:
    choice = input("add / show / quit? ")
    if choice == "add":
        add_task(tasks, input("Task name? "))
    elif choice == "show":
        show_tasks(tasks)
    elif choice == "quit":
        print("Bye!")
        break
    else:
        print("Unknown choice. Try add, show or quit.")

Notice: neither guard needed try/except. Bulletproofing is mostly plain if/else — you reach for the net only when the failure arrives as an error. Checking beats catching when a simple question ("is it empty?") does the job.

Everything together: the menu grows remove (with P1's armoured remove_task), and keeps P2's two guards. The scripted rude user hits all three failure paths — unknown choice, remove a missing task, empty name — then finally behaves. Your app must survive all of it.

This app now shrugs off anything a keyboard can throw at it — which matters, because in Unit 10 it starts keeping your real list.

9.6

Problem bank — everything at once

Practice · ~12 min

The mixed set: nets, raises, rogues and debug prints — plus a sixth rogue making its entrance. In order; they get meaner.

B1Safe division — meet the sixth rogue

Dividing by zero raises ZeroDivisionError — the sixth member of the gallery. Write safe_divide(a, b) that prints a / b = result normally, but Cannot divide a by zero. when b is 0. Call it once directly, then once with two asked-for numbers. Inputs fixed: 10, then 0.

9 / 4 = 2.25 Numerator? 10 Denominator? 0 Cannot divide 10 by zero.
Show solution
def safe_divide(a, b):
    try:
        print(f"{a} / {b} = {a / b}")
    except ZeroDivisionError:
        print(f"Cannot divide {a} by zero.")

safe_divide(9, 4)
a = int(input("Numerator? "))
b = int(input("Denominator? "))
safe_divide(a, b)

Same net, new rogue: name the error, catch exactly it. 9 / 4 is 2.25 — the honest float, straight from Unit 2.

B2Safe lookup, two ways

A missing dictionary key, handled two ways: once with .get() and a default, once with try/except KeyError. Both should print not on the menu for "vada". Rule of thumb: reach for .get() when a stand-in value is all you need; reach for the net when a missing key should trigger different actions.

not on the menu not on the menu
Show solution
prices = {"idli": 10, "dosa": 30}
# way 1: .get() with a default
print(prices.get("vada", "not on the menu"))

# way 2: try / except KeyError
try:
    print(prices["vada"])
except KeyError:
    print("not on the menu")

Identical output, different philosophies. .get() quietly substitutes a value — one line, perfect for defaults. The net version lets the except block do things — log, retry, ask the user. Simple default → get; different behaviour → try/except.

B3Raise at the gate, catch at the door

Both ends of the conversation in one program: check_age(age) raises ValueError("age cannot be negative") for negatives and prints Age N accepted otherwise. The loop calls it for each age, catching the ValueError and printing Rejected: N — so the bad age in the middle can't stop the good one after it.

Age 25 accepted Rejected: -3 Age 40 accepted
Show solution
def check_age(age):
    if age < 0:
        raise ValueError("age cannot be negative")
    print(f"Age {age} accepted")

for age in [25, -3, 40]:
    try:
        check_age(age)
    except ValueError:
        print(f"Rejected: {age}")

The function guards the rule; the caller decides what a violation means here (skip and continue). That split — raise where the rule lives, catch where the decision lives — is how grown-up programs are organised.

B4Stretch — the messy data sweep

Real data arrives dirty. Split the string on commas (Unit 8), attempt to convert each piece inside a try; sum the ones that convert, count the ones that don't. One net inside one loop cleans the whole feed.

Sum: 28 Rejected: 1
Show solution
data = "12,7,notanumber,9"
total = 0
rejects = 0
for piece in data.split(","):
    try:
        total = total + int(piece)
    except ValueError:
        rejects = rejects + 1

print(f"Sum: {total}")
print(f"Rejected: {rejects}")

12 + 7 + 9 = 28, one reject. The net sits inside the loop, so one bad piece costs one iteration, never the whole run. This exact shape — try each item, tally the failures — cleans real-world data files every day, and you'll meet it again the moment files arrive in Unit 10.
