15.1

Is-a: inheriting — a class built on another class

Read · ~4 minPractice · ~10 min

The problem. Your BankAccount works. Now the bank wants savings accounts. A savings account is a bank account — same owner, same balance, same deposit, same withdraw, same report — plus an interest rate. Copying the whole class and pasting one extra line into it is how codebases rot: fix a bug in withdraw and you now have to remember to fix it twice.

The idea, in plain words. Think of a family recipe book. The house dal has a full page: soak, boil, temper, salt. The restaurant dal doesn't repeat any of that — its page says "same as the house dal, plus a spoon of cream at the end." Nobody rewrites the boiling instructions, and when the house dal improves, the restaurant dal improves with it, free.

Python spells that one line:

class SavingsAccount(BankAccount):

The name in the brackets is the parent class (also called the base or superclass); the new one is the child (subclass). And that's it — SavingsAccount now has __init__, deposit, withdraw and report, without a single line copied. Even if its whole body is the word pass, objects made from it can do everything a BankAccount can.

One useful question comes with the family: is this object one of those? isinstance(s, SavingsAccount) answers True — and so does isinstance(s, BankAccount), because a savings account genuinely is a bank account. Inheritance is a promise, not a copy.

Trace it by hand — the free methods
class SavingsAccount(BankAccount): pass s = SavingsAccount("Meera", 500) s.deposit(250) s.report()

Lines 1–2: a new class is born whose only content is "same as BankAccount". Zero methods written.

Line 4: Python needs SavingsAccount.__init__. Not found in the child, so it walks one step up to BankAccount and finds it there. That parent __init__ runs, with self being our new savings object: it gets a box owner holding "Meera" and a box balance holding 500.

Line 5: same walk — deposit isn't in the child, is in the parent. It runs, balance becomes 750.

Line 6: report, same walk again:

Meera: 750.00

Three method calls, one line of class code. That walk — child first, then parent — is the only mechanism in this section, and it explains everything that follows.

Fig. 1 — The lookup walk. Every attribute and method call starts at the object's own class and climbs the arrow until it finds a match. Keep this picture: the next three sections are all consequences of it.
Key idea
class Child(Parent): means "everything the parent can do, the child can do". Python looks for a method in the child's class first, then climbs to the parent. Nothing is copied — the child points at the parent.
Worked example

Task: give the bank a savings account with no new code at all, and prove it really is a bank account. Thinking: write the parent once (this is Unit 13's class, unchanged), then one class line with pass inside. Then use it as if it were fully written — because it is.

15.1 · P3Stretch — a method only the child has

A child can add methods of its own. Give SavingsAccount a method double() that doubles the balance by calling the inherited deposit with the current balance — no arithmetic of your own, and no touching self.balance directly.

Nina: 800.00
Show solution
class SavingsAccount(BankAccount):

        self.deposit(self.balance)

Inside a child method, self.deposit(...) takes the same walk as everywhere else: not in the child, found in the parent. Children use their parents' methods exactly the way outsiders do.

15.2

Extending with super() — "same as the parent, plus…"

Read · ~3 minPractice · ~10 min

The problem. A savings account needs an interest rate — a box the parent knows nothing about. So the child needs its own __init__. But the moment you write one, the parent's __init__ stops running: the walk finds the child's version first and stops there. Do you now re-type self.owner = owner and self.balance = balance? That's copying again, and copying was the disease.

The idea, in plain words. Back to the recipe card: "same as the house dal, plus a spoon of cream." The word "same as" is a real instruction — it tells the cook to go and follow the other page first. Python's word for it is super(). Read super() as "my parent", so super().__init__(owner, balance) means run my parent's setup with these values. Then, on the next line, you add the cream.

def __init__(self, owner, balance, rate): super().__init__(owner, balance) self.rate = rate

Three lines, and the child now has all three boxes: owner and balance filled by the parent, rate filled by the child. The order matters in spirit — parent's setup first, your additions after — and note you don't pass self to super().__init__; Python already knows which object is being built.

With rate in place, a genuinely new method becomes possible — one the parent could never have written:

def add_interest(self): self.balance = self.balance + self.balance * self.rate / 100

Trace it by hand — two __init__ methods, one object
s = SavingsAccount("Meera", 1000, 5) s.add_interest() s.report()

Line 1: Python makes one empty object and calls the child's __init__ with self = that object, owner = "Meera", balance = 1000, rate = 5.

Inside it, line A: super().__init__(owner, balance) hands control to the parent's __init__ — same object, no second object is created. It gives the object a box owner ("Meera") and a box balance (1000), then returns.

Inside it, line B: back in the child, self.rate = rate adds the third box: 5. One object, three boxes, two classes cooperating.

Line 2: add_interest — found in the child. 1000 × 5 / 100 = 50.0, so balance becomes 1050.0.

Line 3: report — not in the child, found in the parent, and it reads the same owner and balance boxes it always did:

Meera: 1050.00
Common confusion

Forget the super().__init__(...) line and Python does not warn you. The object is built with only the boxes your child __init__ set — no owner, no balance. The complaint arrives later, from somewhere innocent-looking: AttributeError: 'SavingsAccount' object has no attribute 'owner'. Decode it as usual — last line first, then read it literally: this object has no box called owner. It never got one, because nobody ran the code that creates it. Whenever a child class raises "has no attribute" for something the parent obviously sets, the missing super().__init__ is the culprit — every time.

Worked example

Task: a savings account that knows its rate and can pay interest. Thinking: the child's __init__ takes one extra parameter, hands the two familiar ones up to the parent, and keeps the new one for itself. Everything else stays inherited.

15.2 · P2Decode the AttributeError

Run this as-is first and read the last line of the report. It complains about owner — but the parent clearly sets owner, so what went wrong? Fix it with one added line.

Dev: 900.00
Show solution
class SavingsAccount(BankAccount):
    def __init__(self, owner, balance, rate):

Writing a child __init__ replaces the parent's — the parent's never runs unless you say so. The values arrived in the child's parameters and then were thrown away; super().__init__ is what passes them on.

15.3

Overriding & polymorphism — in plain words

Read · ~4 minPractice · ~10 min

The problem. Premium customers are allowed a small overdraft — they may go up to 500 below zero before the bank objects. The inherited withdraw refuses that flatly. This isn't a new ability to add; it's an existing one that must behave differently for this kind of account.

The idea, in plain words. Write a method in the child with the same name as one in the parent, and the child's version wins. You already know why: the lookup walk starts at the child and stops at the first match. That's called overriding — the recipe card that says "ignore the parent's step 4, do this instead". The parent's version isn't deleted or damaged; it's simply never reached for this kind of object (and super().withdraw(...) can still reach it deliberately, if you want the old behaviour plus something).

Now the payoff, and it is the reason this whole unit exists. Give three account types their own report, put one of each in a list, and write a single loop:

for a in [account, savings, premium]: a.report()

One line of calling code. Three different outputs. The loop never asks what kind of account it's holding — it just says report(), and each object answers in its own way, because each object's lookup walk starts in its own class. Nothing in the loop changes when you add a fourth account type tomorrow.

That loop is polymorphism. The word is Greek for "many shapes", it sounds like a barrier, and it means exactly this and nothing more: the same call, sent to different objects, does the right different thing.

Trace it by hand — who answers report()?
account = BankAccount("Ravi", 1000) # report → parent's version savings = SavingsAccount("Meera", 2000, 5) # report → its own premium = PremiumAccount("Zoya", 300) # report → its own for a in [account, savings, premium]: a.report()

Pass 1: a holds the plain account. Look for report in BankAccount — found immediately.

Pass 2: a holds the savings account. Look in SavingsAccount — found there, so the walk stops; the parent's report is never consulted.

Pass 3: a holds the premium account. Look in PremiumAccount — found there too.

Ravi: 1000.00 Meera: 2000.00 (savings at 5%) Zoya: 300.00 [premium]

The loop is three lines long and knows nothing about accounts. The objects carry their own answers.

Key idea
Write a method with the parent's name in the child and the child's version wins — that's overriding. Then for a in things: a.report() — one line of calling code, each object answering in its own way — that loop is polymorphism. There is no more to the word than that.
Common confusion

Overriding is not "having two versions of a method and Python picking by the arguments" — that's a different language's feature. In Python one name means one method per class, full stop. If a child defines withdraw, that child's objects have exactly one withdraw: theirs. The parent's still exists for the parent's own objects, and the child can borrow it on purpose with super().withdraw(amount) — but it will never be chosen automatically.

Worked example

Task: three kinds of account — plain, savings, premium — where withdraw and report behave differently, driven by one loop. Thinking: premium overrides withdraw to allow 500 of overdraft; savings and premium each override report. Then a single loop, blissfully ignorant of all of it.

15.3 · P3Stretch — override and keep the original

Sometimes you want the parent's behaviour plus a bit more. Override report() in SavingsAccount so it first calls the parent's version with super().report(), then prints a second line — two spaces, then interest rate: <rate>%.

Show solution
    def report(self):
        super().report()
        print(f"  interest rate: {self.rate}%")

super() means "my parent" wherever it appears, not just in __init__. This "run the old one, then add mine" shape is the most common override of all.

15.4

Has-a: composition — objects inside objects

Read · ~3 minPractice · ~10 min

The problem. You need a library. A library has a name and a shelf of books; each book has a title and an author. Inheritance is fresh in your mind and tempting — so should Library inherit from Book? Something in you already says no, and it's worth finding out exactly what.

The idea, in plain words. Unit 13's picture: an object is a box of boxes with abilities attached. Nothing said the inner boxes must hold numbers and strings. They can hold other objects — or a list of them. A Library object holds a box called books containing Book objects, and its methods work by asking those books to do things. That's composition: building a big thing out of smaller finished things, the way a car has an engine rather than being one.

The code shape is unremarkable, which is the nicest thing about it — you already know every line:

def __init__(self, name): self.name = name self.books = [] # an empty shelf def add(self, book): self.books.append(book) # a whole Book object goes in

No new syntax at all — just a list attribute, and objects going into it. The show() method then loops over self.books and prints each one, and because Unit 14 gave Book a __str__, printing a book prints something readable instead of a memory address.

Trace it by hand — a box of boxes of boxes
lib = Library("Adi's shelf") lib.add(Book("Small Things", "Roy")) lib.show()

Line 1: one Library object with two boxes: name holding the text, and books holding an empty list. Each library gets its own list, because the line runs afresh inside every __init__.

Line 2: the inner call runs first — a whole Book object is built (its own two boxes, title and author). That finished object is then handed to add, which appends it. The library's books list now holds one object, not one string.

Line 3: show reads len(self.books) → 1, then loops. Each loop variable is a real Book, so b.title works, and printing b goes through Book.__str__:

Adi's shelf holds 1 books: - Small Things by Roy

Two classes, neither of them a parent or a child, cooperating perfectly.

Fig. 2 — Left, the child points up at the parent and gains its abilities. Right, one object simply holds others in a list. Both are "reuse"; only one of them is a promise about what the object is.
Common confusion — the judgment, and how to make it

Inheritance is exciting and beginners over-use it. The test takes two seconds: say "is-a" out loud. "A Library is a Book" — nonsense; a library isn't a kind of book, it contains books. So: composition. "A SavingsAccount is a BankAccount" — that rings true; it's an account, with extras. So: inheritance. Try it anywhere: a Car is an Engine? No — a car has an engine. A Dog is an Animal? Yes. And when the sentence sounds half-right and you genuinely can't decide, prefer composition — it keeps the two classes independent, and a wrong "has-a" is far easier to unpick later than a wrong "is-a".

Worked example

Task: a library that holds books and can list them. Thinking: two plain classes, no parent-child anywhere. Book gets a __str__ so it prints nicely; Library keeps a list and loops over it. Notice how ordinary this is — composition is mostly just lists you already know how to use.

15.4 · P1A team has players

Fill in Team.add (append the player to the list) and Team.show (loop the list, printing <name>: <score> for each). A team is not a kind of player — this is has-a.

Ravi: 30 Nina: 45

    def add(self, player):

    def show(self):

The loop variable p is a whole Player object, so it still has its own boxes — p.name, p.score. Boxes inside boxes.

    def total(self):

15.4 · P3Stretch — both relationships in one program

A house has rooms (composition), and a studio is a house (inheritance) that describes itself differently. The parent is written; add Studio, overriding describe() to print <owner>'s studio: one open space of <area> sq m.

Ravi's house: 2 rooms, 30 sq m Nina's studio: one open space of 32 sq m
Show solution

15.5

Your build — shapes that measure themselves, and a party that fights

Read · ~2 minPractice · ~12 min

Two small builds, both landing on the same punchline from opposite directions. First shapes: every shape can tell you its area(), but each computes it its own way — so one printing loop handles circles and rectangles without ever asking which is which. Then a party of game characters, each with its own attack(), driven by one battle round.

If the loops in these two builds feel suspiciously identical, that's the lesson landing. Write them and you'll never need the word "polymorphism" explained again.

15.5 · P1Shapes — one loop, two formulas

Complete Circle.area() (use math.pi and self.radius ** 2) and Rectangle.area(), then write the loop that prints <name>: <area to 2dp> for every shape in the list.

Circle: 12.57 Rectangle: 12.00 Circle: 7.07
Show solution
class Circle(Shape):
    def area(self):
        return math.pi * self.radius ** 2

class Rectangle(Shape):
    def area(self):
        return self.width * self.height

for s in shapes:
    print(f"{s.name}: {s.area():.2f}")

Circle(2) is 12.566…, rounded to 12.57; the rectangle's honest 12 gets dressed as 12.00 by :.2f. Note the child __init__s hand a fixed name up to the parent — super() takes literal values just as happily as parameters.

15.6

Problem bank — everything at once

Practice · ~14 min

The mixed set: inheriting, extending with super(), overriding, the polymorphic loop, and one thing that simply holds another. In order; they get meaner. The last one reaches back to a class you wrote yourself two units ago.

B1Animals that speak for themselves

Give Dog and Cat their own speak() — <name> says Woof and <name> says Meow — then loop over the mixed list. No if, no isinstance: let the objects answer.

Blob makes a sound Rex says Woof Mango says Meow
Show solution
class Dog(Animal):
    def speak(self):
        print(f"{self.name} says Woof")

class Cat(Animal):
    def speak(self):
        print(f"{self.name} says Meow")

for a in [Animal("Blob"), Dog("Rex"), Cat("Mango")]:
    a.speak()

The textbook example, and it earns its fame: three classes, one call site, three behaviours.

B2Two years of interest

Build SavingsAccount properly: __init__ with super() plus a rate, and add_interest() that grows the balance by rate percent. Then add interest twice, reporting after each.

Meera: 1050.00 Meera: 1102.50
Show solution
class SavingsAccount(BankAccount):
    def __init__(self, owner, balance, rate):
        super().__init__(owner, balance)
        self.rate = rate

    def add_interest(self):
        self.balance = self.balance + self.balance * self.rate / 100

1000 → 1050.0 → 1102.5. Interest compounds because each round reads the new balance — the same "right side first, then store back" you learned with your very first box.

B3A school has students

Composition with a roll call. Complete add, count (return len of the list) and roll_call — the header line <school>: <n> students, then one line per student as <name> (<grade>). The school name is typed in; here it's fixed to Nehru High.

School name? Nehru High Nehru High: 3 students Asha (9) Dev (10) Nina (9)
Show solution
    def add(self, student):
        self.students.append(student)

    def count(self):
        return len(self.students)

    def roll_call(self):
        print(f"{self.name}: {self.count()} students")
        for s in self.students:
            print(f"{s.name} ({s.grade})")

roll_call calls self.count() rather than len(self.students) again — one method leaning on another of its own is perfectly normal, and it means the counting rule lives in exactly one place.

B4Stretch — inherit from your own Playlist

Unit 13's Playlist is the parent this time. Build KaraokePlaylist: its add(song, duet=False) passes the song up with super().add(song) and remembers duets in a second list; its show() overrides the parent's to tag those songs with (duet). Everything else stays inherited.

Friday night: - Tum Hi Ho - Senorita (duet) - Kabira - Shallow (duet)
Show solution
class KaraokePlaylist(Playlist):
    def __init__(self, name):
        super().__init__(name)
        self.duets = []

    def add(self, song, duet=False):
        super().add(song)
        if duet:
            self.duets.append(song)

    def show(self):
        print(f"{self.name}:")
        for s in self.songs:
            if s in self.duets:
                print(f"- {s} (duet)")
            else:
                print(f"- {s}")

Both overrides lean on the parent in different ways: add borrows it with super() and adds bookkeeping; show replaces it outright. And the default duet=False means the three plain calls still work unchanged — a child can extend a method's signature as long as old calls keep meaning what they meant.
