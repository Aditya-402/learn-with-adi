16.1

The open-door problem — and the underscore handshake

Read · ~3 minPractice · ~8 min

The problem. Unit 13 gave BankAccount a careful withdraw that checks the balance before taking money out. Very responsible. Then anyone, anywhere, can write one line — account.balance = -999 — and walk straight past every check you wrote. The front door is guarded and the wall has a hole in it.

The idea, in plain words. Most languages solve this with a lock: mark the box private and the compiler refuses to let outsiders touch it. Python does not have that lock. What Python has instead is a handshake: name the box with a leading underscore — self._balance — and every Python programmer alive reads that as "internal. Mine. Touch it at your own risk."

Be clear about what that means, because it surprises people: nothing is enforced. a._balance = -999 still works. The underscore is a convention, not a wall — a sign on the door, not a lock. And yet it works, reliably, everywhere, because the culture around it is genuine: code that reaches past an underscore is code that other programmers will not defend when it breaks. Python's bet is that a clear agreement between adults beats a lock that people spend their careers picking. It's a good bet.

So the shape of the fix has two halves, and this unit builds both:

  • Hide the real box. Rename self.balance to self._balance — that's the "internal" sign.
  • Offer a guarded way in. Give the outside world a balance it can read — and, if you allow writing at all, a way in that runs your checks first. That's 16.2 and 16.3.

The word for this — hiding the raw insides, exposing a checked surface — is encapsulation. It's the last of the four ideas that make a class a class, and it's the one that turns a bag of data into something you can trust.

Trace it by hand — the hole in the wall
class Account: def __init__(self, owner, balance=0): self.owner = owner self.balance = balance a = Account("Ada", 500) a.balance = -999 print(a.balance)

Line 6: a new object is built. Inside it, two labeled boxes: owner holding "Ada", balance holding 500.

Line 7: this is plain assignment into a box that happens to live inside an object. Python does not consult the class, does not run any method, does not check anything. It just stores. balance now holds -999.

Line 8: reads the box back out:

-999

No error, no warning, and a bank account holding minus nine hundred and ninety-nine rupees. Every check withdraw ever performed was optional.

Common confusion

"So _balance is private?" No — and it matters that you know it. a._balance reads and writes perfectly well; Python will never stop you. The underscore is a message to people, not an instruction to the interpreter. (There is a two-underscore form, self.__balance, which makes Python quietly rename the box so it's harder to reach by accident — but it's rarely worth the noise. One underscore is the everyday convention, and the one you'll see in real code.)

Worked example

Task: take a tiny class with a wide-open attribute and perform the first half of the fix — rename the store to an underscore name, and hand out a method that reads it. Thinking: nothing is protected yet. All we've done is move the box behind a sign and offer a polite way to look at it. That's still progress: there is now one named place through which the outside world is meant to arrive.

16.2

@property — a guarded window

Read · ~4 minPractice · ~10 min

The problem. Hiding the box behind _balance and offering account.get_balance() works, but look what it costs: every reader now has to remember the parentheses, and every piece of code that used the friendly account.balance has to be rewritten. Surely you can have both — the guard and the plain, pleasant spelling.

The idea, in plain words. You can. Write a method that returns the value, then put @property on the line above it:

@property def balance(self): return self._balance

Now account.balance — no parentheses, looks exactly like an attribute — quietly runs that method and hands back what it returns. It's a window cut into the wall: the outside sees a value, and your code decides what shows through. The old spelling is back, and the raw box stays behind the sign.

Two gifts come with it, free.

The first: read-only. Define a property with no way to write it, and assignment is refused — for real this time. account.balance = 999 raises an AttributeError, because Python looked for a setter and there isn't one. That's the first genuine "no" in this unit; it comes from the language, not from good manners.

The second: computed values. A property doesn't have to hand back a stored box. It can work the answer out, fresh, every single time it's read:

@property def area(self): return 3.14159 * self.radius ** 2

Change the radius and the area is right on the very next read — because there is no stored area to go stale. Compare that with computing the area once in __init__ and storing it: change the radius later and you're carrying a number that used to be true. A computed property cannot lie about a value it never kept. That is the whole reason people reach for them.

Trace it by hand — the value that stays fresh
class Circle: def __init__(self, radius): self.radius = radius @property def area(self): return 3.14159 * self.radius ** 2 c = Circle(2) print(f"{c.area:.2f}") c.radius = 3 print(f"{c.area:.2f}")

Line 9: the object holds exactly one box: radius = 2. There is no box called area. There never will be.

Line 10: Python sees c.area, finds no box of that name, finds a property on the class — and runs the method. 3.14159 × 2² → 12.56636, formatted to 12.57.

Line 11: the radius box now holds 3. Nothing else changed, because nothing else was ever stored.

Line 12: the method runs again, from scratch: 3.14159 × 3² → 28.27431 → 28.27.

12.57 28.27
Fig. 1 — Left: the plain attribute of Units 13–15, reachable by anyone in either direction. Right: the same spelling, but every read passes through code you wrote, and a write with no setter is turned away by the language itself.
Common confusion

A property is read without parentheses. c.area gives you the number; c.area() tries to call that number and dies with TypeError: 'float' object is not callable. And the reverse trap is worse because it's silent: forget the parentheses on a real method and a.count hands back the method object itself, so you print something like <bound method Jar.count of ...>. The rule is simple — if it's decorated with @property, drop the parentheses; otherwise keep them.

Key idea
A property makes a method wear an attribute's clothes. Reading looks free and simple; underneath, your code runs — so it can guard, convert, or compute. And a value that is computed on every read can never be stale.
Worked example

Task: both flavours in one program — a read-only window onto a hidden box, and a value that is worked out fresh each time. Thinking: notice that a.balance and c.area are spelled exactly like ordinary attributes. Nobody using this class needs to know or care that a method is running.

class Book:
    def __init__(self, pages):
        self._pages = pages

    @property
    def pages(self):

Two names, two jobs: _pages is where the value lives, pages is how the world is allowed to see it. Getting these two confused — writing return self.pages inside the property — makes the property call itself forever; Python stops it with a RecursionError.

16.3

Setters that say no

Read · ~3 minPractice · ~10 min

The problem. Read-only is a fine answer when a value should never be written from outside. But plenty of values should be writable — a volume level, a student's marks, an account balance the bank itself adjusts. You want the assignment to work, and you want it to be inspected on the way in.

The idea, in plain words. Add a second method with the same name, decorated with @<name>.setter. It receives the value someone is trying to store, and it can do anything it likes before storing it — including refusing:

@balance.setter def balance(self, value): if value < 0: raise ValueError("balance cannot be negative") self._balance = value

Read the decorator literally: @balance.setter means "attach this as the setter half of the property already called balance". So the getter must come first — the name has to exist before you can hang a setter on it. Both methods are called balance, and that is not a mistake: they're two halves of one thing.

Now a.balance = 800 quietly runs your check and stores. And a.balance = -999 — the line that started this unit — reaches your raise and stops the program dead. Unit 9 taught that raise is how a piece of code announces "I was asked for something impossible"; this is the moment it pays for itself, because the impossible request is now caught the instant it's made rather than three functions later when the numbers stop adding up.

At the call site, Unit 9's other half handles it politely:

try: a.balance = -999 except ValueError as e: print("Refused:", e)

This split has a name worth learning, because you will use it for the rest of your programming life: validate at the boundary, trust the inside. The setter is the boundary — the one place data enters the object. Check it there, once, thoroughly, and every method inside the class is then free to assume self._balance is a sensible number. No defensive re-checking, no "but what if it's negative" scattered through twenty methods. Guard the door and the house is safe.

Trace it by hand — the assignment that runs code
a = Account("Ada", 500) # _balance = 500 a.balance = 800 a.balance = -999 print(a.balance)

Line 2: Python sees an assignment to balance, finds a property, finds its setter, and calls it with value = 800. Inside: 800 is not less than 0, so self._balance = 800. The box now holds 800.

Line 3: the setter runs again with value = -999. This time the if is true, so raise fires. The assignment never happens — _balance is still 800 — and, with nothing catching it, the program stops right here:

ValueError: balance cannot be negative

Line 4: never reached. That's the point: bad data didn't get in, and it didn't get to travel.

Common confusion

Inside a setter, write self._balance = value — the underscore name. Writing self.balance = value calls the setter again, which calls it again, forever, until Python gives up with RecursionError: maximum recursion depth exceeded. It's the single most common property bug, and the traceback is a mile long, so recognise it early: the property is the door; _name is the room. A door that opens onto itself is not a door.

Worked example

Task: the full getter/setter pair on Account, with a good write, a bad write caught politely, and proof the object survived unharmed. Thinking: the object is now genuinely responsible for its own state. Not because outsiders are careful — because they can't get in any other way.

16.3 · P1A sensible age

Turn age into a property with a setter that refuses anything outside 0–120, raising ValueError("age must be between 0 and 120"). The code below the class must not change.

class Person:
    def __init__(self, age):
        self._age = age

    @property
    def age(self):
        return self._age

    @age.setter
    def age(self, value):

The third line of output is the important one: the refused write left the old value completely alone. A rejected change is a change that never happened.

16.3 · P3Stretch — a setter that also tidies

Setters can clean as well as refuse. Write a name property whose setter strips surrounding spaces, refuses an empty result with ValueError("name cannot be empty"), and stores the tidied name in Title Case (.strip() and .title() from Unit 6). Note __init__ assigns self.name — so the setter runs even at birth.

Ada Lovelace Refused: name cannot be empty Ada Lovelace
Show solution
class Student:
    def __init__(self, name):
        self.name = name

    @property
    def name(self):
        return self._name

    @name.setter
    def name(self, value):
        value = value.strip()
        if value == "":
            raise ValueError("name cannot be empty")
        self._name = value.title()

Two things worth pocketing. First, __init__ going through the property means the very first value is validated too — otherwise Student("") would slip past every guard you wrote. Second, the box _name is created by the setter on that first assignment; you never had to write it in __init__ at all.

16.4

Class attributes vs instance attributes

Read · ~3 minPractice · ~9 min

The problem. Every account at your bank prints the bank's name on its statement. The name is the same for all ten thousand of them. Storing self.bank_name = "Learn Bank" in __init__ means ten thousand identical copies — and if the bank is renamed, ten thousand objects are now wrong.

The idea, in plain words. Some facts belong to the cookie cutter, not to each cookie. Write them straight in the class body, outside any method:

class BankAccount: bank_name = "Learn Bank" # one box, on the class itself def __init__(self, owner): self.owner = owner # a box per object

That's a class attribute: one box, living on the class, shared by every instance ever made. self.owner is an instance attribute: a fresh box inside each object.

The magic is in how Python looks things up. When you write self.bank_name, Python checks this object first. No box of that name in there? It goes up to the class and looks again — and finds it. So self.bank_name works inside any method, even though no object ever stored it. Change BankAccount.bank_name once and all ten thousand statements say the new name on the next read, because they were all reading the same box the whole time.

Class attributes are where the shared, rarely-changing facts of a type go: a GST rate, a species name, a maximum size, a count of how many objects have been made.

Trace it by hand — lookup goes up, assignment doesn't
class Account: bank_name = "Learn Bank" a = Account() b = Account() print(a.bank_name) a.bank_name = "Ada's Vault" print(a.bank_name, b.bank_name)

Lines 4–5: two objects, both completely empty — not one box inside either of them.

Line 6: Python looks inside a for bank_name. Nothing. It looks up at the class. Found: "Learn Bank".

Line 7: here's the twist. Assignment never goes up. This does not change the class's box — it creates a brand-new box called bank_name inside a, holding "Ada's Vault".

Line 8: a.bank_name now finds its own box first and stops there. b still has nothing of its own, so it goes up and finds the class's untouched value:

Learn Bank Ada's Vault Learn Bank
Fig. 2 — Reading walks upward from the object to the class; writing always lands in the object. That asymmetry explains every class-attribute surprise you will ever meet.
Common confusion

Shadowing. self.bank_name = "Something" inside a method looks like it edits the shared value. It does not. It creates a private box in that one object that hides — shadows — the class's box from then on, for that object only. Everyone else carries on reading the shelf. To change the shared value you must name the class: BankAccount.bank_name = "Something". Same trap, sharper edge, when the class attribute is a list: self.items.append(x) doesn't create anything, so it mutates the one shared list and every object sees it. Class attributes want to hold plain, unchanging values — numbers, strings — and nothing else.

Worked example

Task: a class attribute read by two instances, then renamed once at the class — watch both follow. Thinking: nobody stored the name; both objects were reading the same box on the shelf all along.

16.5

Your build — BankAccount, final form

Read · ~2 minPractice · ~14 min

This is the checkpoint. Four units ago, BankAccount was a name, a number, and two methods that trusted everybody. Unit 14 taught it to print itself. Unit 15 taught it to have children. Now it learns to defend itself — and the result is the class you honestly could not have read on your first day of Unit 13.

The final specification, all of it:

  • The money lives in self._balance — behind the sign.
  • balance is a read-only property. The outside world can look; it cannot set.
  • deposit(amount) and withdraw(amount) are the only ways money moves. Both refuse a non-positive amount with ValueError; withdraw also refuses to overdraw.
  • A class attribute bank_name, used by report().
  • __str__ from Unit 14, so print(account) reads like English.

Three stages: the shell, the guards, then a scripted afternoon at the bank that walks straight into every single guard and bounces off all of them.

16.5 · P1Stage 1 — the shell

Build the class with the class attribute bank_name, the hidden _balance, a read-only balance property, and Unit 14's __str__ returning owner: balance.

class BankAccount:
    bank_name = "Learn Bank"

    def __init__(self, owner, balance=0):
        self.owner = owner
        self._balance = balance

    @property
    def balance(self):

    def __str__(self):

Inside the class, use self._balance — the real box. Outside, a.balance — the window. Get in the habit now and the recursion trap can never bite you.

16.5 · P2Stage 2 — the guards

    def deposit(self, amount):
        if amount <= 0:
            raise ValueError("deposit must be positive")

    def withdraw(self, amount):

16.5 · P3Stage 3 — an afternoon at the bank

The whole class, plus report() using the class attribute and formatting the money with :.2f, and a __str__ reading BankAccount(Ada, 1000). Then the scripted scenario below runs into every guard in turn. Fill in the class; the scenario is written for you.

BankAccount(Ada, 1000) Deposited 500 Refused: deposit must be positive Withdrew 300 Refused: insufficient funds Refused: balance is read-only Learn Bank | Ada: 1200.00
Show solution
class BankAccount:
    bank_name = "Learn Bank"

    def __init__(self, owner, balance=0):
        self.owner = owner
        self._balance = balance

    @property
    def balance(self):
        return self._balance

    def deposit(self, amount):
        if amount <= 0:
            raise ValueError("deposit must be positive")
        self._balance = self._balance + amount

    def withdraw(self, amount):
        if amount <= 0:
            raise ValueError("withdrawal must be positive")
        if amount > self._balance:
            raise ValueError("insufficient funds")
        self._balance = self._balance - amount

    def report(self):
        return f"{self.bank_name} | {self.owner}: {self._balance:.2f}"

    def __str__(self):
        return f"BankAccount({self.owner}, {self._balance})"

Read that scenario once more and notice what it proves. Three different attacks — a negative deposit, an impossible withdrawal, a direct write to the balance — and the object turned all three away without a single line of checking at the call site. Every guard lives inside the class, where it belongs. That is encapsulation, and that is the Intermediate level, complete.

class Product:
    gst_rate = 0.18

    def __init__(self, name, price):
        self.name = name
        self.price = price

When the rate changes in next year's budget, you edit one line and every product in the shop is correct. That's the whole argument for class attributes in eleven words. (Note price_with_tax() keeps its parentheses — it's a method, not a property. Either design is defensible; a property would read nicer, a method makes the computation obvious.)

B4Stretch — the club's oldest member

A Club keeps its members in self._members, a list of (name, age) tuples. Add add(name, age) and a read-only computed property oldest_member that returns the name of the oldest — or None when the club is empty. It must be right after every single addition, without anyone updating it.

None Grace Edith
Show solution
class Club:
    def __init__(self, title):
        self.title = title
        self._members = []

    def add(self, name, age):
        self._members.append((name, age))

    @property
    def oldest_member(self):
        if len(self._members) == 0:
            return None
        oldest = self._members[0]
        for member in self._members:
            if member[1] > oldest[1]:
                oldest = member
        return oldest[0]

Nobody ever "updates the oldest member", because there is nothing to update — the answer is derived from the list at the moment you ask. Every stored summary in a program is a promise to keep it in step with reality; a computed property is the same answer with no promise to break.

The Intermediate level is complete

Unit 17 · Iterators & the iteration protocol

Stop and take this in. Four units ago a class was a strange word with a colon after it. Now your objects build themselves, print themselves in plain English, compare by what they mean rather than where they sit in memory, inherit from a parent, hold other objects inside them, and refuse bad data at the door. That's the Intermediate level, finished — and it's the hardest conceptual climb in this series.

Now the door to Advanced. Everything so far has been about writing your own things. From here on you'll be reaching into Python's own machinery — and you already hold the keys, because that machinery is made of exactly the dunder methods you've been writing. First question, and it's a better one than it sounds: what does a for loop actually do? You've written hundreds of them since Unit 4 and never once been told. The answer is a protocol — a small, precise agreement — and any class of yours can join it. Once it does, your objects work in for loops as if Python had shipped them itself.
