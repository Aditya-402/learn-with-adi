20.1

Wrapping a function by hand

Read · ~4 minPractice · ~10 min

The problem. You have twelve functions that work. Now someone wants every one of them to announce itself — print a line before it runs and a line after. You could paste two prints into all twelve bodies, and then paste them again into the thirteenth next week, and then hunt them all down when the wording changes. There must be a way to add behaviour around a function without opening it up.

The idea, in plain words. Don't change the function. Build a new function that does the extra bit, calls the old one in the middle, and hands back whatever the old one returned. The original stays untouched; the new one wears it like a coat. Unit 19 already gave you every tool this needs — a function can take a function as an argument, define a function inside itself, and return that inner function as a value.

Here is the whole pattern, and it is worth reading twice:

def announce(func): def inner(*args, **kwargs): print("-- starting --") result = func(*args, **kwargs) print("-- finished --") return result return inner

Read it from the outside in. announce takes one thing: a function. It defines inner, which prints, calls func, prints again, and returns func's answer. Then — and this is the line beginners skip — announce returns inner without calling it. No parentheses. It hands back a function, ready to be called later.

Two details do a lot of quiet work. *args, **kwargs means inner accepts any arguments and forwards them untouched, so the same wrapper fits a function of one argument, five arguments, or keyword arguments — you don't have to know. And return result means the wrapper passes the answer through instead of eating it; forget that line and every wrapped function starts returning None.

Trace it by hand — the coat goes on
def add(a, b): return a + b loud_add = announce(add) print(loud_add(2, 3))

Line 1–2: a box called add holds a function. Nothing else happens.

Line 4: announce(add) runs now. Inside it, the parameter func holds the add-function. It defines inner and returns it. The box loud_add now holds that inner function — and crucially, that inner function walked out of announce carrying func in its packed lunchbox. That's Unit 19's closure, and this is what it was for.

Line 5: loud_add(2, 3) calls inner. args becomes (2, 3). It prints, opens its lunchbox to find func — still the original add — calls func(2, 3) → 5, prints again, returns 5. The outer print shows it.

-- starting -- -- finished -- 5

The original add is untouched. It never learned it was wearing a coat.

Fig. 1 — A decorator is a function factory. It runs once, builds a new function, and that new function leaves with the original tucked in its lunchbox. Every decorator in this unit is this picture.
Common confusion

return inner versus return inner(). With parentheses you would call inner immediately and return whatever it printed back — usually None, and at the wrong moment. Without parentheses you return the function itself, unrun, for someone to call later. Unit 19's rule holds: parentheses mean "do it now"; a bare name means "the thing itself".

Worked example

Task: build announce and wrap add by hand — no new syntax at all, only Unit 19 tools. Thinking: take a function in, define an inner that sandwiches a call to it, return the inner. Then store the result in a new name and call that. Watch the order of the three output lines: both prints happen inside the call, before print(loud_add(2, 3)) gets anything to show.

20.1 · P1Wrap a different function

The wrapper is written for you. Add a greet(name) that returns f"Hello, {name}", wrap it by hand into a box called loud_greet, and print the result of calling it with "Adi".

-- starting -- -- finished -- Hello, Adi
Show solution
def announce(func):
    def inner(*args, **kwargs):
        print("-- starting --")
        result = func(*args, **kwargs)
        print("-- finished --")
        return result
    return inner

def greet(name):
    return f"Hello, {name}"

loud_greet = announce(greet)
print(loud_greet("Adi"))

The same wrapper fitted a one-argument function without a single change — that's *args earning its keep.

20.2

The @ syntax — one line of sugar

Read · ~3 minPractice · ~10 min

The problem. Wrapping by hand works, but look at what it costs: you define add, then two lines later you write loud_add = announce(add), and now there are two names floating about and everyone calling your code has to remember which one is the good one. The wrapping is written far away from the function it applies to.

The idea, in plain words. Python gives you a shorthand that puts the wrapping right on top of the def, where you can't miss it:

@announce def add(a, b): return a + b

And that is exactly, precisely, character-for-character equivalent to:

def add(a, b): return a + b add = announce(add)

Nothing more. No magic, no hidden machinery, no new concept — the @ line is syntax sugar for one assignment. Python defines the function, passes it to announce, and stores whatever comes back under the same name add. From then on, the name add refers to the wrapper, and the original function survives only inside the wrapper's lunchbox. A function used this way has a name: it is a decorator.

Because the wrapper receives the function it decorates, it can also read facts about it. Every function knows its own name in func.__name__ — the same dunder territory as Units 13–16 — which makes a genuinely useful logging decorator about six lines long.

Trace it by hand — when does the @ line run?
def noisy(func): print("decorating now") def inner(*args, **kwargs): print("running now") return func(*args, **kwargs) return inner @noisy def hello(): print("hello") print("--- defined ---") hello()

The def, with its @: Python builds hello, then immediately calls noisy(hello). So decorating now prints here, at definition time, before your program has really started doing anything.

Then --- defined --- prints. Then the single call to hello() runs inner: running now, then the real body's hello.

decorating now --- defined --- running now hello

Call hello() ten more times and decorating now never appears again. The decorator ran once; the wrapper it built runs every time.

Key idea
@announce above def add means add = announce(add). One assignment, applied at definition time. If you can say that sentence, you understand decorators — everything else is what you choose to put inside the wrapper.
Common confusion

The @ line does not run on every call. It runs once, when Python reaches the def. Put a print in the decorator's body (outside inner) and you'll see it fire exactly once no matter how many times the function is called afterwards. Anything you want to happen per call must live inside inner.

The polite habit — functools.wraps
A wrapped function quietly loses its identity: add.__name__ becomes "inner", because the name add now points at the wrapper. Putting @functools.wraps(func) on inner (after import functools) copies the original's name and documentation across, so tools and error messages keep telling the truth. It's one line, it costs nothing, and real code always includes it. Shown here once; use it from now on.
Worked example

Task: a logging decorator that reports which function was called, with what arguments, and what it gave back. Thinking: the wrapper already holds func, so func.__name__ is free; args is a tuple and drops straight into an f-string. Note that 12 prints twice — once by the logger, once by the outer print.

20.2 · P3Stretch — give the function its name back

Show solution
import functools

def logged(func):
    @functools.wraps(func)
    def inner(*args, **kwargs):
        return func(*args, **kwargs)
    return inner

@logged
def area(w, h):
    return w * h

print(area.__name__)

Without it you get inner — every decorated function in your program answering to the same name, which makes debugging miserable. functools.wraps is itself a decorator, applied to inner. Decorators all the way down.

20.3

Decorators that count and transform

Read · ~3 minPractice · ~10 min

The problem. Announcing and logging only watch. A wrapper sits in a position of real power: it sees every call going in and every answer coming out. What can it do with that — remember things between calls, or change the answer on its way out?

The idea, in plain words. Both, and neither needs a new concept.

Remembering between calls. A counter has to survive from one call to the next, and it can't be an ordinary variable inside inner — that box is created fresh every call and thrown away at the end. It can't simply be a variable in the enclosing function either: reading the lunchbox is free, but assigning to a name inside inner makes a brand-new local box instead of updating the captured one (Unit 19's sharpest edge). The honest, readable way out is to hang the counter on the function object itself — functions are values, and values can carry attributes:

inner.count = 0 # a box stuck onto the function inner.count = inner.count + 1 # inside inner, per call

Because inner.count is a box on an object, not a plain name, assigning to it changes the object rather than creating a local — the same reason self.total = ... worked in Unit 13. (A list captured in the lunchbox — calls = [0], then calls[0] = calls[0] + 1 — works for the same reason and is worth recognising when you meet it, but the attribute reads better.)

Changing the answer. Even easier: catch the result, alter it, return the altered version. The caller sees only what the wrapper hands back — a wrapper that returns result.upper() + "!" turns every polite function into an enthusiastic one without the function knowing.

These two moves cover most real decorators. Timing a function, retrying it three times if it fails, checking whether the user is logged in before letting the call through — all of them are this same shape: do something, call func, do something, return the result.

Trace it by hand — a counter that survives
@call_counter def ping(): print("pong") ping() ping()

At the def: call_counter(ping) runs, builds inner, sets inner.count = 0, returns inner. The name ping now holds that wrapper, with a count box attached reading 0.

First call: inner.count goes 0 → 1, prints call #1, then the real body prints pong.

Second call: the same wrapper object is still there with its count box — 1 → 2. Nothing was reset, because the decorator never ran again.

call #1 pong call #2 pong
Common confusion

Stacking decorators reads bottom-up. @excited above @call_counter above def cheer means cheer = excited(call_counter(cheer)) — the one nearest the def is applied first, so it ends up innermost, closest to the real function. At call time the outermost wrapper runs first and the innermost last. Read the stack downwards to see who wraps whom, upwards to see who speaks first.

Worked example

Task: a decorator that numbers every call to whatever it wraps. Thinking: the count must live somewhere that outlives a single call, so it goes on inner itself, initialised after def inner and before return inner. Predict the six lines before running.

20.3 · P1The excited decorator

Write excited: it calls the wrapped function, then returns the result uppercased with an exclamation mark added. The greet function below must not be edited — all the enthusiasm comes from the wrapper.

HELLO, ADI!
Show solution
def excited(func):
    def inner(*args, **kwargs):
        result = func(*args, **kwargs)
        return result.upper() + "!"
    return inner

The wrapper intercepted the answer on its way out. greet still returns its quiet lowercase string — it just never reaches the caller unaltered.

20.3 · P2Count a function that returns

Apply call_counter to square(n) and call it twice, printing each answer. Watch the interleaving: the counter line comes out before the answer line, every time.

Show solution
@call_counter
def square(n):
    return n * n

print(square(3))
print(square(5))

print(square(3)) can't print anything until square(3) has finished — and the counter line is printed during that call. Inside always finishes before outside starts printing.

Put both decorators on one function: @excited on top, @call_counter underneath, on cheer(team) which returns f"go {team}". Predict the two output lines first, then check.

Desugared: cheer = excited(call_counter(cheer)). 20.4

Context managers — what with really does

Read · ~4 minPractice · ~10 min

The problem. Some things must be paired. Open a file, close it. Print a heading, print a footer. Start a database transaction, finish it. And the pairing has to hold even when the work in the middle explodes — a file left open because line 4 raised an error is exactly the bug that ruins a program at three in the morning. Wrapping every such block in try/except by hand is possible and nobody does it reliably.

The idea, in plain words. Back in Unit 10 you wrote with open("notes.txt") as f: and these notes promised the full story later. Here it is, and it is smaller than you expect. with X as y: does three things:

  • Going in, it calls X.__enter__(). Whatever that method returns is what lands in y.
  • Then it runs the indented block.
  • Going out, it calls X.__exit__(...) — always. Normal finish, early return, or an exception tearing through the middle of the block: __exit__ runs. That guarantee is the entire reason with exists.

An object with those two dunder methods is called a context manager. That's it — no registration, no special base class. Units 13–16 taught you that __init__, __str__ and friends are hooks Python calls at the right moment; __enter__ and __exit__ are two more hooks, called at the two edges of a with block. open() returns an object that has them; so can yours, in eight lines.

class Section: def __init__(self, name): self.name = name def __enter__(self): print(f"--- BEGIN {self.name} ---") return self def __exit__(self, exc_type, exc_value, traceback): print(f"--- END {self.name} ---")

__exit__ takes three extra parameters, and they're a courtesy: if the block blew up, Python passes in the type of exception, the exception itself, and its traceback, so a context manager can react to failure — logging it, rolling back a transaction. If the block finished cleanly, all three are None. You are free to ignore them, as we do here, and simply run your cleanup either way.

Trace it by hand — the promise under fire
try: with Section("Risky"): print("about to fail") raise ValueError("bad data") print("never reached") except ValueError as e: print("caught outside:", e)

Going in: Section("Risky") is built, then __enter__ runs and prints the BEGIN line. (There's no as here — the returned object simply has nowhere to land, which is fine.)

The block: about to fail prints. Then raise fires. The line after it never runs — the block is abandoned mid-flight.

Going out: before that exception is allowed to travel any further, Python calls __exit__ — so the END line prints. Then the exception continues on its way and Unit 9's except catches it outside.

--- BEGIN Risky --- about to fail --- END Risky --- caught outside: bad data

Read that output again. The END line appears after the failure and before the catch. Nothing you can do inside the block can skip it.

Fig. 2 — Every exit from a with block passes through __exit__. That single guarantee is why with open(...) was safe back in Unit 10, and why you never had to write f.close().
Key idea
with X as y: is y = X.__enter__(), then your block, then X.__exit__(...) — and the last step happens whether the block succeeds, returns, or raises. Pair anything that must be paired by putting it in those two methods.
Common confusion

Running __exit__ does not swallow the error. The cleanup happens, and then the exception carries on outward exactly as if the with weren't there — you still need a try/except if you want to handle it. (A context manager can suppress an exception by having __exit__ return True, which is a sharp tool used rarely and never by accident. Return nothing, as we do, and errors pass through politely.)

The short way — contextlib
Writing a whole class for two print statements feels heavy, and Python agrees. Decorate a generator function that has exactly one yield with @contextmanager from the contextlib module: everything before the yield is the __enter__ half, everything after it is the __exit__ half. Unit 18's generators and this unit's decorators, shaking hands. Try it in P3 below.
Worked example

Task: build Section and prove the guarantee by breaking the block on purpose. Thinking: two dunder methods, a deliberate raise in the middle, and Unit 9's try/except outside to catch what comes out — so the program ends tidily and you can read the order for yourself.

20.4 · P1Write the two hooks

Finish Section: __enter__ prints the BEGIN line and returns self; __exit__ prints the END line. Then use it around two prints.

--- BEGIN Report --- line one line two --- END Report ---
Show solution
class Section:
    def __init__(self, name):
        self.name = name

    def __enter__(self):
        print(f"--- BEGIN {self.name} ---")
        return self

    def __exit__(self, exc_type, exc_value, traceback):
        print(f"--- END {self.name} ---")

__exit__ must accept those three parameters even if it ignores them — Python always passes them. Leave them out and you get a TypeError at the end of the block, which is a confusing place to meet one.

20.4 · P2Prove the guarantee

Make the block fail on purpose. Inside with Section("Load"): print reading file and then raise ValueError("file missing"); catch it outside with try/except and print caught: and the message. Note where the END line lands.

--- BEGIN Load --- reading file --- END Load --- caught: file missing
Show solution
try:
    with Section("Load"):
        print("reading file")
        raise ValueError("file missing")
except ValueError as e:
    print("caught:", e)

END before the catch — the cleanup runs while the exception is still travelling. This is precisely why Unit 10's files were never left open, no matter what went wrong while reading them.

20.5

Your build — the report runner

Read · ~2 minPractice · ~12 min

This is the last build of the language, so let's make it count. A small report runner: report functions that each print a summary, a @logged decorator that narrates every call, and Section blocks that frame each day's output — with one report that refuses bad data and blows up, caught politely so the framing still closes.

Look at what goes into thirty lines. Functions as values and closures (the decorator). *args/**kwargs (the wrapper). Dunder protocols and classes (the context manager). Dictionaries and loops (the totals). Error handling (the failing report). f-strings with :.2f (the money). That is nearly the whole series, cooperating.

Three stages. Build them in order and read every line of output before moving on.

20.5 · P1Stage 1 — the logged report

Write logged: it prints [log] calling <name>, calls the function, prints [log] <name> done, and returns the result. Apply it to sales_summary, which prints the item count and the total. Mind the two leading spaces on the report's own lines.

[log] calling sales_summary items: 3 total: 87.75 [log] sales_summary done
Show solution
def logged(func):
    def inner(*args, **kwargs):
        print(f"[log] calling {func.__name__}")
        result = func(*args, **kwargs)
        print(f"[log] {func.__name__} done")
        return result
    return inner

@logged
def sales_summary(items):
    ...

12.5 + 45.25 + 30.0 = 87.75. The report function has no idea it is being logged, which means you can log the next twelve reports by typing one line above each.

20.5 · P2Stage 2 — frame it

Bring Section back and run the logged report inside a with Section("Daily report"): block. Six lines of output, nested two deep — predict their order before you run.

--- BEGIN Daily report --- [log] calling sales_summary items: 3 total: 87.75 [log] sales_summary done --- END Daily report ---
Show solution
with Section("Daily report"):
    sales_summary({"tea": 12.5, "cake": 45.25, "dosa": 30.0})

Three layers of framing, each closing in the right order: section, log, report, log, section. Nothing in the report function knows about either layer.

20.5 · P3Stage 3 — the whole machine

Two reports now, run over two days. Tuesday has no sales, so top_seller raises. Fill in the last block: a with Section("Tuesday"): that calls top_seller(tuesday), wrapped in a try/except printing report skipped: and the message. Then read the expected output very carefully — one of the [log] ... done lines is missing, and you should be able to say why before you run it.

--- BEGIN Monday --- [log] calling sales_summary 3 items, total 87.75 [log] sales_summary done [log] calling top_seller best: cake at 45.25 [log] top_seller done --- END Monday --- --- BEGIN Tuesday --- [log] calling top_seller --- END Tuesday --- report skipped: no sales to rank
Show solution & the missing line
try:
    with Section("Tuesday"):
        top_seller(tuesday)
except ValueError as e:
    print("report skipped:", e)

The missing line is [log] top_seller done for Tuesday. The raise happened inside func(*args, **kwargs), so the wrapper's next line never ran — a plain decorator offers no guarantee at all when things fail. The --- END Tuesday --- line, by contrast, printed anyway, because __exit__ does. That contrast, in one program, is the whole unit: decorators wrap behaviour, context managers guarantee cleanup, and you need both.

20.6

Problem bank — everything at once

Practice · ~14 min

The last mixed set of the language. Wrappers that transform, wrappers that repeat, blocks that pair, and a final exam in reading output order. In order; they get meaner.

B1The shout decorator

Write shout: it uppercases whatever the wrapped function returns and adds three exclamation marks. greet must stay exactly as it is.

GOOD MORNING, ADI!!!
Show solution
def shout(func):
    def inner(*args, **kwargs):
        return func(*args, **kwargs).upper() + "!!!"
    return inner

Transform on the way out. Note the wrapper never prints — it returns, and the caller prints. Wrappers that print when they should return are hard to reuse.

B2Do it twice, keep both

Write repeat_twice: it calls the wrapped function twice and returns a list of the two results. The function's own printing should therefore appear twice.

rolling rolling [6, 6]
Show solution
def repeat_twice(func):
    def inner(*args, **kwargs):
        first = func(*args, **kwargs)
        second = func(*args, **kwargs)
        return [first, second]
    return inner

A wrapper is under no obligation to call the function exactly once. Call it twice, call it zero times, call it again if it fails — that last one is the retry decorator every networked program has.

B3Indent — a pairing you can see

Write an Indent context manager: __enter__ prints >> and returns self, __exit__ prints <<. Then nest one with inside another as shown and check the pairing — every >> gets its <<, innermost first.

>> outer work >> inner work << back outside <<
Show solution
class Indent:
    def __enter__(self):
        print(">>")
        return self

    def __exit__(self, exc_type, exc_value, traceback):
        print("<<")

No __init__ needed — a context manager only owes Python those two methods. The inner block closes before the outer one continues, which is exactly how nested brackets, nested tags and nested function calls behave. Same shape everywhere.
